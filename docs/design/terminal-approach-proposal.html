Terminal Approach Proposal

Should Claude Code and Codex stay embedded inside Bubble Tea, or run in native tmux panes with Bubble Tea as a control pane?

NOT ADOPTED: the user chose option B, keep embedded panes Nothing here has been run Testing is still not authorized (GR-3) 2026-11-04 Owner: design.architect

Outcome, 2026-11-04: the user chose option B. Panes stay embedded in Bubble Tea, and tmux isn't used. This document is kept as a record of the alternative. The rest of it is unchanged from when it was proposed, so it doesn't describe the current design. See the design.

Recommendation at the time: switch to tmux panes, with Bubble Tea as a control pane. Embedding means hosting two demanding terminal apps inside a young emulator, and most of the risk sits there. tmux removes that, and it also keeps agents alive when an SSH connection drops.

This conflicts with your decision to embed the panes. Bubble Tea would no longer be the whole window. tmux also becomes a required install, and rtk loses sight of your keystrokes, which weakens draft protection (section 4). Only you can make this change: the current design stays in force until you do.

How to read the evidence. SEEN observed on this machine. DOCS from man pages or source, read but not run. MEMORY general knowledge, not checked for this proposal. TEST unknown until tested. Unlabelled text is proposal.

1. Why reconsider now

No test has shown embedded panes failing. Reading the source shows how much has to go right. From docs/implementation/pane-risks.md DOCS:

  • Keyboard: x/vt v0.1.0 has no Kitty, CSI-u or modifyOtherKeys support. Harnesses see a legacy terminal, and modified keys beyond the fallback don't work.
  • Scrollback: currently bounded at one line, because the library's zero setting has no effect. Scrolling back through an agent's output would need separate work.
  • Terminal queries: unsupported ones are ignored, so a harness that waits on one could hang or degrade.
  • Hard concurrency: cancellation on macOS, emulator close and write ordering each need careful handling, and all of it is untested.
  • Lifetime: agents live inside the TUI process, so a dropped SSH session to your Ubuntu server may kill them.

Each is fixable, but together they make the team responsible for a terminal host, which isn't the product. This is what frontend's first version already had to deal with.

4. What tmux does not fix

tmux removes emulator risk. It doesn't make delivery safe by itself:

  • Drafts can be merged, and this is the main loss. Embedded could over-hold, but it knew you'd typed something. Under tmux, the proposed rule is: hold while any key was pressed in the last 10 seconds, then deliver when idle. If you leave a half-written prompt and pause, an arriving message is pasted after it and both are submitted. F4 still delivers immediately.
  • Typing races. Your keystroke can land between the check and the paste, or between the paste and Enter. The window is small, but it's there. OpenRig documents the same race DOCS.
  • The gate still depends on hooks. If a hook misreports, a paste can still reach a prompt. Codex's hook trust review and session ID behaviour are still unknown TEST.
  • Paste behaviour per harness is still untested. Paste timing and how each harness treats a paste aren't verified on this design TEST.
  • New failure modes. tmux version differences, terminal type settings, key bindings when nested, and a leftover private server after a crash.

A possible later fix for drafts: OpenRig reads the visible input box before pasting, and refuses if it holds text or can't be read DOCS. That's screen reading per harness, which breaks on updates, but its failure mode is to hold, so it's much safer than using the screen for agent state. I'd leave it out of the first version.

6. Effect on the work so far

  • Kept as is: internal/store, message states, MCP tool and SQLite history.
  • Small changes expected: the router gets draft information from key timing, and sees your submissions through the UserPromptSubmit hook when the prompt has no message frame. Whether that hook carries the prompt on both harnesses is unverified TEST. internal/agent launches through tmux, and its terminal settings are redone. F4 moves to a tmux key binding, because rtk no longer receives your keys. Exit codes come from tmux (pane_dead_status) instead of a child process. A write's result becomes "tmux accepted the command", which is weaker than "every byte reached the PTY", so the status wording must say so. "Run ended" no longer proves the agents ended, unless the shutdown wrapper worked. Lead reviewed this by reading the code: store, server, hooks and session binding carry over.
  • Replaced: internal/pane becomes a thin tmux driver behind the existing PasteSubmit boundary. The parts of internal/tui that render panes and forward keys go; its log, status and history stay.
  • Cost: most of the recently written pane code would be retired. Nothing gets deleted until you decide. That's cheap now compared with later, which is your point in raising this.

7. Decision needed

Replace decision 2, "panes embedded in Bubble Tea"?

  • Option A (recommended): native tmux panes with a Bubble Tea control pane. Accepts a required tmux install, Bubble Tea no longer being the whole window, and the draft risk in section 4.
  • Option B: keep embedded and accept that its risks stay open until testing. Pause ends and pane work resumes.

If you choose A, one setting has a default you may want to change: the 10-second rule for drafts. The stricter alternative never auto-delivers to the pane you're focused on, which is safer but means pressing F4 whenever you're waiting in that pane for a reply.

Neither option authorizes testing, and the current design stays in force until you choose. Neither proves the choice works: A has better evidence, but it hasn't been run on this design either.
