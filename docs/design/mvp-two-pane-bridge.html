Two-Pane Bridge

A small Go program with a Bubble Tea TUI that runs Claude Code and Codex side by side and lets them message each other.

v0.17: the user reports mouse focus, Ctrl+C, automatic Codex startup and messages both ways working by hand on macOS; the team has run nothing, and no automated test has run Implemented, compile-checked only With delivery lead 2026-11-04 Owner: design.architect

The design in brief. One Go binary owns both terminal sessions. An agent sends by calling a ratatoskr_send tool over MCP, which both harnesses support. The program delivers by typing into the recipient's pane, but only when hooks report that recipient is idle. Both directions use the same code, and neither harness needs a plugin in another language.

The riskiest part is not messaging. It is whether two full-screen TUIs render and take keyboard input properly inside Bubble Tea. That gets tested first, with tmux as the known alternative if it fails (section 4).

How to read the evidence. The team has run nothing here. The user's hand runs are the only observations. They found the mouse and Ctrl+C bugs in section 4, and the user then reported that mouse focus and Ctrl+C work on the fixed build. A later hand run on Codex 0.166.0, traced read-only by the architect, showed messages reaching Codex and being accepted, with its launch config, MCP connection, hooks and session binding working, and found two problems: decisions 10 and 11. Everything else here is still untested. Open items are in Outstanding issues. HELP installed CLI help (Claude Code 2.1.311, Codex 0.166.0). DOCS vendor docs read 2026-11-04. CONSULT codebase-explorer's source analysis of other projects. TEST unverified, must be tested. Everything else is proposal.

4. How the panes work

Reconfirmed by the user, 2026-11-04: keep panes embedded in Bubble Tea. The user considered a proposal to switch to tmux panes and chose not to. The known risks stay open and untested until the user has testing run.

A. Embedded in Bubble Tea (chosen)B. tmux splits (known alternative)
HowGo runs each harness in a PTY, feeds its output to an emulator, and draws the result inside a Bubble Tea pane.Go creates a tmux window with split panes. Bubble Tea runs in a third pane as a status and log bar.
GainsOne binary with no other dependency. The whole window is the TUI. The program sees every keystroke, so it can avoid pasting over something you're typing.tmux has already solved rendering and input, so much less code is needed.
CostsColours, wide characters, redraw speed and key translation all have to work through a young emulator.Needs tmux installed. Key handling, focus and layout mostly belong to tmux, so Bubble Tea is only part of the experience.

Decision: A, chosen by the user, and tested first in a time-boxed spike. If either harness is unusable, the choice goes back to the user, with B as the known alternative. The messaging design doesn't change either way, because the router only needs a way to write to a pane.

Mouse

Reported by the user, 2026-11-04: clicks didn't switch panes, because the first version never turned mouse reporting on. ratatoskr now owns the mouse, by these rules. TEST

EventWhat happens
Left click in a pane that isn't focused, on its body or headerFocus moves there. The click isn't passed to the harness.

The cost: while ratatoskr holds the mouse, selecting text needs the terminal's bypass modifier, usually Shift, or Option in some macOS terminals.

Ctrl+C

Decided by the user, 2026-11-04. In the user's first hand run, the whole UI froze on Ctrl+C. The user reports Ctrl+C working on the fixed build, but the freeze's cause was never established. The rule that prevents it is under "Shutting down" in section 11. Separately, the user expected Ctrl+C to stop rtk, but it goes to the focused harness so that it can interrupt a turn. This contract keeps that and adds a way out. TEST

The cost: one harness can't be exited with its own double Ctrl+C, and an accidental double press can end both agents. The time limit is a guess.

Known risk, from reading source only and not observed: frontend reports that x/vt v0.1.0 has no Kitty, CSI-u or modifyOtherKeys keyboard support, and no Shift+Enter encoding. The plan is for harnesses to see a legacy terminal, with Shift+Enter mapped to a documented newline input in one isolated function. This doesn't show that panes are unusable, but it puts "use each pane normally" (section 12) at risk.

5. Messaging options

Each direction has two separate problems: how the sender gets a message out and how it gets into the receiver. Getting in is the hard part, because neither harness has one documented, stable way to accept input from outside while its TUI is running.

Same in both directions

Sender calls MCP ratatoskr_send→ Router queues it and waits until the recipient is idle→ Bracketed paste + Enter into recipient's PTY

Gains

  • One code path. Both harnesses support MCP tools and the same hook names. DOCS
  • The token is issued at launch, so the sender isn't something the model types in.
  • Each tool can be pre-approved, so sending needn't prompt. HELP DOCS
  • You see the message arrive in the pane.

Costs

  • Delivery is typed input, so it reads as a user turn. The message frame must say it came from a peer.
  • Pasting at the wrong moment could disturb a prompt, so the gate must be conservative.
  • Relies on hooks being accurate, including after interrupts. TEST

Same in both directions

Sender runs ratatoskr send --to codex in its shell→ Router queues it and waits until the recipient is idle→ Bracketed paste + Enter into recipient's PTY

Gains

  • The least code: no MCP dependency.
  • Easy to run by hand when debugging.

Costs

  • Codex's workspace-write sandbox may stop the command reaching the program. The docs show a network opt-in, but say nothing specific about localhost or Unix sockets. DOCS TEST
  • Quoting multi-line text through a shell is error-prone.
  • Identity comes from an environment variable that the agent can read or override.

Claude → Codex

MCP ratatoskr_send→ Router→ App server turn/start, or turn/steer if busy; TUI attached with codex --remote

Codex → Claude

MCP ratatoskr_send→ Router→ Channel notification notifications/claude/channel

Gains

  • No typing into terminals, so no risk of disturbing a prompt or a draft.
  • Codex's app server also reports events, which may replace its hooks. TEST
  • Queued channel events arrive together on the next turn. DOCS

Costs

  • Channels are a research preview. Custom ones need --dangerously-load-development-channels, and Team or Enterprise accounts need an owner to enable them. DOCS
  • The CLI marks the app server experimental. HELP
  • Two different paths to build and test. Whether a turn started by another client appears in the attached TUI is unverified. TEST

Same in both directions

Sender writes to a mailbox through a tool or file→ Message waits in the mailbox→ Recipient's Stop hook returns decision: block with the message, or the agent checks its inbox

Gains

  • No terminal typing at all.
  • Both harnesses can continue a turn from a Stop hook. DOCS
  • Delivery lands at the end of a turn, which is a clean moment.

Costs

  • It can't wake an idle agent. If both are idle, the conversation stops, which is the normal case for "ask and wait".
  • Asking agents to poll wastes model turns and relies on them doing it.

Claude → Codex and Codex → Claude

Router→ Claude's inbox socket at messagingSocketPath
Router→ Codex thread/queue/add JSON-RPC, or the codex queue CLI

Gains

  • agent-net's code uses these paths, and its own Linux spikes report messages queuing behind a running turn. CONSULT
  • codex queue is a shipped command, so that half is less exposed. HELP

Costs

  • The Claude socket's support status was not established, and it is untested on macOS. CONSULT TEST
  • The docs I read list no thread/queue method. DOCS
  • Could break on any harness update.

Rejected: relaying each turn's final message automatically. It needs no tool, but it forwards text written for you rather than for the other agent. agent-net deliberately avoided this for Codex for that reason CONSULT, and it would loop easily.

7. The delivery gate

The state of each agent comes from hook events, not from reading its screen. OpenRig's screen reading has broken on a harness update CONSULT, so this design avoids it. Both harnesses document the event names used here DOCS.

starting

Hold

  • SessionStart → idle, Claude Code only. For Codex it binds the session and changes no state, because it arrives at the start of a turn. TEST
  • No hook event for a set time → unknown, with a banner

idle

Deliver, unless you may be mid-draft in this pane. F4 overrides that.

  • UserPromptSubmit → busy

busy

Hold

  • Stop → idle
  • PermissionRequest → needs you
  • No event for a set time → unknown

needs you

Hold. Never paste into a prompt.

  • PostToolUse, or Stop → busy or idle

  • Later event with the bound session ID → matching state

  • PTY closed; no automatic restart

8. Interfaces

Agent tool

ratatoskr_send(to: string, body: string, reply_to?: string)
  → { id, status: "queued" }
  → error { reason: "unknown_recipient" | "unknown_reply_to" | "recipient_offline" |
                   "budget_exhausted" | "too_large" | "empty_body" | "storage_unavailable" }

to is a display name such as codex, which ratatoskr resolves to an opaque agent ID. The router uses only that ID, and the name must match exactly one agent. Every message gets a unique ID when it is accepted, which is what allows retries to be deduplicated once messages cross machines. The short IDs like m7 in this document are for illustration. A body that is empty after control characters are stripped and whitespace is trimmed returns empty_body.

The sender is worked out from the bearer token and is never a parameter. The MCP server's instructions and the tool description tell each agent who its peer is, and that its normal replies are not sent to the peer. That avoids adding per-harness prompt flags.

What the recipient sees

<ratatoskr-message from="claude" id="m7" reply-to="m6">
Please review internal/parser for error handling.
</ratatoskr-message>
This came from a peer agent, not the human. To reply, use the ratatoskr_send tool from the ratatoskr MCP server; other messaging tools don't reach your peers.

Delivery status

StatusMeaning
queued / heldDurably recorded and waiting. held also gives the reason.
deliveringAbout to be written to the PTY. Recorded first, so a crash leaves evidence.
pastedWritten to the PTY, not yet known to be received.
acceptedUserPromptSubmit fired after the paste. The harness took the input, though that doesn't prove the model acted on it.
unconfirmedNo confirmation within a time limit. Shown to you and not retried, to avoid sending it twice.
failedRecipient exited or the write failed. A failed write is never reported as delivered, a flaw found in agent-net's Claude adapter. CONSULT
interruptedThe run ended before the message finished. The reason shows whether it was ever written (section 9).

Launch sketch

claude --mcp-config <session-dir>/mcp.json --settings <session-dir>/settings.json \
       --allowedTools mcp__ratatoskr__ratatoskr_send

RATATOSKR_TOKEN=... codex \
  -c 'mcp_servers.ratatoskr.url="http://127.0.0.1:<port>/mcp"' \
  -c 'mcp_servers.ratatoskr.bearer_token_env_var="RATATOSKR_TOKEN"' \
  -c 'mcp_servers.ratatoskr.tools.ratatoskr_send.approval_mode="approve"' \
  -c '<hooks config, shape to be confirmed>'

The flags and config keys are documented HELP DOCS, but setting nested MCP and hook config with -c is unverified TEST. Hooks call back through the rtk hook subcommand, so this is Go too. The hook command is identical across runs, with an absolute rtk path and no per-run values, because Codex skips new or changed hooks until you review them DOCS. Whether its trust record keys on the command string is unverified TEST, and the bypass flag is not used. The command reads the server URL and token from a 0600 file in a fixed session directory, because it isn't verified that environment variables reach hooks. A hook event only counts if it comes from this run's harness session: ratatoskr compares the harness session ID in the hook's input with the ID bound to that agent. A missing or mismatching ID never applies its event. It is counted for the log and a banner, and an idle agent moves to unknown, because the agent's own ID may have changed and a stale idle could paste into a busy agent. A later event with the bound ID restores the matching state. ratatoskr never rebinds to a new ID, because an orphan could fire the event that triggered it. If /clear, /compact, resume or fork do change a harness's ID, which is not established TEST, that agent needs F4 delivery for the rest of the run. Claude's ID is chosen at launch with --session-id; Codex's is bound from its first SessionStart with source startup, and if Codex doesn't report that, it stays unknown TEST. This guards against a harness left over from a crash, which could read the new run's token and report a false "idle". The check can't rely on anything in the session directory. If a harness provides no usable session ID, its state stays unknown and you deliver with F4 TEST. Backend also found that Codex may skip hooks until they pass its trust review TEST. If so, that agent stays in unknown and you deliver with F4.

9. Persistent messages

Chosen by the user: messages and their delivery history live in SQLite and survive a restart. This records message transport, not work. It shows what ratatoskr accepted and did with each message. It doesn't show that a recipient read it or acted on it, and it has no task ownership, claims or handoffs. Agent sessions don't survive a restart either; only the record of their messages does.

What is stored

StoredNot stored
  • Each run of the program, and how it ended
  • Each agent launched in a run, with its harness, version and exit code
  • Each accepted message: sender, recipient, body, reply link, current state
  • Every state change, with time and reason
  • Tokens and other credentials
  • Pane contents and scrollback
  • Live agent state, gate state and the relay budget
  • Permission prompts and your answers
  • Refused sends: the sender gets the error straight away and nothing was accepted
 
runs            (id, started_at, ended_at, end_reason, app_version)
agents          (id, run_id, display_name, harness, harness_version,
                 started_at, exited_at, exit_code)
messages        (seq INTEGER PRIMARY KEY, id UNIQUE, run_id, from_agent_id, to_agent_id,
                 reply_to, body, state, created_at, updated_at)
message_events  (id INTEGER PRIMARY KEY, message_id, at, from_state, to_state, reason)

This is a sketch for backend to refine. messages.id is an opaque, globally unique ID assigned when the message is accepted, and it will be the dedup key across machines. seq sets delivery order, first in, first out per recipient. Agent IDs are new each run, because a new run means new harness sessions. A reply_to must name a message in the same run.

Figure 6. Message states. accepted, failed, unconfirmed and interrupted are final, with one exception: unconfirmed can become accepted if a late UserPromptSubmit contains this message's ID TEST. None of these states means the model read or acted on the message.

Only one message per recipient is in delivering or pasted at a time, so a confirmation can't be credited to the wrong message.

Commit order

MomentTransactionWhy
ratatoskr_send arrivesInsert the message and its first event, commit, then return queuedqueued means durably recorded. If the commit fails, the sender gets an error and the message doesn't exist.
Gate passesCommit delivering, then write to the PTYA crash can't hide a write. If this commit fails, nothing is written.
Write returnsCommit pasted or failedRecords only what the write call reported.
Hook or time limitCommit accepted or unconfirmedThe evidence decides the state.
  • Each transaction updates the message and appends its event together, and only if the message is still in the expected state.
  • No transaction stays open during a PTY write or while waiting on a hook.
  • One goroutine in the store package owns all writes. Uses WAL mode with synchronous=FULL; message volume is low, so the extra safety costs little.

After a restart

A lock file allows only one ratatoskr per machine, so recovery can't touch a live run's messages. The operating system releases the lock if the program crashes. Startup then does this in one transaction, before launching any harness:

State found in an old runBecomesWhat it means
queued, heldinterrupted, reason never_writtenDefinitely not delivered.
deliveringinterrupted, reason write_unknownAmbiguous: the crash came around the write, so it may or may not have arrived.
pastedinterrupted, reason pasted_unconfirmedWritten, but the harness never confirmed it.
  • Nothing is ever resent automatically, because the agent it was meant for no longer exists and a resend could duplicate work. This version has no resend action; you can read the body in the history and pass it on yourself.
  • Harnesses start as new sessions. This version doesn't resume old conversations or feed old messages into new ones. A new agent knows nothing about a previous run.
  • An unclosed run is marked crashed, and the message log shows how many of its messages were interrupted. A clean quit records the same transitions, after the existing warning.

Storage and retention

  • Location: $XDG_STATE_HOME/ratatoskr/ratatoskr.db, defaulting to ~/.local/state/ratatoskr/ on both macOS and Linux. Directory mode 0700, file mode 0600. It is never kept in the project or in the session directory, which is removed on exit.
  • Per machine: one database covering all projects run on that machine. It isn't synced. Over SSH on your server, it lives on the server.
  • Sensitive data: bodies are stored as plain text and may contain anything an agent wrote, including secrets. File permissions are the only protection, and backups of your home directory will include it.
  • Retention: runs that ended more than 30 days ago are deleted at startup with their agents, messages and events. Bodies are capped at 64 KiB, with larger sends refused. To erase everything, delete the file while ratatoskr isn't running.
  • Viewing: the F3 log reads from the database, showing the current run by default and older runs on request. Stored text is sanitised before it's displayed, so an old message can't send control sequences to your terminal.

Schema changes

The schema version is kept in PRAGMA user_version and migrations are embedded in the binary. An older database is backed up with VACUUM INTO, then upgraded in one transaction. A database newer than the binary is left untouched and the program refuses to start, with a clear message. There are no downgrades.

10. Invariants

  1. Never write a message to a pane unless the gate passes, or you press deliver yourself. The only other PTY writes are your own keystrokes and the emulator's replies to terminal queries, which carry no message content.
  2. Never answer a permission prompt. You answer them in the pane.
  3. Strip control characters from message bodies before pasting, including ESC. Otherwise a body containing the paste-end sequence could inject keystrokes into the other agent's terminal.
  4. The sender comes from the token, never from model input.
  5. Don't edit your harness config. Everything is passed at launch, or kept in a private session directory at a fixed path, <state dir>/session (mode 0700). It is emptied at startup, only after the single-instance lock is held, and removed on exit.
  6. Bind to 127.0.0.1 only, on a random port, with a separate token per agent.
  7. Report delivery honestly. No status claims more than the evidence shows.
  8. Commit before you claim or write. queued is only returned after a commit, and no PTY write happens before delivering is committed.
  9. Never resend automatically after a restart. Ambiguous messages stay ambiguous, and are shown that way.
  10. Limit automatic back-and-forth. A relay budget (default 20) resets when you press Enter in a pane, including to answer a permission prompt. Once it runs out, sends are refused until you step in, so agents can't loop unattended.

This is not a security boundary. Both agents run as you and could read each other's files or tokens. Tokens guard against other local processes and mistakes, not a determined agent. A message also can't approve anything for the recipient, but it can still persuade the recipient's model, so its normal permission prompts remain the real check.

12. Build order and acceptance

Suspended by the user, 2026-11-04. No spike or acceptance check below may run until the user says when and how (GR-3). They stay here as the planned checks. Implementation continues on the settled design, so the risks they were meant to test, embedded panes above all, are still open.

Spikes, when testing is allowed, in this order, on macOS and Ubuntu

  1. Panes. Run both harnesses in Bubble Tea with x/vt and do real work. Check colours, redraw speed, resizing, Unicode, and special keys including Shift+Enter, Esc and Ctrl+C. If it fails, the result goes back to the user, with tmux as the known alternative.
  2. Delivery. For each harness, try {idle, busy, at a permission prompt, mid-draft, just interrupted}, and record exactly what a paste does. The consult found no project had tested the prompt case.
  3. Launch config. Confirm MCP and hooks can be set at launch with no changes to your config, and that Codex's sandbox doesn't block its MCP connection.

Done means

  1. On macOS and on Ubuntu, including over SSH, one command opens one window with both harnesses logged in with your existing accounts. All the checks below pass on both.
  2. You can use each pane normally, as if it were running on its own terminal, and switch focus by keyboard.
  3. Ask Claude to ask Codex something: Codex receives it with no copying by you, and its reply reaches Claude.
  4. The same works when started from the Codex side.
  5. A message sent while the recipient is busy arrives after its turn, once, and in order.
  6. A message sent while the recipient is at a permission prompt doesn't touch the prompt, and is delivered after you answer.
  7. A body containing ESC sequences arrives as harmless text.
  8. Two agents told to keep messaging each other stop at the budget.
  9. After a restart, the log still shows the previous run's messages with their state history.
  10. Killing ratatoskr with kill -9 at each of these moments gives the matching interrupted reason on the next start, with nothing resent: while a message is held, just after delivering commits (using a test hook), and just after a paste.
  11. A second ratatoskr on the same machine refuses to start and doesn't change the first one's messages.
  12. A forced database write failure stops delivery, and no paste happens without a matching record.
  13. The database is created with the stated permissions, contains no tokens, and runs older than the retention period are removed at startup.
  14. ~/.claude and ~/.codex settings are unchanged after a run. Session history written by the harnesses is expected.

13. Decisions

1. Messaging path

Decided by the user, 2026-11-04: option A, MCP to send and gated paste to deliver.

2. Pane approach

Decided by the user, 2026-11-04, and reconfirmed after reviewing the tmux proposal: embedded in Bubble Tea. The spike still runs first. If it fails, that goes back to the user rather than switching to tmux automatically.

3. Permission prompts

Decided by the user, 2026-11-04: prompt the user to approve. Each harness keeps its own prompts, the TUI shows a "needs you" badge, and the user answers in the pane. Only ratatoskr_send is pre-approved.

4. Platform

Decided by the user, 2026-11-04: macOS and Linux (Ubuntu server); Windows deferred. This version runs on either machine, with both agents on that machine. Cross-machine messaging follows under decision 5.

5. When machines connect

Decided by the user, 2026-11-04: single machine first, then cross-machine messaging as the next step. The user's Mac and Ubuntu server can already reach each other over Tailscale, so a direct link is the likely starting point. That link gets its own design when the time comes.

6. Message persistence

Decided by the user, 2026-11-04: persistent messages first, using SQLite for messages and delivery history (section 9). A work queue with ownership stays out of scope for now. The location, retention period and recovery rules in section 9 are the architect's proposal, and the user can change them.

7. Command and implementation

Decided by the user, 2026-11-04: the command that launches the TUI is rtk, and implementation may begin, with a setup README. The product is still Ratatoskr. A failed spike that reopens one of these decisions goes back to the user.

8. Testing and pushing

Decided by the user, 2026-11-04: the team doesn't test or push until the user instructs it, and the user decides when and how (GR-3). This replaces the earlier spikes-first order. Everything in this design is untested until then.

9. Ctrl+C

Decided by the user, 2026-11-04: the first press interrupts the focused agent; a second press within about a second asks to quit rtk, warning first if messages are waiting or a draft is unsent; if no agent can receive the interrupt, one press asks to quit. Details are in section 4.

10. Tool name

Architect's change, 2026-11-04: the MCP tool is ratatoskr_send, not send_message. Codex 0.166.0 has a built-in send_message. In the user's run, Codex followed the frame's old wording to that tool, messaged itself, and said it had replied, so nothing reached Claude. In the next user run, Codex found the tool as mcp__ratatoskr__ratatoskr_send and its reply reached Claude. Later runs on macOS repeated this.

11. Codex's first message

Decided by the user, 2026-11-05: Codex launches with a short automatic prompt, passed as its launch argument, not typed into the pane. Codex fires SessionStart on its first turn, not at launch, and the router waits for a hook before delivering. Without a first turn, messages would hold until the user started one. The prompt starts that turn, says who the peer is and names ratatoskr_send. It costs one extra Codex model turn at every launch, even if no message is sent, and shows in the pane. Messages sent meanwhile wait until that turn ends. It doesn't bypass trust or permission prompts. Pasting into a starting agent is rejected, because Enter could answer a dialog. The user tested this on macOS and reports it works: in that run, a message from Claude reached Codex with no hold and Codex's reply came back. Other platforms and dialog cases are untested.

14. Growing to several machines

The planned next step after this version (decision 5), and not built in it. Cross-machine messaging adds a layer and leaves the agent-facing parts alone: sending is still a local MCP call, and delivery is still a gated paste on the recipient's machine. agent-net separates its local and between-machine links in a similar way. CONSULT

Mac: Claude calls ratatoskr_send→ Mac: ratatoskr⇒ Encrypted, authenticated link⇒ Ubuntu: ratatoskr, delivery gate→ Ubuntu: paste into Codex's PTY

Figure 7. Cross-machine path. Each machine runs its own ratatoskr, because only a local process can write to a local pane.

Build into the first version so the local contract can stay stable

These come from the consult, which notes that no analysed project demonstrates a clean upgrade from one machine to many. They reduce the risk rather than remove it.

  • Asynchronous sends and typed delivery statuses
  • Opaque agent addresses, with display names resolved to IDs
  • A unique ID on every message, so that retries can be deduplicated
  • A defined result for sending to an agent that is offline: recipient_offline. Whether messages should wait for an offline agent across machines is left to the link design.
  • A local database on each machine, which can later hold messages waiting to cross the link. The databases aren't synced, and the link design must add the states a message passes through in transit.

Known consequences

  • Prompts stay on the machine running the agent. Under decision 3, the user approves in that machine's window. Relaying prompts between machines would be a separate feature, and the link would then carry approvals.
  • Embedded panes tie agents to the TUI process. If an SSH connection drops, the TUI and both agents may die with it TEST. Stopgap: run ratatoskr inside tmux or screen on the server. Longer-term fix: split it into a background daemon and an attaching TUI.
  • The link needs its own design. The choices run from agent-net's gateway, TLS and enrolment to a private network such as Tailscale, or an SSH tunnel. agent-net has no node revocation, and OpenRig's lighter model gives weaker guarantees. CONSULT The user's machines are already on Tailscale, which makes a direct link over the tailnet the likely choice. Being on the tailnet must not be enough on its own: incoming messages get typed into agent panes, so each ratatoskr still has to authenticate the other.
