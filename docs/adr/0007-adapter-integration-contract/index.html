ARCHITECTURE DECISION RECORD 0007

One contract, any language: how outside harnesses and orchestrators join through adapters

A proposal for a generic, language-neutral Ratatoskr integration interface. An external harness or orchestrator (OpenRig, a Pi agent, a custom service) joins through an adapter that its own authors write in any language. The core speaks one stable, documented participant contract; the adapter translates between that contract and its harness, so no harness detail enters the gateway or the core. The user has chosen the wire direction: a separate, small HTTP+JSON participant API on the gateway (option W2, section 7). Reachability, TLS, authentication and enrolment, identifiers, the inbound delivery mechanism, the schemas and who may contact whom are still open. A2A is deferred and is not the assumed contract. This is a proposal only. No code was written, nothing was run, and the page has not been opened in a browser.

1. Short answer

The requirement. External harnesses and orchestrators must be able to join through adapters written in any language. A Go-only interface (an importable package, a Go plug-in) does not meet that, because most adapters would not be written in Go. USER

The shape. Define a participant contract: a short list of operations (connect, register sessions, send, receive, report delivery, discover, close) and exact meanings for each, written as a document with machine-readable schemas and a set of conformance fixtures (example exchanges any adapter can be checked against). The contract is meant to be independent of how bytes travel, and the user has chosen the binding: a separate HTTP+JSON participant API on the gateway, documented and supported for any language's HTTP client. A Go library may exist as a convenience, but the document is the contract, not the library. RECOMMENDATION

The pattern. The core and the gateway know participants, sessions and messages. They do not know Codex, OpenRig, Pi or any harness. Everything harness-specific (how to type into it, how to ask it a question, how it names its own agents) lives in the adapter. RECOMMENDATION

The chosen wire, and its edges. USER W2: a participant API on the gateway for external adapters. The daemon-to-gateway host protocol stays separate and unchanged; this API does not reuse or expose it. It is a documented, supported integration surface, not an internal one. Approved 2026-11-08: the seven decisions in section 13, including a long-poll inbox for inbound delivery and a single-use pairing code for enrolment.

What is still not decided. Whether delegated work is ever tracked, a rate limit, and whether an owner may later supply their own certificate instead of the pinned one (section 13). The exact routes, fields, limits and errors are in the implementation contract, which is an engineering document and has not been run.

2. What exists today

Read in the cross-machine contract CODE (its text describes protocol version 1; the code is a later version whose details this page did not re-read, UNVERIFIED):

  • A wire already exists, between our own daemons and the gateway. JSON over HTTP with a bearer credential and a protocol-version header, plus one long-lived newline-delimited JSON stream per host that carries offer, directory, ping and report. Runtimes always dial out; the gateway never dials in.
  • Identity is the host. The host comes from its credential, never from a request. Sessions are registered per run with new ids; a message address is name@host.
  • Honest delivery results exist (section 5): host_stored is success and means the host has the message, not that anyone read it.
  • It was built for one kind of client. An offer is turned by the host's daemon into a paste into a terminal, subject to that daemon's gates. There is no published schema, no policy for outside authors, and no way for something that is not an rtk host to take part.

So the pieces for honest results and for identity from a credential exist in the host protocol. What is missing is a contract an outsider can implement and a way to enrol one. The user chose not to open the host protocol for that (option W1) but to add a separate participant API beside it, so the host protocol is unchanged. USER

3a. MCP and hooks: who owns what

This section is a RECOMMENDATION about the architecture boundary. RECOMMENDATION It is not a decision by the user that every adapter must use MCP or hooks. The language-neutral network contract needs neither; each adapter may use whatever local mechanism its harness offers.

The rule, in short. For a Ratatoskr-managed Claude or Codex session, the daemon (core) owns the per-session MCP server and its configuration, and the hook configuration and receiver. For an external participant, the adapter owns its harness-facing integration, its deployment and its configuration. The gateway owns only the participant API, authentication, routing and the ledger, and never installs an MCP server or a hook into an external harness.

Every box and step in the table and diagrams carries one of three labels: OWNED BY RATATOSKR OWNED BY THE ADAPTER STILL UNDECIDED.

What exists for a managed session (read in the code, not run)

  • A loopback-only server in the daemon (internal/server/server.go) listens on 127.0.0.1 and gives each agent its own bearer token, kept only as a hash. It serves the agent's MCP server at /mcp and the hook receiver at POST /hook. CODE
  • Claude is launched with --mcp-config, --settings (the hooks) and --allowedTools (internal/agent/claude.go). Codex is launched with -c mcp_servers.ratatoskr.* (the server, its bearer token variable and the approval mode) and one -c hooks.<event> per hook event (internal/agent/codex.go). CODE
  • The hooks are five events (SessionStart, UserPromptSubmit, Stop, PermissionRequest, PostToolUse), each running rtk hook with the agent and event (internal/agent/hooks.go). They tell the router what state the harness is in. They do not carry messages. CODE
  • Incoming messages go through the daemon's router and delivery gate and are pasted into the pane by the terminal bridge, and only when the agent is idle with nothing in flight and no user draft (internal/router/gate.go). CODE
  • On main only ratatoskr_send is pre-approved in the launch settings. CODE Behaviour of any of this has never been run by the team. UNVERIFIED

4. Identity and addressing

Everything in this section is a recommendation for decision. Participant identifiers, session identifiers, the address form and enrolment are open user decisions (section 13); none is settled here, and nothing from the deferred A2A design is carried over as an answer.

  • A participant is an enrolled principal. It has a stable id and its own credential, scoped to it and revocable on its own. It is not a host and does not borrow a host's pairing key. RECOMMENDATION How it is enrolled is OPEN; the nearest existing pattern is host pairing, where the owner mints a single-use code at the gateway.
  • The participant comes from the credential, never from a request. The same rule as hosts today. An adapter can register and send only as sessions of its own participant. RECOMMENDATION
  • One participant, many sessions. A participant may hold several named sessions at once (an OpenRig adapter fronting one operator today and more seats later; a Pi adapter fronting three Pi agents). This mirrors a host with several agents. Each registration gets a new opaque session id, and a name has at most one open session, so a replacement session never inherits an older one's messages. CODE for hosts; RECOMMENDATION to apply it unchanged to participants.
  • Addresses. OPTION A participants share the name@host namespace: operator@openrig-main works with the existing send tool, but participant ids and host names must never collide, so enrolment must refuse a clash. OPTION B a distinct form such as ext:operator@openrig-main: no collision possible, but every tool and list must learn a second form. RECOMMENDATION A, with the collision check. OPEN
  • Names and ids. A friendly name is looked up when the message is sent; the exact session id is what the gateway routes on. An ambiguous name is refused, not guessed (the rule hosts already follow).
  • The origin is written by the gateway. The receiver sees name@participant (or name@host) as the gateway established it. A from field in a body is ignored.

  • The baseline contract is conversation only. It is what every current need (managed sessions, the operator, a Pi participant) is. RECOMMENDATION
  • Tracking is a separate, optional profile a participant opts into by declaring a capability, so a chat-only adapter never sees task semantics. Whether a profile is ever specified is OPEN and, if it is, it is a later record. This avoids the reason A2A was deferred: forcing every chat to become a task. RECOMMENDATION
  • A delegated-work profile could be modelled on A2A tasks or on something smaller. This page does not choose, and does not assume A2A.

7. Wire options

Chosen: W2, a separate, small HTTP+JSON participant API on the gateway for external adapters. USER 2026-11-08, relayed by the operator.

What that means. It is a documented, supported integration API that any language's HTTP and JSON client can call. The daemon-to-gateway host protocol is a different surface and stays separate and unchanged. This record remains a proposal for the API contract; it is not authorisation to build it.

Later decisions. Reachability, TLS, enrolment, identifiers, inbound delivery and who may contact whom were decided afterwards, on the same day, and are recorded in section 13.

8. Versioning and compatibility

  • A contract version MAJOR.MINOR, independent of the existing host protocol version and of any adapter's own version. The adapter states what it speaks on connect; the gateway answers with the one it will use, or an explicit incompatibility that names the range it supports. A mismatch is shown, never silently tolerated (the behaviour hosts already have). RECOMMENDATION
  • Within a major version changes only add. Unknown fields are ignored; unknown optional features are ignored; a feature the other side requires but lacks is refused at connect. RECOMMENDATION
  • Capabilities are feature flags, not version bumps (delivery reports, discovery, a task profile if one ever exists), so an adapter can stay on one version and still say what it does.
  • Conformance fixtures are versioned with the contract. An author can run their adapter's exchanges against the fixtures. Nothing about the fixtures exists yet. OPEN
  • Open: where the version travels in an HTTP request (a header, a path, or the connect call); how many major versions the gateway serves at once; the notice before one is dropped; where the specification lives and whether it is published for outside authors.

9. Security

  • Authenticate every request (the mechanism and enrolment are open). A participant credential, if that is chosen, would be random, stored only as a hash at the gateway, scoped to one participant and revocable without touching any other. It is never put in a document or a log, and an adapter keeps it out of argv. RECOMMENDATION
  • Identity from the credential, origin from the gateway. Neither an adapter nor a message body can name its own sender. CODE (hosts)
  • A narrow namespace. A participant registers sessions only under itself. The owner enrols exactly the participants intended (one for OpenRig's operator, not one per seat) unless they choose otherwise. RECOMMENDATION
  • Reachability and TLS are open user decisions. Hosts today use plain HTTP on loopback and a tailnet and TLS elsewhere, and being on a tailnet authorises nothing CODE; whether the participant API follows that, and who may reach it from where, is not decided. A publicly reachable address is not authorisation for an internet-wide listener. OPEN
  • Message text is untrusted input. A message from another machine can carry instructions meant for the receiving model. The receiving side labels the origin and does not let a message bypass a permission prompt or a gate. This is true of every message today and stays true for adapters.
  • Abuse limits (message size, rate, sessions per participant) are needed and not chosen. OPEN
  • Who may contact whom is an open user decision. An earlier answer was given under the deferred A2A design; it is not carried over here, and no default is assumed. OPEN

10. What an adapter author implements

11. Scenarios

Two illustrative scenarios, in the diagram below. Neither has been tried; both rest on what the user described. UNVERIFIED throughout.

  • An OpenRig operator adapter. It runs near OpenRig (any language), enrols as the participant openrig-main with one session, operator. A managed Codex on another machine sends to operator@openrig-main. The gateway offers it to the adapter, which saves it and answers participant_stored, then hands it to the exact current operator seat with a supported OpenRig delivery and may report participant_delivered. The operator answers through the adapter's outbound tool (its form is open, section 3a). OpenRig keeps its queues and lifecycle; nothing of it enters the gateway. ADR-0008 holds the boundary and limits.
  • A Pi-based participant. A Pi agent runs several agents. An adapter in whatever language suits Pi enrols as pi-lab and registers three sessions, planner, coder, critic, each with its own opaque id. Others address coder@pi-lab. If coder restarts, it registers again, gets a new id, and does not inherit old messages. Pi's actual interfaces were not examined; the adapter's inside is its author's concern. UNVERIFIED
