ARCHITECTURE DECISION RECORD 0005

Host Agent Cards, local editing, gateway polling and a Graph tab

Every host's daemon publishes one A2A-style Agent Card that describes the host as a whole. The owner writes or edits that card on the host itself, optionally starting from an LLM draft built from the Claude and Codex skills found there. The gateway polls the cards of the hosts paired with it and draws them as a graph in a new third tab, Graph, beside Terminals and Network. The code is written and has passed only gofmt, go vet and go build (darwin and linux). Nothing has been run, no migration has touched any database, and this page has not been opened in a browser. The mockups below are drawings with sample data, not screenshots.

1. Short answer

A host card describes the host, not a session. One card per daemon, covering the host's agent service as a whole: its name, which harnesses and skills its owner declares, how to reach it, and how it must be authenticated. USER wants the node to be the host. PROPOSAL for the card shape.

The owner edits the card on the host that owns it, and nowhere else. There is no remote write path. The gateway and every other host see the card read-only. USER

The gateway polls each paired host's card on a preset schedule, whether or not anyone is looking at a tab, from an address the owner controls. It stores the cards and the consolidated graph in its own SQLite database. USER This is the first time a Ratatoskr daemon would listen on a network, and the first time the gateway database gets a new migration for this purpose, so section 5 designs both honestly.

The card is public. The canonical well-known card is an unauthenticated, read-only endpoint, readable by anyone who can reach the address. USER So it carries no secrets (section 3).

Publishing a card is not an A2A implementation. The spec requires a set of operations (SendMessage, GetTask and others) that Ratatoskr does not have. The card therefore declares only the interface that exists. Section 3.

1a. What was built (2026-11-07, written, never run)

Source: the contract, where the exact names and rules live. The review was static only. The lead read the migrator, the card server, the poller, the dialer, the graph route and the tab code in full and relied on the owning seniors' review for the rest; I spot-read the migrator, its SQL and the dialer and found no defect.

PieceAs built
Card listenerOff by default. rtk daemon --card-listen ADDR turns it on at start (the address classes and --allow-lan/--insecure-http rules follow the gateway's). Serves GET and HEAD of /.well-known/agent-card.json and the agent.json alias, with ETag and 304. Turning it on later means rtk daemon stop, which ends every session.
CardStrict when published, tolerant when polled (unknown fields are ignored and counted). The interface is the card's own URL with binding RATATOSKR-CARD. No securitySchemes: the endpoint is unauthenticated, so there is no scheme to declare. Checked against the proto on 2026-11-07: every REQUIRED field is emitted and the JSON names match, and three gaps found by that check (the card description, each skill's description and each skill's tags are REQUIRED by the proto) are now required at publish in the code, still never run. The published revision on disk has no URL by design; the served card gets its own URL when it is served. protocolVersion means "the A2A version this interface exposes", and this interface exposes none, so "1" is our own card-interface version. Even then the host is not an A2A service, so the card never claims one.
EditingLocal socket operations and rtk daemon card show|validate|publish|history|rollback, plus the editor in the Graph tab. The CLI cannot declare skills; only the editor can. No remote write path. The same-user limit stands.
SkillsUser-scope directories only, read never executed. The scan runs by itself at daemon start, whether or not the listener is on, and runs the existing <harness> --version for a harness with something found. Nothing is published by it. Checked against the official docs on 2026-11-07: ~/.claude/skills is documented as Claude Code's personal (user) location. ~/.agents/skills is documented as Codex's user location (from the tail of the page, which was summarised, so lower confidence). $CODEX_HOME/skills and ~/.codex/skills are not documented as skill directories on any page read; the environment-variable page says CODEX_HOME is the root for "config, auth, logs, sessions, skills", which is an inference, not a statement. They stay as location_verified: false. Both harnesses follow symlinked skill folders; the scanner does not, and lists them as "symlink not followed", so the inventory can be shorter than what a harness loads.
DraftingNot implemented. The only thing built is a fixed status "not configured", a source label for a future model draft and an editor screen that says so. There is no provider, no payload builder, no confirmation step, no model call and no draft parser or diff. The first report called this "plumbing"; that overstated it. A concrete minimal design and the choice it needs from you are in section 7.
Gateway databaseA real versioned migrator and four additive tables (host_card_targets, host_cards, card_revisions, poll_attempts). Only rtk gateway --listen migrates an existing database, after a VACUUM INTO backup at mode 0600; admin commands refuse and say to start the gateway. The migration runs before the gateway binds, so a gateway that migrates and then fails to bind stays migrated, and an older binary then needs the backup.
Targets and pollerrtk gateway card-target set|show|clear. IP literals only (no DNS, so a Tailscale MagicDNS name does not work). http on loopback and Tailscale; a LAN target needs https with --fingerprint, or --insecure-http. A deny list refuses metadata and Tailscale service addresses; 100.100.100.200 is on it but unverified. Poll default 60 s (--card-poll-interval, 10 s to 1 h), jitter, no overlap, no redirects, no proxy, no credentials. Fresh within 2 intervals; offline after max(15 minutes, 4 intervals). Changing a target clears that host's stored card.
Graph routeGET /v1/graph (long poll, like /v1/network). Connection (stream and heartbeat) and card (poll) are separate objects with their own source and age. 768 KiB limit; over it, card bodies are dropped largest first and card_omitted and truncated say so. An older gateway answers 404 and the window says "gateway too old".
Edgesmessages_seen only, computed from the message ledger; there is no edges table. A count is sends the gateway decided (failed ones included), never "delivered"; host_stored is the subset that reached a host.
Graph tabA third touching block, 27 cells wide or T N G narrow, click first, F7 optional. A 3 by 4 grid needs 120 by 26; smaller, or more than 12 hosts, shows a list. A fifth mark ✗ rejected (ASCII X). rejected is wider than first worded: the newest poll was refused for an invalid card, an oversize body or a changed certificate, the last good card is kept, and the reason says which. The curves in this page's mockup are simplified.

Known limits

  • The public-content check is a block-list of shapes, not a guarantee. It has false positives (the word "bearer" alone blocks a publish) and no username check beyond home-path shapes.
  • Not built: an rtk daemon graph command, a cap on parked long polls, retention settings.
  • The migration, VACUUM INTO on a pre-created empty file, the poller, the listener, the graph route and every screen are unrun. The user chose to test first, so every check in the test guide is marked written, not verified.
  • Light themes, mouse on real terminals, narrow widths and the 256/16-colour mapping for the new tab are undrawn, as for the other tabs.

3. What the card is, and what it is not

It is a host's aggregate service card, not a session card

One card per daemon. The node in the graph is the host, so the card says what the host's Ratatoskr service offers. It does not describe one session, and a session does not get a card. USER node = host. Session detail stays in the Network tab.

Publishing a card is not implementing A2A

The spec's operations table lists, among others, SendMessage, SendStreamingMessage, GetTask, ListTasks, CancelTask and SubscribeToTask, and says all implementations must support them independent of binding. SPEC Section 3.1, 5.3. The spec does not define "complete implementation" as a phrase; the list above is its closest statement. Ratatoskr has none of these operations: it has its own gateway wire protocol (version 2) for messages. So:

  • No fake endpoint. The card lists only an interface that is really listening. It does not point at a SendMessage URL that does not exist.
  • An honest custom binding. protocolBinding is an "open form" string whose core values are JSONRPC, GRPC and HTTP+JSON. SPEC 4.4.6. As built: RATATOSKR-CARD with protocolVersion 1, and the interface's url is the card's own URL, the one thing that really exists. It means "discovery metadata only; no task operations". (The first draft showed RATATOSKR-GATEWAY and a /ratatoskr/v1 URL; that advertised an endpoint the daemon does not have and was dropped.) UNVERIFIED How third-party A2A clients treat an unknown binding; they may ignore the interface, which is the intent.
  • The card is public and read-only. USER It answers GET at the canonical path without authentication. Any party that can reach the address can read it, so it is written as a public document (below). SPEC 8.1 says a server MUST make an Agent Card available, which a public card satisfies; it still does not make the host an A2A server.
  • Capabilities say false. streaming, pushNotifications and extendedAgentCard are false, because none exists.
  • Future A2A service. A real A2A server (SendMessage and the rest, mapped onto the existing message ledger) is a separate ADR. It would add a JSONRPC or HTTP+JSON interface to the same card. This design leaves room for it and does not authorize it.
  • It does not replace the current transport. MCP, hooks, gates, pairing, TLS pinning and the gateway's message routes are untouched. USER / existing constraints.

A public card must contain no secrets

Because anyone with network reachability can read the card, the daemon builds it from an allow-list and refuses to publish anything else. PROPOSAL

  • Never in the card: tokens, keys, pairing credentials, poll or session secrets, full skill bodies, absolute file paths or usernames, environment values, session text, prompts, working directories, or the contents of any config file.
  • In the card, deliberately public: host name, a description the owner wrote, skill names and the short descriptions the owner chose to declare, harness names and versions, the interface URL. The owner sees this list in the editor and a "this card is public" notice before publishing.
  • A best-effort check at publish time looks for token-like strings, path-like strings and oversized skill text and blocks the publish with a readable reason. It is a safety net, not a guarantee; the allow-list is the real control.
  • Honest cost. A public card reveals which hosts run Ratatoskr, what they call themselves and which skills they declare, to anyone who can reach the port. That is reconnaissance value on a shared network. The listener is therefore off until the owner turns it on, and it should be bound to an address the owner picked.

4. What exists today

It can

  • Pair a host with the gateway and authenticate it with a credential. Every daemon dials the gateway; the gateway never dials a daemon. CODE ADR-0002 and the network contract.
  • Hold each host's network report in memory with a revision, long-polled by GET /v1/network, and drop it on unpair. Reports are not in the database; cards will be. CODE network contract (committed 2f65bf0).
  • Route messages between paired hosts through the gateway.

It can't

  • Listen on a network. A daemon serves a local Unix socket only. CODE the ADR-0004 section "what exists today".
  • Be reached by the gateway. Reachability today runs outward only; a host behind NAT works because it dials out.
  • Detect or list skills, or store a card. No such code exists.
  • Say which host messaged which, beyond routing each message. Whether the gateway keeps a per-pair count is UNVERIFIED.

Same-user limit, unchanged: agents run as the owner's OS user, so any of them can read credential files or call the daemon socket. This design does not claim to isolate them. CODE contract, "Honest limit".

5. Scheduled polling, liveness and storage

Polling reverses the direction of every connection in the system. Today hosts dial out. With polling, the gateway dials in, on a schedule. That is a new network listener on every polled daemon, with its own address, TLS and firewall story, and none of it exists today. USER chose a preset schedule because the gateway needs to check that a daemon is alive anyway.

QuestionAnswer
Who decides to poll?USER The gateway, on a preset schedule, for every paired host that has the card listener enabled. Not only while a Graph tab is open.
What interval?USER Superseded 2026-11-08: the user chose a default of 5 seconds. The flag range is 2 seconds to 1 hour, the request timeout is 4/5 of the interval, and a host is fresh within the larger of 2 intervals or 15 seconds (contract section 16). Earlier proposal: 60 seconds, 10 seconds to 1 hour.

Hammering is prevented by the interval floor and no-overlap rule, not by exponential backoff. OPEN Whether a long-dead host should drop to a slower schedule.

Which address is polled?PROPOSAL Only an address the owner entered on the gateway side for that paired host. Transport security?PROPOSAL HTTPS with an owner-controlled certificate fingerprint pinned for that host, as the recommendation. SPEC A2A says an interface URL must be absolute HTTPS in production (4.4.6) and production traffic must be encrypted (7.1). Because the card is public, the confidentiality of the body matters less than its integrity: without TLS a network attacker could alter the card on the way to the gateway. OPEN Whether plain HTTP is allowed on a trusted LAN. No tailnet HTTPS support exists today and none is claimed.
Cache and revalidation?USER Superseded 2026-11-08: none. The card is small, so every poll is a full GET and the daemon always answers 200 with the complete card, ignoring If-None-Match; the gateway validates and stores the latest card each time, makes no new revision for an unchanged one, and does not wake the graph. A 304 is now only an error from an unexpected daemon. Earlier proposal: conditional requests with If-None-Match and the card's ETag, a hash of the canonical card. SPEC 8.6: servers SHOULD send ETag, clients SHOULD use conditional requests.
Revocation?Unpair removes the host's card, revisions and edges from the database in the same transaction. A changed certificate stops polling for that host and is reported, never retried silently.

6. Who may edit, and the honest limit

  1. One owner per card. The card is a file on the host plus its revisions, written only by the daemon on that host, on request from a window on that host over the local socket. USER
  2. No remote write path. The gateway has no route to change a card; the polling listener serves GET only; a window attached remotely does not edit. Reading is the only thing that crosses the network.
  3. To edit a remote card, you go to that host the way you already would: SSH from the Network tab (ADR-0004), then its window. This design adds no other way in.
  4. Honest limit. The editing request travels over the same local socket every same-user process can reach, and the "not a descendant of an agent" check is best effort. CODE An agent running as the owner could edit the card. What the design does: every revision records who made it (window, or a socket client), the field and the time; the diff is shown before publish; the previous revision can be restored. It does not claim the card is tamper-proof against same-user agents.
  5. Trust of what you read. The gateway and other hosts treat a polled card as untrusted text. It is escaped for display, bounded, and its skills never become permissions or instructions to another agent.

Generating a draft with a model (designed, not built)

  • Explicit. A key press, then a confirmation screen naming the provider and model and showing the exact payload and its size (mockup 4, step 2). No default provider. No call on scan, on open, on a timer or in the background.
  • What is sent: host name, skill names and front-matter descriptions, harness names and versions, scope words. Not sent by default: skill bodies, paths, usernames, environment, credentials, session text, or the current card. Sending the current card (to "improve" it) is a separate tick.
  • What comes back is a suggestion. It is parsed, schema-checked, and shown as a diff. Endpoint, security and version fields in a draft are ignored because they are derived. A draft never overwrites a field the owner edited by hand unless they choose it in the diff.
  • Records. Each revision keeps its source per field: you, detection, or model draft (provider, model, time). The prompt and the reply are not kept unless the owner asks.
  • Failure. A model error, an invalid draft or no answer leaves the published card untouched, with a plain message. The last good card keeps being served.
  • Cost and consent. A call may cost money on the owner's account; the screen says so. OPEN Which provider is offered: the installed Claude Code or Codex in headless mode, or a configured API. Running either is a future decision and was not tried here.

8. What an edge means

Hosts as nodes do not determine edges. agent-net's graph has repository and service nodes with charters, and edges the owner sets: depends, governs (with advisor, arbiter or owner mode) and deploys. CODE agent-net docs/decisions/0022-component-graph-and-cto.md and internal/protocol/graph.go. Those edges say how work and authority flow between projects, and an owner edits them through a CTO agent. The requested graph is different: nodes are machines. Copying agent-net's edge kinds onto hosts would be wrong, since a host has no "depends" relationship to another host.

Proposal for the first edges. PROPOSAL Two layers, both with a visible legend, and nothing inferred:

  1. Messages seen. A directed line from host A to host B means: in the last 24 hours the gateway routed at least one message from an agent on A to an agent on B. Width or label shows the count; faint means none in the last hour. Source: the gateway's routing. UNVERIFIED The gateway may not keep per-pair counts today; if not, a small in-memory counter is new work.
  2. Gateway polling. A spoke from the gateway's host to each paired host, coloured by the last poll result. It means "the gateway can or cannot read that card". It is not a relationship between two hosts.

Not drawn: edges inferred from skill overlap, naming, charters or card text. Not claimed: that a line means trust, permission or that anything is up. Each layer can be switched off. Filters: freshness (all, fresh only, hide stale and offline). Every node and line states its source and age in its detail. No idle inference: the only state a node shows is the card's freshness. 11. Gaps, limits and compatibility

  • New network surface and public data. A listener per host and a card readable by anyone who can reach it are the biggest changes. The card is built from an allow-list so it holds no secrets, but it does disclose that Ratatoskr runs there and what the owner declared.
  • Not a complete A2A implementation, on purpose. The card is public and read-only, so card discovery works, but the host offers none of A2A's required operations and uses a custom binding. A generic A2A client can find and read the card and can do nothing else.
  • Spec validation. The normative proto was read for the AgentCard messages (section 1a). Not read: the OAuth flow messages, section 13 and 12.8 of the page in full, and earlier versions. The 14.3 registration is only a page summary. The tag was not resolved to a commit hash. Card JSON in the mockups is illustrative sample data.
  • Gateway data. Whether per-pair message counts exist is unverified. Table names, the migration number and retention numbers are proposals.
  • Address entry. How the owner records each host's card address and optional certificate fingerprint on the gateway side is not designed here. It is not a pairing secret exchange any more, since nothing secret is needed to poll.
  • Wire and schema. Wire protocol 2 is unchanged. The gateway database needs a new migration (section 5); this replaces the earlier no-migration position. A graph read route is additive. Older gateway builds cannot open a migrated database.
  • Unchanged. MCP, hooks, gates, pairing, the existing heartbeat and stream (still the authority on connection), the 15 s liveness window, SSH entry (ADR-0004), local-only editing with no remote write, no worker dispatch, no Herdr dependency, no HTTPS-over-tailnet claim, no offline replay.
  • Not verified. Terminal rendering of the graph, mouse on real terminals, clipboard, narrow widths, any harness's skill loading, any model call, any poll.
