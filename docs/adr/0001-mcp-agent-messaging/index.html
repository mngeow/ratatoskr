1. The decision

An agent sends a message by calling one MCP tool, ratatoskr_send, on a local server inside rtk. rtk records the message in SQLite, waits until hooks report that the recipient is idle, and then types the message into the recipient's terminal as a bracketed paste followed by Enter. Replies use the same path in the other direction.

MCP solves the outbound half only. Everything that gets a message into a model that isn't doing anything is Ratatoskr's own code, and it's different for each harness.

What MCP does here

  • Gives both models one callable tool with one contract: to, body, optional reply_to.
  • Lets each harness connect at launch, using its own config shape.
  • Returns a result to the model that made the call.
  • Carries a per-agent bearer token, so the sender is never an argument the model chooses.

What MCP doesn't do here

  • Start a turn in an idle model. Our server only answers calls. It runs Stateless with JSONResponse, so it holds no open channel to a harness at all.
  • Say when a harness is safe to interrupt. Hooks do that.
  • Draw anything in a terminal, or write to one.
  • Guarantee a model processes a message, or replies.

This describes this implementation and the two harnesses as read. It isn't a general claim about what MCP can do.

2. Context

The user wants Claude Code and Codex running side by side in one Bubble Tea window, able to talk to each other without a person relaying. Both are full interactive TUIs that stay visible and usable, each in its own pane, so a headless mode doesn't meet the goal.

Each direction has two separate problems: how a message gets out of the sender, and how it gets into the receiver. Getting out is easy, because both harnesses can call tools. Getting in is the hard part: as read in their docs on 2026-11-04, neither harness has one documented, stable way to accept input from outside while its TUI is running. DOCS

Three constraints shaped the choice. A message must never look like an answer to a permission prompt. It mustn't land on top of something the user is typing. And it must wake an agent that's idle, because "ask and wait" leaves both agents idle most of the time.

Claude Code (one harness adapter)

Launched with its own new session ID, an MCP config file and a settings file holding the hooks. The bearer token sits in the MCP config file (mode 0600) because the docs don't state whether ${VAR} expands there. Its environment carries no token.

Because rtk picks the session ID, the router binds this agent at registration. Claude's SessionStart means it's ready, so it moves the agent to idle.

Codex (the other harness adapter)

Launched with nested -c config options for the MCP server, the tool's approval mode and each hook, then a startup prompt as the trailing argument. It reads the bearer token from RATATOSKR_TOKEN in its environment, because it has no per-server header option. The prompt is visible in the process list, so it never carries a secret.

No session-ID flag was found in its help output, so the router binds from the first SessionStart with source startup. On Codex that event marks a turn beginning, so it binds but doesn't mean idle. Codex first becomes idle on Stop.

HTTP server: the MCP tool and the hook endpoint

Listens on 127.0.0.1 on a port the OS picks, and refuses to start on anything that isn't loopback. Every request passes three checks in order: Host must equal the exact address, which stops DNS rebinding; any Origin header is refused; and the bearer token must match. Without a valid token, even an unknown path gets 401.

Each agent gets 32 random bytes as a token, stored only as a SHA-256 key, and its own MCP server instance. The transport is the Go SDK's Streamable HTTP handler, set to Stateless and JSONResponse, so each request stands alone. The sender comes from the request's token and is never a tool argument. If the context's agent isn't this server's agent, the tool refuses.

The tool answers {id, status: "queued"}. status is always queued: the message is committed, not delivered.

Hooks: how rtk knows an agent's state

Both harnesses are given the same five events: SessionStart, UserPromptSubmit, Stop, PermissionRequest and PostToolUse. Each runs rtk hook --agent NAME --event EVENT --session-dir DIR. That command reads the harness's JSON from stdin, reads the token from a 0600 file (not its command line), and posts to /hook with a 2-second limit.

Hooks only observe. The command always exits 0, writes nothing to stdout and swallows panics, and the server always answers 204. So it can't approve, block or answer anything in a harness. The command is the same on every run, because Codex asks again for a hook whose definition changed.

The router uses three payload fields: session_id, prompt and source. Before binding, only a SessionStart with source startup counts. After binding, an event from another session is ignored, shown in a banner, and can only move an idle agent to unknown: a stray session can push an agent toward holding, never toward delivery.

Router actor: queues, state and the gate

One goroutine owns all queues and agent state, so events apply strictly in order. Send checks a message in a fixed order: storage up, sender known, recipient known and not itself, recipient not exited, body not empty after sanitising, body under 64 KiB, reply_to exists in this run, relay budget not used up. A refusal returns its reason to the model as a word such as unknown_recipient.

The relay budget is 20 messages, and it resets when the user submits in a pane, which stops two agents talking forever unattended. Only the head of a recipient's queue is considered, so a held head holds everything behind it. One message per recipient can be in flight at a time.

All these limits are guesses marked in the code as untested.

SQLite store: what was sent and what happened to it

One writer goroutine, WAL mode, synchronous(FULL). A new message and its first event are inserted in one transaction, and the model gets queued only after that commits. Every state change updates the message and appends a message_events row in one transaction, and memory follows only if it committed.

Any write failure other than "this message changed state" marks the store unavailable for good, which stops delivery. Stopping is the safe side when a record may be missing. Bodies are stored raw and sanitised on the way out. Runs that ended over 30 days ago are deleted at startup.

This is a record, not a work queue: nothing has an owner, a claim or a retry. See section 8.

Pane writer: the only way into a harness

Before writing, the router builds a frame. stripControl removes C0 and C1 controls including ESC and BEL, turns CR into a newline and replaces invalid UTF-8. Any frame tag in the body has its < escaped, so a body can't close the frame or open another. Attributes are escaped and folded onto one line.

PasteSubmit then refuses any text still containing ESC, waits for any earlier user input to finish, holds the write lock for the whole sequence, and writes the bracketed paste, a 50 ms pause and a separate \r. Enter is never written after the context ends, and the router gives the whole write 10 seconds. A failed write reports whether any bytes landed.

The frame a recipient sees 
<ratatoskr-message from="NAME" id="ID" reply-to="REPLY">
BODY
</ratatoskr-message>
This came from a peer agent, not the human. To reply, use the ratatoskr_send tool from the ratatoskr MCP server; other messaging tools don't reach your peers.

It arrives as ordinary typed input, so to the harness it's a user turn. The last line is how the model knows otherwise. reply-to is left out when empty.

TUI: the human's part in delivery

rtk can't see a harness's input box, so it infers a draft: any key except a plain Enter, and any click passed to the harness, tells the router the user is drafting, before those bytes are sent. A draft holds delivery until the UI clears it.

F4 is an explicit deliver-anyway for the focused agent. The router still decides, and only allows it for an unknown agent or an idle one with a draft. It's never allowed at a permission prompt or while the agent is busy. F3 opens the message log, which is how you read a message that was never delivered.

    The harness may already hold some or all of the text, and it can't be taken back. A retry could submit it twice, or submit a fragment. 5. Why the tool isn't called send_message

The tool was first named send_message. Codex 0.166.0 has a built-in tool with that name, in its collaboration namespace. MCP didn't reject anything and no error appeared: the model simply had two plausible tools and picked the wrong one. RUN

After: runs 01a1a918, 01a1a91c, 01a1a932

Seen on macOS only. The doubled name in the tool's full ID is intended.

The name is one of four places that steer the model: the tool description, the server's MCP instructions, the frame's last line and Codex's startup prompt. Each one says built-in messaging tools don't reach peers. That's guidance, not enforcement. 6. What this changes about permissions and trust

One narrow change, and everything else is left as you configured it. The change is the user's decision: this one tool is pre-approved at launch, because a prompt on every send would stop the agents talking. In Claude that's --allowedTools naming only this tool. In Codex it's the per-tool approval_mode.

  • No sandbox or approval flags are added or loosened, and no --dangerously-* option is used. CODE
  • Codex's hook review stays with you. rtk doesn't use the bypass flag, and it holds messages until the hooks run.
  • Nothing answers a prompt for you. Hooks can't, the gate holds at needs_you, and F4 refuses there.
  • Config goes in at launch. rtk is built not to write to ~/.claude or ~/.codex. That's by construction: the acceptance check that would confirm it hasn't run. UNVERIFIED
  • This isn't a security boundary. Both agents run as you and could read each other's files and tokens. A message can't approve anything, but it can still persuade a model, so each harness's own prompts remain the real check.

7. Alternatives

Delivery needs the same care in most of these, so the real differences are how a message gets out and how the receiver is woken. DOCS claims date from 2026-11-04. Effort ratings are the architect's judgment, not measurements. None of these was built or run for comparison.

A. MCP, then gated paste (chosen)

Tool call over MCPCommit and queueWait for idle, from hooksPaste + Enter into the PTY

Why it won. It's one code path both ways. Identity comes from a token issued at launch. Each tool can be pre-approved on its own. It wakes an idle agent. And you can watch each message arrive.

What it costs. Delivery is typed input, so it reads as a user turn. A bad gate could disturb a prompt. It depends on hooks being accurate. And it needs an MCP dependency.

B. Shell CLI plus terminal delivery, like rig send

Model runs a shell commandCommit and queueWait for idlePaste + Enter

What it offers. The least code, no MCP dependency, and you can run it by hand when debugging. It's a proven shape in general: the OpenRig team that built this product talks through a command that types into terminals. That shows the shape works for that team, not how it would compare here.

Why not. Codex's workspace-write sandbox might stop the command reaching rtk; the docs say nothing specific about localhost or Unix sockets DOCS. Multi-line text is fragile through shell quoting. Identity would come from a variable the agent can read or override. And pre-approving a shell command is a wider grant than pre-approving one named tool ARCHITECT.

Still the fallback. If MCP had proved awkward at launch, B would need only a new way out, since delivery stays the same. It wasn't needed: both harnesses' MCP connections worked in the user's runs.

Why not. As read: Claude's channels were a research preview, custom ones needed --dangerously-load-development-channels, and the Codex CLI marked its app server experimental DOCS. It means two delivery paths to build and test. And whether a turn started by another client shows up in the attached TUI wasn't known UNVERIFIED.

Worth revisiting. If these interfaces stabilise, they could replace the paste for that harness while the MCP half stays put.

D. Polling or inbox tools

Tool or file writeMailboxWaits until the recipient checks, or its Stop hook injects it

What it offers. No terminal typing, and an MCP inbox tool would be easy to add. Both harnesses can continue a turn from a Stop hook, which is a clean moment DOCS.

Why not. It can't wake an idle agent. A model that isn't running can't poll. If both are idle, which is the normal state for "ask and wait", the conversation just stops. Asking models to poll spends turns and relies on them remembering.

E. Private interfaces

What it offers. Another project, agent-net, uses these and reports messages queuing behind a running turn on Linux. codex queue is a shipped command.

Why not. The Claude socket's support status wasn't established and it's untested on macOS. The docs read list no thread/queue method. Any harness update could break it.

Also rejected: relaying each turn's final message automatically. It needs no tool, but it forwards text written for the human rather than for the other agent, and it would loop easily.

Why MCP fits mixed harnesses, and what it leaves to adapters

MCP gave one tool contract across two harnesses from different vendors, which is why it fits. But most of what makes delivery work isn't covered by it. Adding another harness would mean answering every row on the right for that harness. MCP support alone doesn't make it work, and no harness beyond these two has been examined for this record.

8. Consequences and limits

Four things that are easy to confuse

  1. queuedA durable row exists. It's what the sender is told, and all it's told. CODE
  2. pastedThe bytes reached the PTY, and Enter was written. The harness might still have ignored them.
  3. acceptedThe harness fired UserPromptSubmit, with an empty prompt or one containing the ID. UNVERIFIED whether each harness supplies the prompt text. If it doesn't, an empty prompt credits whatever message was pasted, including a submit that was really the user's.
  4. The model read itNo signal exists for this.
  5. The model acted on itNo signal exists either. Your evidence is a later tool call or the pane. All 10 stored messages reached accepted, and in run 01a1a744 Claude still got no reply.

Persistence isn't a work queue

SQLite here records what was sent and what happened to it, so nothing vanishes silently and a crash leaves an honest trail. It doesn't own work. There's no assignee, claim, deadline, retry or "done" signal from the recipient, and accepted doesn't mean the work happened. A message gets at most one delivery attempt in the run it was sent, and no run picks up another's messages. An owned work queue was left out on purpose (design decision 6).

What we get

  • One code path in both directions, with the harness-specific parts confined to launch specs and a small hook rule.
  • A sender that can't be forged by a tool argument, and can't block on the recipient.
  • A safe default: every doubtful case holds, and any new state holds until someone adds a branch.
  • Messages you can watch arrive, and a log that keeps them.

What it costs, and present limits

  • Peer messages look like user turns. Only the frame says otherwise, and that's text a model can weigh, not a guarantee.
  • It rests on hooks. A hook that's missing, untrusted or mistaken means messages hold until F4. Whether Stop fires after an interrupt is UNVERIFIED.
  • The sender is never told the outcome. It only gets queued. Failed and held messages show up for the human only.
  • One Codex turn per launch, even if nobody sends anything. The cost hasn't been measured.
  • Fixed limits, all guesses: 20 relays between user submits, 64 KiB per body, 60 s startup, 5 min busy, 20 s confirm, 10 s write.
  • Two agents, one of each, on one machine. Cross-machine messaging is the planned next step and isn't built. Any session ends with rtk.
  • Bodies are plain text on disk. File permissions are their only protection.
  • Pane and paste risks are still open: the young terminal emulator, partial pastes and paste mode. The current list is in outstanding issues.
