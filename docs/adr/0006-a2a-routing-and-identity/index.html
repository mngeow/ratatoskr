ARCHITECTURE DECISION RECORD 0006

A2A for Ratatoskr: where a message goes, who is really asking, and who may take part

Reduced first delivery, 2026-11-08. The user accepted a smaller first phase: standard A2A message exchange with a clarification and a result, on one proven round trip, with the foundations (exact destination, authentication, session replacement) kept. Section 1a is the scope and the technical compliance qualification. Goal, clarified 2026-11-08: Ratatoskr is a modular network that external orchestrators and services (OpenRig, an independent Pi, a custom service) can join, not only terminals Ratatoskr launches. A participant is an authenticated, addressable agent or service; a managed session is one kind. Section 5a covers that. OpenRig operator integration and the discovery tool are separate records: ADR-0007 and ADR-0008.

A proposal, with animated diagrams, for replacing the custom message contract with the standard A2A protocol served by the gateway. The hard part is not the message format. It is two questions the current system answers by convention and A2A answers not at all: which exact session is this for, and who is the sender, provably. This is a proposal only. No code was written, nothing was run, and the page has not been opened in a browser. It is separate from ADR-0005, which publishes host cards and is not an A2A implementation.

1. Short answer

One example runs through the whole page. Claude on the Mac asks Codex on Ubuntu to review a retry loop. Codex needs one clarification. Claude answers. Codex returns the review. That is today a message, a reply message, and a human reading two terminals. With A2A it is one task with a question, an answer and a result.

Three things answer three different questions, and they must never be mixed up. The endpoint says where the message is going. The credential says who is asking. The gateway's policy says whether that asker may use that route. The public card only describes an endpoint; it authorizes nothing. And A2A's ROLE_USER or ROLE_AGENT says which side of one exchange wrote a message, not who anyone is.

Recommendation for destination. The gateway serves one A2A endpoint per exact session, such as https://gateway/a2a/agents/SESSION_ID (illustrative), using the standard JSON-RPC binding. A friendly name like codex@ubuntu is looked up once, at send time. A conversation never moves to a replacement session. PROPOSAL

Recommendation for identity. Start with host-delegated identity validated by the gateway: the daemon names the acting session, the gateway checks it is the current session of the authenticated host, and the gateway, not the sender, writes the origin that the target sees. Outside clients get their own gateway-issued credentials. Add gateway-issued, memory-only session credentials later if you want a stolen pairing file to stop being enough to impersonate sessions. PROPOSAL

What this costs. Phase 1 is the smaller part of: an A2A server in the gateway, a task store and migrations, agent-facing tools for questions and results, an asynchronous wake path, a credential system, and adapters. Section 1a says exactly what is in it. Section 9 sizes the whole design. Nothing here must be built now.

1a. Reduced first delivery (user-accepted 2026-11-08)

The operator recommended shrinking the first A2A phase, and the user accepted that for this ADR (USER accepted; the exact list below is my wording of it, PROPOSAL). No build is authorised.

The one acceptance story. Claude on the Mac asks Codex on Ubuntu to review a retry loop, through the gateway. Codex asks one clarification (INPUT_REQUIRED). Claude answers, correlated to that task. Codex returns the result explicitly. Either side can read the status and result by polling. That round trip is the first delivery. Diagrams 2 to 5 show it; diagram 6 is a later phase.

Phase 1: what is in

The six product choices the user made on 2026-11-08 are recorded in section 1b and replace the earlier open rows on outsider policy, cancellation, retention and transport.

  • Standard A2A message exchange in the standard JSON-RPC binding, from the A2A v1.0.0 proto: a direct reply where no task is needed, and a tracked task where one is.
  • Task, context and session kept distinct. The task id is the unit of work, the context id groups related tasks, and neither is a Ratatoskr session id.
  • Participants, not only managed sessions. A destination is a participant: a managed Ratatoskr session, or an externally managed service that enrols, registers and speaks A2A (section 5a). Phase 1 specifies that contract and one reference adapter; it builds no marketplace, no NAT tunnel, no federation and no SDK suite.
  • Exact destination binding. One endpoint per exact session, and a session replacement is rejected, never followed (section 5). A configured list of destinations with plain name-to-endpoint resolution is enough; there is no discovery.
  • Essential authentication and ownership. The gateway authenticates the caller, writes the origin the target sees, and checks that a caller may only read tasks it owns or is party to (section 6). These are foundations, not deferred.
  • Clarification and answer. INPUT_REQUIRED, then a correlated answer on the same task.
  • Explicit completion and results. COMPLETED, FAILED and REJECTED only from an explicit report or a system event. A turn ending is never completion.
  • Task retrieval by polling: GetTask, and ListTasks scoped to the caller.
  • Kept as they are: the harness MCP, hooks, PTY and readiness adapters and the internal delivery receipts stay separate from A2A task state. Fail immediately when the target is offline, no replay, and an uncertain dispatch is reported as uncertain.

The qualification in one sentence. A server that claims A2A must implement four operations fully and refuse the other seven by the standard's own errors; it may not claim streaming, push or an extended card it does not have, and it must not invent a private subset while saying it is interoperable. If the user prefers not to carry those obligations, the honest alternative is to call the first delivery "A2A-shaped" and not claim interoperability, which is a different decision from this one.

What decision 2 means in plain terms. An enrolled external participant can send a message to any session on the network, including the owner's Claude and Codex sessions. Each of those is a language model that can be persuaded by text, so enrolling a service is as much of a trust decision as pairing a machine. The control is the owner's: enrol only services you trust, and revoke the credential to end its access at once. Permission to contact sessions is not permission to do anything else. It does not allow an external participant to read tasks that are not its own, control a terminal, approve a permission prompt, spawn a worker, or edit a card. Task ownership, read, list and cancel remain scoped to the caller and the parties to a task.

  • An A2A role is not an identity. SPEC The proto: ROLE_USER means "the message is from the client to the server" and ROLE_AGENT "from the server to the client". It marks direction inside one exchange. The spec says "Identity information is handled at the protocol layer, not within A2A semantics" (section 7).
  • A public card does not authorize calls. The card is information that anyone may fetch. The spec expects the server to "authenticate every incoming request" (7.4) and to authorize on "the authenticated identity and its own policies" (7.5).
  • Message, task and context ids are not session ids. SPEC messageId "is created by the message creator"; Task.id is "generated by the server"; contextId is "the contextual collection of interactions (tasks and messages)". A session id names a running terminal session. Three different things, kept in three different columns of any table that records them.

5. Destination: which session is this for

This section describes managed sessions. Section 5a generalises it to participants; the exact-session rules below are the session-bound case of it.

A2A's model is one agent per endpoint URL. A card describes an agent and lists its interface URL(s). SPEC The proto's AgentInterface has a required url, protocol_binding and protocol_version, and an optional tenant described only as the "Tenant ID to be used in the request when calling the agent". A standard client sends to the URL it is given, with no knowledge of Ratatoskr.

The proposal: one endpoint per exact session

  • The gateway serves the endpoints. https://gateway/a2a/agents/SESSION_ID is illustrative. The session id is the gateway's session id (a UUID, new for every registration), so the URL names exactly one running session and no other. CODE internal/protocol/wire.go:61 PROPOSAL
  • Standard binding, standard fields. The card says binding JSONRPC, protocol version 1.0, and that URL. A generic client needs no custom required field, no tenant and no proprietary routing header. SPEC JSONRPC is one of the three core binding values.
  • The friendly name is a lookup, once. codex@ubuntu resolves through the gateway's existing directory to the current session id when the send happens. The model never sees a URL.
  • Existing work never moves. A task and its context are bound to the session they started in. If that session ends, they end (diagram 5). A new send to the same friendly name starts new work in the new session, visibly.
  • Gateway-centred by your choice, not by A2A. The spec does not require a gateway. USER chose a central gateway for Ratatoskr; every endpoint here lives on it.
  • Do not misuse tenant. It is a path or field the server may or may not interpret. Using it to select a session would work only for clients that know to fill it in, which is the proprietary routing this design avoids.

One host, many sessions

A host is not a session. One host can run many sessions, of the same harness or different ones, and each is its own destination. The design above already routes by session, so this is a clarification, not a new mechanism. Example (invented ids): Host mac has three sessions.

Where the per-session card lives

The spec's well-known location is the domain root, https://{server_domain}/.well-known/agent-card.json (8.2); it also lists registries and catalogs and "direct configuration" as ways to find a card. SPEC It does not define a path-scoped well-known location. This design serves each session's card at .../a2a/agents/SESSION_ID/.well-known/agent-card.json (a choice, not a spec rule) and hands the URL to clients by direct configuration or through Ratatoskr's own directory. UNVERIFIED Whether third-party clients accept a card at such a path; they would if given its URL. A listing endpoint for humans is a Ratatoskr feature, not an A2A one.

5a. Participants: managed sessions and externally managed services

Section 5 assumed every destination is a terminal session Ratatoskr launched. The goal is wider: OpenRig, an independent Pi, or a custom service should be able to join. A participant is an authenticated, addressable agent or service. A managed session is one implementation of it; an externally managed service is another. USER direction, clarified 2026-11-08; the mechanics are PROPOSAL.

Four ids that must never be mixed up: the participant id (who, stable per its lifecycle binding), the connection id (one live link, changes on every reconnect and must not rotate the participant), the session id (a managed session only), and the task id (one unit of work). Two roles that look alike

  • An external service as destination: something other participants send work to. It is registered at an endpoint and gets tasks.
  • A standard A2A client as ingress: something that calls in to ask for work, with its own credential, and is never a destination. Diagram 6 shows this role. Both use the same enrolment but have different policies.

Registration rules for A (owner-controlled). Only the owner, with an admin credential, registers an endpoint. The gateway then makes outbound requests to a URL it was given, which is the same class of risk as ADR-0005's card poller, so the same rules apply: an IP address, not a name; a dial-time check of the address against a deny list; no redirects followed; no proxy; size and time caps. CODE internal/gateway/carddial.go:6 TLS is never silently bypassed. The standard says production interface URLs must use HTTPS; today ADR-0005's polling accepts plain HTTP on loopback and Tailscale addresses and HTTPS with a pinned certificate on a LAN, and a task carries content and a bearer credential, so the registration states plainly which it allows. USER Decided (section 1b): LAN and tailnet destinations only, at URLs the owner configures. Plain HTTP is accepted inside Tailscale (as the gateway already does, with the link encrypted by Tailscale), and on a LAN either HTTPS with a pinned certificate or an explicit plain-HTTP opt-in. No tailnet HTTPS is built. Public-internet destinations and a NAT connector are not enabled. The gateway itself has no public mode and no HTTPS on a tailnet address, so a service that must call the gateway back is limited to the networks the gateway already listens on.

Enrolment and credentials

  • Scoped and independently revocable. The owner enrols a participant and gets a credential naming that participant only: what it may send to, and what it may read. Revoking it affects nothing else. The host pairing key is not reused as a universal owner credential. The credential is shown once and stored as a hash, like the pairing secrets.
  • Source attribution. The gateway knows the participant from its credential and writes the origin; the message body's from is never trusted. A registered external service answering a task is authenticated the same way when it reports back.
  • Standard or Ratatoskr-specific. A2A defines how a server declares authentication schemes (the card's security fields) and requires servers to reject bad credentials; I did not find in what I read a standard for enrolling a participant or issuing its credential. So enrolment and registration are Ratatoskr-specific admin operations; the authentication on A2A calls stays standard. UNVERIFIED beyond the sections read.

6. Identity: who is really asking

Host delegation (option H below) is a trust boundary for managed sessions on a paired host. It is not a universal proof of identity and does not apply to external participants, which have their own credentials (section 5a).

What the target can actually rely on

The target daemon cannot check the requester itself. It can check that the frame came over its own authenticated link to the gateway. So the chain is: the gateway authenticates and authorizes the requester; the gateway writes an origin record (requester kind, host, session, task id, policy decision) into the internal frame; the target trusts the origin because of who sent the frame, not because of anything in the message body. body.from proves nothing. Trust limits, stated plainly

  • The gateway is the root of trust. If it is compromised, every origin, ownership and policy decision can be forged. Signed assertions would not fix this: they only prove the gateway signed, and the gateway holds the key.
  • The same-user limit stays. Agents run as the owner and can read files and, depending on the OS, process memory. Neither H nor S isolates them from a compromised host.
  • Authentication is not worker permission. It says who may ask. What Codex then does is governed by its own permission prompts, hooks and gates, unchanged.
  • The existing HTTP risks remain. The gateway may run plain HTTP on loopback, a Tailscale address, or a LAN with an explicit flag, and refuses a public address. CODE internal/gateway/listen.go:3 A bearer token over plain LAN HTTP is readable on that LAN. A2A says production use "MUST" be encrypted (7.1) and an interface URL "must be a valid absolute HTTPS URL in production". SPEC Outside clients are therefore only as safe as the transport you give them. OPEN No tailnet HTTPS support exists or is claimed.
  • A label shown to a model is not a gate. Codex is told who asked; it can still be persuaded by the text.

7. Tasks, questions and results

The task layer is what the current system lacks, and what makes "ask, clarify, result" a thing the system knows instead of two terminals a human reads.

A schematic send

POST /a2a/agents/0192...9d31

Authorization: Bearer <illustrative token>
Content-Type: application/json

{ "jsonrpc": "2.0", "id": "1", "method": "SendMessage",
  "params": { "message": { "messageId": "m-01", "role": "ROLE_USER",
                            "parts": [ { "text": "Review the retry loop in client.go." } ] },
              "configuration": { "returnImmediately": true } } }

What the spec and proto say about these pieces: A2A-Version is sent "with each request" (3.6.1). JSON-RPC uses PascalCase method names such as SendMessage and GetTask (9.1). returnImmediately true "returns immediately after creating the task"; false, the default, makes the call wait until the task is final or needs input. SPEC The response is a Task or a Message (a proto oneof); how JSON-RPC wraps that, the exact enum spelling in JSON, and the endpoint path were UNVERIFIED: the spec page's own examples disagree with the proto in places (section 12).

How task states mean something in Ratatoskr

A2A stateMeans hereSet by
SUBMITTEDThe gateway accepted the request and dispatched it to the target host. Not that the model has read it.Gateway
WORKINGThe target's harness took the prompt (today's accepted receipt).Target daemon, through the adapter
INPUT_REQUIREDThe worker explicitly asked a question. The question is the status message.The worker, by a tool call
COMPLETED, FAILED, REJECTEDThe worker explicitly reported that, or the system ended it (the session ended: FAILED).The worker by tool, or the gateway
CANCELEDCancellation actually took effect. Not produced in phase 1 (a working task answers TaskNotCancelableError, section 1b).Gateway, on confirmation
AUTH_REQUIREDNot used in the first version.none
  • No "Stop means completed". A harness hook such as Stop says a model turn ended. It is evidence the model went quiet, nothing more. A task finishes only by an explicit report. If a turn ends with no report, the task stays WORKING and carries a metadata flag, "turn ended without a report", that a person or the sender can see. PROPOSAL
  • Delivery receipts stay separate. host_stored, pasted, accepted and the uncertain results are adapter facts about getting text into a terminal. They are recorded on the task's delivery record, not mistaken for task states. CODE they exist today as message states.
  • New agent-facing tools are needed, because the worker must be able to say "I need input" and "here is the result": one to report a state with a message and optional artifact, one for the sender to reply to a task, and one to read a task. The existing send tool stays and returns the task id. Tool names are an OPEN detail.
  • Results are artifacts. SPEC Artifact needs an id and at least one Part (text, bytes, a URL or structured data). First version: text artifacts.

The asynchronous wake

When Codex asks a question, the gateway knows at once and can tell the Mac daemon over its stream. But a daemon holding an event is not a model reading it. The daemon must put the question in front of Claude's model, which means injecting it as a prompt when Claude is free, the same adapter path ratatoskr messages use now: held while busy, pasted when idle, tracked as pasted and accepted. CODE That path can hold, miss, or be ignored by the model. Nothing in A2A makes a model attentive. For an external client, "the wake" is simply polling or a subscription.

MCP, hooks and the terminal remain adapter mechanics. They are how a task reaches and leaves a particular harness. A harness that later offers a native session API could replace hooks as the detector of turn boundaries. It would not replace A2A as the way outside parties and Ratatoskr sessions talk. PROPOSAL Pi and OpenCode would each need their own adapter; nothing about them is examined here.

12. Gaps and spec inconsistencies

  • Wire examples are schematic. No example was validated against a reference implementation. Enum spelling in JSON, the JSON-RPC result wrapper and the endpoint path (the spec shows /rpc only as an example) were not verified.
  • The spec disagrees with itself in places. It says SendMessage "MUST return immediately" (3.1.1) while also making the call block by default (3.2.2); it requires PascalCase JSON-RPC method names (9.1) but shows category/action (9.3); it says application/json for JSON-RPC (9.1) and uses application/a2a+json elsewhere (14.1.1); it shows lowercase task states in examples while the proto uses TASK_STATE_*. The proto is the stated normative source (1.4), so this page follows the proto and flags the rest.
  • Not found in the spec: a path-scoped well-known location; any A2A error name for authentication or authorization; a rule on messageId uniqueness scope; a section named "task immutability" (the closest text is in 3.4.2 and 3.4.3).
  • Read 2026-11-08 for the compliance table (section 1a): 3.1, 3.2.6, 3.3.1 to 3.3.4, 3.5.1, 3.6 and 4.4.3, mostly verbatim; the numeric error codes of 5.4 and section 5.1 came from summaries only. The spec has no conformance section. UNVERIFIED
  • External participants: the enrolment and credential mechanics, the allowed address and TLS classes for registered URLs, and the lifetime of tasks across a service restart are proposals without source evidence. I did not find a standard enrolment API for A2A in the sections read.
  • Not read verbatim: section 7.6 (in-task authorization), the push-notification config tables, and the OAuth flow messages. Section 7.6 might matter for AUTH_REQUIRED, which this design does not use.
  • Not examined: Pi and OpenCode, native harness session APIs, and whether Claude and Codex can be woken reliably by a prompt injected at an arbitrary time. Today's pasting works only on the cases that have been observed; much of it has not been run since the daemon change.
  • Unchanged: MCP, hooks and gates for managed sessions, the SSH entry, the Network and Graph tabs (hosts stay the Graph's nodes), workers and remote dispatch.
