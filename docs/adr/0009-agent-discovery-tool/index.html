ARCHITECTURE DECISION RECORD 0009

Agent discovery for models, and a gateway dashboard for people

A proposal for one tool, here called ratatoskr_discover, that returns every paired host's card, its description and capabilities, its host name, and the sessions you can contact right now, in one compact list. The model decides whom to contact. The gateway is a directory, not a search engine. This is a proposal only. No code was written, nothing was run, and the page has not been opened in a browser.

Third revision, 2026-11-11 (later still). The owner decided: no TLS in v1, plain HTTP; viewers may see exact session ids and all Agent Card details; the v1 dashboard is read-only (D11 to D13). Consequence, in plain words: dashboard data, including host and session details, travels in cleartext and can be observed or modified by anyone able to intercept the connection. Future TLS is deferred. These three answers did not by themselves settle the bind questions; the fourth revision below does.

Sixth revision, 2026-11-11 (latest). The owner accepted the recommendations on transport and legacy flags (D18 to D20, USER). The participant API on 7790 keeps HTTPS as the default, with plain HTTP as an explicit opt-in through --participant-insecure-http. The host protocol on the shared 7777 is plain HTTP by default, together with the dashboard, and HTTPS with fingerprint pairing is preserved as an opt-in. rtk gateway --allow-lan and rtk gateway --insecure-http are retired. Breaking, decided but not built: every existing command line or script that passes either flag changes behaviour, and a LAN gateway that relied on the old HTTPS default becomes plain HTTP unless the HTTPS opt-in is chosen. No blocking decision remains; the non-blocking open items are N1 to N4 (section 13).

Fifth revision, 2026-11-11 (latest). The owner decided that the shared port 7777 is plain HTTP for both the dashboard and the host protocol (T2, D17). Consequence: host credentials (the bearer on every host request) and message bodies on that listener are cleartext on every reachable interface and can be read or injected; network firewalling is the boundary. Still open: the transport of the separate participant API on 7790 (T1), and what happens to today's HTTPS host mode, --fingerprint pairing and the --allow-lan and --insecure-http flags (T3).

Fourth revision, 2026-11-11 (latest). The owner decided: all gateway services (dashboard, host protocol, participant API) default to binding 0.0.0.0, a default changeable by command-line arguments (X1), and the dashboard shares port 7777 with namespaced routes (X2). Consequence: the host protocol, which carries host credentials, and the participant API now default to every interface too, including any public one. New open items: what transport each service uses under a wildcard bind (T1), and the tension that a shared 7777 couples the dashboard's transport to the host protocol's (T2). X3 is decided in the same revision: the refusals of the wildcard and of explicit public bind addresses are removed for all three listeners, and explicit public IPs may be given on the command line. Consequence: network firewalling becomes the exposure boundary; the command-line override is not protection.

Second revision, 2026-11-11 (later). The owner decided: the dashboard is open to anyone who has the link, with no authentication in v1; the gateway binds 0.0.0.0 by default (every interface), default port 7777 and changeable by a command-line argument; Cytoscape.js draws the graph; and the mock-ups use the cream, warm palette of the explainer video (D7 to D10, section 7). Consequence, in plain words: anyone who can reach the exposed listener and obtain its URL can see the graph, every Agent Card and the other dashboard data. The URL is not a secret and not authentication. Details and the questions this leaves open are in section 13.

Revised 2026-11-11 (section 7). The owner decided that TOON is used only in the model-facing reply of this tool (section 8), and that the gateway hosts an HTMX web dashboard with a navigation bar and a Network page whose graph opens a host's Agent Card (sections 9 to 13, with static mock-ups in section 12). The two surfaces are kept apart: models see TOON, people see HTML, and the gateway's JSON APIs and stored cards do not change.

1. Short answer

One tool, one list, the model chooses. A session calls the tool and gets a compact list: for each paired host, its name and address, its card's description and declared skills, when the gateway last saw the card; and for each session on it, the exact name and id and whether it is connected. The model reads the list and picks. USER

The gateway only aggregates. It joins data it already holds. It does not search, filter by meaning, rank, embed, call a model or recommend. USER

A host's declaration is not a session's ability. A card says what the host's owner wrote. It does not say that a given Claude or Codex session on it has the skill, and nothing checks. The list says so, and keeps source, freshness, reachable and unknown as separate facts. PROPOSAL

Most of the data already exists. Hosts, their sessions and their liveness are served at GET /v1/network, and host cards with their freshness at GET /v1/graph. A first directory therefore needs no new protocol. The earlier plan placed it after an A2A first delivery; with A2A deferred, section 5 says what that changes.

  • Source, freshness, reachable and unknown are four separate things. The card's text comes from the host (declared), its age from the gateway's last poll, "connected" from the stream and heartbeat, and anything the gateway does not know is printed as unknown rather than guessed. A stale card or a disconnected host is shown, not hidden.
  • Participants, not only sessions. Only if a gateway interface for externally managed participants is ever built could the list include them, marked as such. That interface does not exist and is not decided (deferral record); nothing here depends on it.
  • Exact ids come with names. Sessions are listed with the exact id so the send goes to that session and not whatever the name means later. Whether the current send tool can address a session by id is UNVERIFIED; the friendly name works today. The id is routing help, not authority.
  • Optional detail. A second form returns one host's full card on request, for a model that wants the skills' descriptions. Payload bounds and paging are added only when the number of hosts makes the list too large; until then no paging. PROPOSAL

4. What it does not do

  • No search, ranking, embeddings or model in the gateway. The gateway returns the whole directory it holds. If it grows too large, the answer is bounds and paging, not relevance.
  • No automatic work assignment and no worker spawning. The tool lists; the model sends a normal message to a session that already exists.
  • No verification of skills. It repeats host declarations and live connection facts. It never says a session "can" do something.
  • No new permission. Seeing a session in the list does not allow sending to it; the gateway's send checks are unchanged, and a refused send is reported as refused.
  • No change to host cards or the Graph tab. They stay as ADR-0005 describes, and they do not imply that a host supports any task or messaging protocol.

8. TOON at the model-facing boundary only

What the owner chose (D1, USER): TOON appears only in the discovery tool's reply to a model. The gateway's JSON APIs, the stored Agent Cards and the canonical card form do not change. The conversion is a presentation step at the very end of the tool, so removing it later means changing one function.

What TOON is, from its own specification (fetched 2026-11-11): toon-format/spec SPEC.md states Version 4.4, Date 2026-10-08, Status: Working Draft, and says that the document "may be updated, replaced, or obsoleted". It describes TOON as "designed primarily for LLM prompts and contexts where every token costs". A uniform array becomes a table with a declared length and field list, then one row per line (spec example: users[2]{id,name,role}:). Strings are unquoted unless they are empty, look like a number, are true, false or null, have leading or trailing spaces, or contain a delimiter, colon, quote, backslash, bracket, brace or control character. Null is the literal null. SOURCE (external; not read in full: the spec sections after the string rules were not read)

Two details the example already shows. A host's declared skills are a nested list, and a TOON table row holds only single values, so the skills move to a second table keyed by host (a layout choice that must be tested, not assumed). A description that contains a comma has to be quoted, and a description containing a colon would too (the spec's rule; UNVERIFIED that an encoder applies it to every host-written string, which is untrusted text).

Measure before adopting

The owner chose the boundary, not a number. No token saving is claimed here. Before this is adopted the team measures, and reports, at least:

  1. Token counts of the actual discovery payload in TOON against minified JSON (and against the plain list of section 2), with the tokenizers of the models that will read it, at representative sizes: for example 3, 10, 30 and 100 hosts, with one to four sessions each. A table of three rows may not save anything; a table of a hundred may.
  2. Correct reading of status. A model must still tell live, stale, offline, none and unknown apart, and must not read null as "online" or "none". Ask it questions with known answers (which sessions are connected? which card is stale? does vmc have a card?) over the TOON and the JSON forms and compare.
  3. Exact session ids. The id in the reply must be byte-for-byte the gateway's id, never shortened, and a model copying it into a send must produce the same string. Test for confusion between similar ids and names.
  4. Hostile text. A card description or skill name is written by a host owner. Test values with commas, colons, quotes, newlines, leading - or #, the word null, and text that tries to look like TOON rows or instructions. The result must decode to the same strings, and must not let a description add or alter a row.
  5. The encoder. Which implementation, and whether a small in-house encoder pinned to a spec version is safer than a library, is OPEN. Because the spec is a working draft that "may be updated, replaced, or obsoleted", pin the version it encodes to, keep the encoder behind one function, and keep golden tests on the exact output.

Fallback. If the measurements do not show a worthwhile saving, or a model misreads a status, the same boundary function returns compact JSON or the plain list instead, and nothing else changes. PROPOSAL

Hub and spoke, honestly

  • The gateway is the hub. Hosts connect to the gateway; they do not connect to one another. The graph draws one spoke from each host to the gateway, styled from connection.live: solid when live, dashed when not live. A host the gateway has never heard from is drawn dotted. No host-to-host line is drawn for connectivity, because none exists. PROPOSAL
  • A difference from the TUI Graph tab, stated. In the source, /v1/graph carries only one kind of edge, messages_seen: a rolling 24-hour count of sends between a pair of hosts, computed from the message ledger, and never "delivered" (GraphEdge, edges_partial). It is real data, but it is history, not connectivity. The web view therefore shows the spokes as the graph, and offers messages_seen only as an optional overlay, off by default, labelled "messages seen in 24 h (sends, not deliveries)". Whether the web view should match the TUI by showing it by default is OPEN. I did not read the TUI's render code, only the data and ADR-0005.
  • Card declaration is never shown as verified. The card panel labels the text "declared by the host owner" and shows the card's age and source beside it. The page never writes "can do" or "supports". PROPOSAL
  • Participants are not hosts. External participants (ADR-0007) have no card and are not in /v1/graph. Whether they appear as a separate node kind is OPEN; nothing here draws one.

13. Security and open questions for the dashboard

Open access, stated plainly. Decision D7 is that the dashboard needs no login in v1. Anyone who can reach the gateway's dashboard listener and obtain its URL can view the Network graph, every Agent Card, host names, session ids and the other dashboard data. The URL is an address. It is not a secret, it is not authentication, and nothing may describe or rely on it as access control. Authentication is deferred. Decision D8 makes the default bind address 0.0.0.0, which listens on every interface of the machine: loopback, the LAN, Tailscale and any public interface the machine has. Together, with the defaults as decided, anything that can route to the gateway machine's port can read the dashboard.

No encryption either (D11). The owner chose no TLS for v1: the dashboard is plain HTTP. So on top of open access and an every-interface bind, dashboard data, including host names, session ids and Agent Card text, travels in cleartext. Anyone on the network path can read it, and can also alter what a viewer sees (for example a forged card or status). Future TLS is deferred.

What a viewer sees (D12). Exact session ids and all Agent Card details, to anyone who reaches the page.

The v1 dashboard is read-only (D13). Every route is a GET; there is no message sending, host revocation or other state-changing control. That follows the owner's decision, and it matters more here because the page is open and unencrypted. Any later control needs authentication, CSRF protection and its own decision.

Every gateway service, not only the dashboard (D14). The owner decided that the dashboard, the host protocol and the participant API all default to 0.0.0.0. A wildcard bind includes any public interface the machine has, so by default the host protocol (which carries host credentials and messages) and the participant API (adapter credentials) are reachable from wherever the machine is reachable, not only the read-only page. Each can be changed with command-line arguments. The participant API keeps port 7790 (DefaultParticipantPort) unless the owner says otherwise. CODE

The dashboard shares 7777 (D15). It is served by the same listener as the host protocol, under namespaced routes. Existing gateway routes are all under /v1/ (/v1/pair, connect, sessions, heartbeat, stream, messages, report, network, graph), and the participant API is a separate listener under /participant/v1; the proposed /ui/* names do not clash. The owner decided only that routes are namespaced; the exact names stay PROPOSAL. CODE

The refusals are removed (D16). Today internal/gateway/listen.go refuses the unspecified address (line 128, "is the unspecified address; name the interface address explicitly") and any address that is not loopback, Tailscale or private LAN (line 135, "no public mode"); ADR-0002 chose that on purpose. CODE The owner decided to remove both refusals for all three gateway listeners, keep 0.0.0.0 as the default, and allow command-line overrides that name explicit public IPs. The security consequence, stated plainly: with no TLS (D11) and an open dashboard (D7), any interface that can be reached can expose the dashboard, Agent Card and session data in cleartext; and if the host protocol and participant listeners are reachable, host credentials, participant credentials and messages are exposed too. Network firewalling is now the exposure boundary. Choosing an address on the command line does not protect anything: an explicit public IP is as exposed as the wildcard. How the refusals are removed in code is an implementation matter for a later, authorised task.

The shared 7777 is plain HTTP (D17). The owner decided that port 7777 is plain HTTP for both the dashboard and the host protocol. So host credentials (the bearer sent on every host request) and message bodies on that listener are cleartext on every reachable interface, and can be read or injected by anyone on the path. Network firewalling is the boundary; neither the address chosen on the command line nor the open page protects them. The participant API on 7790 is a separate listener and is not covered by this decision (T1).

Final transport rules (D18, D19, D20), decided and not built. Participant API on 7790: HTTPS by default, plain only with --participant-insecure-http. Host protocol and dashboard on 7777: plain HTTP by default, HTTPS plus fingerprint pairing as an opt-in. A default changes: today a LAN address without --insecure-http is HTTPS (TransportHTTPS); under D19 a gateway on any address serves plain HTTP unless the HTTPS opt-in is chosen, so an owner who relied on the old LAN default silently moves from HTTPS to cleartext on upgrade. Existing LAN-HTTPS pairings (scenario 2's HTTPS variant) keep working only if the opt-in is chosen. Firewalling remains the boundary for everything on 7777. CODE

What the source does today, and what D8 changes

  • Today rtk gateway --listen has no default address. It needs an explicit IP:port, and it refuses the unspecified address (internal/gateway/listen.go: "is the unspecified address; name the interface address explicitly"). CODE
  • It also refuses every address that is not loopback, Tailscale or a private LAN range, with the words "there is no public mode" in the same file. ADR-0002 chose that on purpose (loopback, Tailscale or private LAN only). CODE
  • Port 7777 is the documented convention (README, ADR-0002 and the scenarios, and the tests). No default port constant exists in the source I read. CODE D8 records 7777 as the default, overridable on the command line.
  • So D8, D14 and D16 reverse today's rule, for all three listeners. The owner decided it; the refusals above are to be removed in a later, authorised build. The transport rules are decided (D17 to D20); only the naming and compatibility items N1 to N4 below remain.
