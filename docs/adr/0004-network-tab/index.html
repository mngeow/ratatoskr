ARCHITECTURE DECISION RECORD 0004

A Network tab inside the attached window: see every host's sessions and enter any of them

One extra tab in the window you already get from rtk attach. It lists the hosts and sessions on the network, and entering a session on another machine opens a direct SSH connection from your Mac. A gateway API supplies what the tab shows, and SSH, run from your own terminal, does the entering. The gateway never carries a terminal. As of 2026-11-07 this is written but has never been run.

1. Short answer

The Mac's attached window gets a third kind of view: a Network tab. It sits beside the terminals and the message log you already have, and it lists local and remote sessions with their freshness. PROPOSAL

Selecting a session on an Ubuntu VM and pressing Enter asks that VM's own daemon, through the gateway, whether the session is still there and enterable. Then your Mac hands its terminal to ssh -t, using your own keys and config, and runs rtk attach on the VM for that exact session. F10 there brings you back to the tab. PROPOSAL

The gateway can be anywhere. It answers "who exists" and relays one short question and answer. The terminal travels over a separate SSH connection from your Mac to the VM, over the LAN or a tailnet. PROPOSAL

This is not a dashboard. There's no new command and no screen of its own. The tab exists only inside a window attached to a session, and its Enter action leaves the window. USER asked for an additional tab.

1a. What was built (2026-11-07)

CODE Read from the working tree and the lead's static review. No test, rtk, gateway, daemon or ssh has been run for any of it (GR-3), so every line below is what the code is written to do. The authoritative field-by-field description is the contract.

The central API direction replaced the relayed question. Each host daemon reports its own sessions to the gateway, the gateway aggregates them in memory, and the owner's daemon reads the result and gives it to the window. The gateway relays no question and no terminal, and nothing polls a host over SSH. Enter builds its plan from that snapshot and the owner's hosts.json, and the remote rtk attach --expect-session makes the authoritative check.

Host map (decision 2)<state dir>/hosts.json, version 1, read at each Enter, keyed by the gateway's host name, with ssh, absolute rtk and optional state_home. Refused if linked, not regular, writable by others, owned by someone else or over 64 KiB. No entry means a by-hand command, run by nothing.
Enter from inside a remote window (decision 5)Blocked with "press F10 to return to the machine you came from, then choose from there".
Window with no sessions (decision 10)Unchanged: a window needs a session. If none run when you return from SSH, rtk prints the no-sessions guidance and exits.

The new commands. rtk daemon network [--json] [--watch] and rtk attach --expect-session ID [--entered-via-ssh]. Exit codes from the remote attach: 0 normal, 3 the expected session isn't running, 4 no daemon, 2 usage or too-old build, anything else is reported as is. SSH's own 255 can't distinguish unreachable, timeout, host key, auth or a dropped link.

Terminal safety added during review. ssh is stopped with SIGTERM and a kill only after 2 s, because a killed ssh can't restore the local terminal. After any ssh that didn't exit cleanly, the saved termios is restored and a targeted escape-sequence reset is written, never a full reset. SIGINT is caught, never ignored, so ssh stays interruptible while connecting. A failed restore ends rtk rather than opening a window on an unknown terminal.

Known limits of what was built

  • Never run. Whether the terminal comes back clean after every way ssh can end is the main thing the owner's first test has to answer.
  • The 600 ms handover wait (drops typeahead during the handover) rests on reading Bubble Tea v2.1.1's source, not on observation. A late terminal reply may still leak, and nothing is flushed on return. UNVERIFIED
  • Same-user agents aren't isolated from this data. They can read pairing.json, and any paired host can read every host's snapshot. The API grants no control, and entry still needs the owner's SSH keys.
  • No cap on parked long-polls (paired hosts only). A poll parked when its host is unpaired can answer for up to 20 s.
  • A stale report is history, not proof a process still runs. unknown is never shown as idle, and a host with no report reads "no report".
  • chi differences: HEAD on a GET route is 405, and an unclean path is 404 rather than a redirect. The router change was first written by the backend without the supervised path and was reported to the owner rather than redone.
  • Unix only: darwin and linux. No HTTPS over a tailnet, no offline replay, no remote worker spawn, no Herdr dependency.
  • Compatibility: either machine may be upgraded first, but the tab needs the gateway and each daemon on the new build, and a window must match its own daemon's build. An older gateway gives bare peer addresses with no live flag.

4. What exists today

Traced in the code. This replaces the first draft's list: the gateway and the socket are as before, with the status-ID correction.

It can

  • Answer a paired machine's credential on its routes: connect, sessions, heartbeat, the stream, and messages. CODE internal/gateway/server.go:183 mux.HandleFunc("GET /v1/stream"
  • Send a daemon the directory on the stream: an address, a host and a live flag per agent. CODE internal/protocol/wire.go:115 type StreamFrame struct
  • Count a host live while its stream is open and its heartbeat is under 15 seconds old. CODE internal/gateway/liveness.go:17 liveWindow = 15 * time.Second

It can't

  2. The entry question goes from your Mac's daemon, through the gateway, to the target host's daemon, and the answer returns the same way. It's not a message: it isn't stored in the ledger, isn't shown to any agent, and can't be sent by an agent.

  5. The plan is built here from the fixed template and your mapping. The answer's strings are cleaned of control characters before display. A refusal comes back as a reason to show instead.

6. Handover, and how the tab differs locally and remotely

Does the local window stay, or does a new view open?

PROPOSAL The window suspends and hands the same terminal to SSH, then takes it back. That's what agent-net does when Herdr isn't there, and what Bubble Tea supports through ExecProcess. A new terminal tab or window would depend on which terminal program you use, which Ratatoskr can't see.

Why suspending is enough

  • The sessions live in the daemon, so the local agents keep running while the window is away.
  • You never have two windows drawing into one terminal.
  • Nothing new has to be installed.

What it costs, and one risk

  • You can't watch the Mac's sessions while you're inside a remote one.
  • A suspended window may be dropped by its daemon. The window delivers frames through channels, and a program that isn't reading may fall behind. CODE internal/windowclient/client.go:63 windowEvents chan WindowEvent UNVERIFIED I haven't traced whether the daemon would then close it.
  • So the proposal is to release the window before the handover (close its connection, letting go of the Mac's input as an ordinary close does), and reconnect when SSH ends. The agents never notice. PROPOSAL

The two tabs are different, because they run on different machines

The window on your MacThe window inside the SSH session, on the VM

Why differentA second SSH hop from the VM would need keys there (or your agent forwarded), and it makes "which F10 is this?" ambiguous. Going back to the Mac and choosing again is two keystrokes.

Detach semantics

  • F10 in a remote window detaches only that window. The agent keeps running on the VM and the session is not ended. CODE internal/daemon/gate.go:202 func (g *gate) releaseAll
  • If SSH drops, the remote window ends the same way, and the Mac's window reconnects and shows the tab. Nothing is resent. A keystroke in flight may or may not have arrived.
  • On return, the Mac's window refreshes the tab before showing it, because everything may have changed while you were away.
  • Ending a session stays rtk daemon stop --session NAME on its machine. The tab doesn't offer it.

7. Trust boundary: what the gateway may tell the Mac

The owner's file says where and how. The gateway and the remote daemon say only which and what state.

  • A hostile gateway can, at worst, lie about which sessions exist, say a host is live or not, or stall a question. The result is a wrong row or a timeout. It can't make your Mac connect somewhere you didn't write down, or run something you didn't choose. PROPOSAL
  • A paired host can ask other hosts about their sessions. The same hosts can already message each other. A host can switch off answering these questions in its own config. OPEN
  • Authority is your login. Entering is exactly as strong as your SSH access to that machine. Prompts in the session are that agent's own, answered by you. The tab answers none.
  • No credential is added. Not for the gateway, not for the daemon's socket, and not for SSH. The Mac's daemon uses its existing pairing only to relay the short question.
  • Agents can't reach any of it. The questions are available through the window protocol only, behind the same user-ID and ancestry checks as the rest. They're not MCP tools and not messages. CODE internal/daemon/ancestry.go:78 func ancestryCheck

8. Herdr: is it feasible, and is it needed?

What was checked, without running anything

  • Herdr 0.9.5 is installed on this Mac with Homebrew, from the install files in its Cellar. It's a version of Herdr, not something Ratatoskr depends on.
  • Its README and the strings in its binary show herdr --remote <ssh target>, saved machines (herdr machine add <ssh-target>), and a need for Herdr on both machines. It connects over SSH.
  • agent-net uses that remote client only for a session that runs in a Herdr pane on the other machine. agent-net internal/daemon/enter.go:105

Why it doesn't fit today

  • Ratatoskr's sessions aren't Herdr panes. They live in the daemon's own PTYs. Herdr's remote client would show Herdr's panes, not them.
  • It could work by running rtk attach inside a Herdr pane on each VM. That's an extra layer to install and keep in step on every machine, and nobody has tried it. UNVERIFIED
  • Whether the Ubuntu VMs have Herdr is not known. UNVERIFIED

Proposal: SSH only, now. Herdr could be offered later as an option for people who already use it, with clipboard image paste as the gain, and agent-net shows how. PROPOSAL No dependency, install or setup change is made or proposed here. Whether to ever add Herdr is your choice (section 11). OPEN

Compatibility

  • Builds. A window must match its own daemon exactly, and the proposal never changes that. The Mac's window talks to the Mac's daemon, and the VM's window to the VM's daemon, so the Mac and the VM can run different builds, unlike a forwarded-socket design.
  • Remote build lacks --expect-session. The remote rtk attach would reject the unknown flag, and the Mac would show the by-hand command. It must not fall back to attaching without the flag.
  • Older daemon on the target doesn't answer the new question, which looks like "no answer". Entering is then off, not guessed.
  • Status gets a field. Control messages already add fields without breaking older readers. CODE internal/daemon/serve.go:355 func helloDecision
