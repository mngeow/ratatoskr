DEFERRED ADR RECORD · A2A (ADR-0006)

A2A is deferred: it does not fit what the sessions need today

A short record of why the A2A implementation is set aside for now, what was built before the decision, what is kept, and what would make it worth reopening. This is a deferral for fit, not a finding that A2A cannot carry messages.

Status
Deferred 2026-11-08 at the user's request, as relayed by the operator USER. A deferral, not a rejection and not a supersession; it can be reopened by the user.
Reason
Fit. A2A's task semantics do not match the main current need (direct conversational peer messaging between managed Claude and Codex sessions). It is not a claim that A2A cannot carry messages.

1. The decision

A2A is not being implemented for now. The user asked to abandon it for the time being, with documentation changes only. USER

Why, in one sentence. A2A can carry direct messages as well as tracked tasks, but the current integration models a Claude or Codex conversation as a long-lived task with an id, states and follow-up calls, while what managed sessions mostly need today is plain peer messaging, which ratatoskr_send already does through MCP, hooks and the terminal bridge. PROPOSAL

What this is not. It is not a finding that A2A is unsuitable, unsafe or unable to carry messages, and not a judgement on the team's code. It is a decision about fit with present requirements.

2. Why it does not fit now

The needWhat serves it todayWhat A2A adds or changes
A session sends a conversational message to a peer and gets a reply laterratatoskr_send, the MCP server, hooks and harness delivery through the daemon's terminal bridge CODEA2A has a direct Message form that could carry this. The branch did not use it for chat; every exchange became a task with a lifecycle.
Track a unit of delegated work to a result, across organisations or vendorsNothing specific; a human reads two terminalsThis is where A2A tasks fit well: ids, states, polled retrieval, a result artifact. It is not the primary need today.
Reach the managed Claude or CodexThe daemon's own bridge: MCP, hooks and a terminal pasteA2A does not replace it. Every A2A message to a managed session still ends in that bridge, so A2A would be an added layer on top of it.
  • Task semantics for every chat. Treating each conversation as a task adds states (submitted, working, input required, completed), a rule that a stop is not completion, an answer-on-the-same-task path and a cancel rule. That cost buys little if the sessions only need to talk.
  • No local simplification. The local MCP, hook and terminal bridge stays required for managed sessions either way.
  • Where A2A may still suit. Delegating bounded work, and interoperating with other A2A systems or an external orchestrator. Those are later and unrequested. PROPOSAL

4. What is preserved

  • The implementation. Branch feat/a2a-participants at 29cccad (local and origin). It holds the A2A server on the official a2a-go/v2 v2.8.0 handler with an own SQLite task store, migration 0003, participant commands, the MCP task tools, outbound bearer authentication, ListTasks with the spec's totalSize, and a reference adapter. CODE Never run, and not on main.
  • The contract. docs/implementation/a2a-participants-contract.md exists on that branch only. Read it without switching branches: git show feat/a2a-participants:docs/implementation/a2a-participants-contract.md. The scenario 6 guide is on the branch too (docs/testing/scenario-6-a2a-participants/).
  • The proposal text. The preserved proposal, moved out of ADR-0006 unchanged. ADR-0006 itself is now a short disposition page.

6. When to reopen it

  • Delegated, tracked work is wanted between sessions or with an outside orchestrator, and plain messaging is no longer enough.
  • Interoperability with other A2A systems is a stated requirement, not an assumption.
  • Then start from the branch and the contract, and settle first the engineering unknowns it left open: the SDK's real result shapes, dispatch and wake against a live stream, the polling mirror against a real service, the MCP tool closures, migration 0003 on a real database, and the VM-B tool question above. Reopening is the user's decision; this page does not authorise any of it.

7. What is not claimed
