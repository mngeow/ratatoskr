1. Summary

First preliminary recommendation, kept as history: option A. It was made before the requirement in section 1a and still applies if a central view isn't needed. PROPOSAL One rtk on each host, each in that host's own terminal, connected directly over the existing tailnet. Ratatoskr adds its own pairing on top, retries through a short disconnect, and doesn't deliver to an agent started later.

This assumes one owner, two hosts, and that separate windows are acceptable. The three open questions can each change it.

What it would give you

  • Claude on the Mac and Codex on the server message each other with the same tool they use today.
  • No always-on service to run.
  • If the link fails, both agents keep working and only messaging stops.
  • Each machine still decides for itself when a message is safe to paste.

What it would cost you

  • Two windows, with no combined view. A prompt on the server is only seen by looking at the server's window.
  • We'd own reconnect, retry, duplicate and ordering code, which needs failure testing that GR-3 currently blocks.
  • Pairing and key replacement become new setup steps.
  • Both rtks must be running. A message can't wait for a host whose rtk is down.
  • Other owners or many hosts would need rework.

1a. Direction under discussion: a central gateway

This is a leaning, not a decision. It adds a requirement the comparison below didn't have: one place that sees all Ratatoskr messages. PROPOSAL If that requirement stands, the architect recommends a small form of option B: one owner, one self-hosted gateway and no broker. Section 1b covers how it's deployed and packaged.

Decided requirement. USER 2026-11-05: "Full message bodies please, I will work on optimising space storage later."

If the gateway shares a machine with an agent, an outage there takes both down together. On its own machine, its outages are independent of either agent, so it adds a failure the agents wouldn't otherwise have. Section 1b compares these.

What it costs compared with option A

  • Bigger target. A compromised gateway can read all stored messages and inject prompts into every connected agent. It still can't answer prompts or bypass a host's gate.
  • Plaintext on the gateway. Reading messages there is the purpose, so end-to-end encryption would defeat it. Any secret an agent sends is stored centrally, which needs file permissions and backup rules. With full bodies and no deletion policy yet, the ledger keeps growing, and any secret stays in it until a policy or a person removes it.
  • Single point of failure, and a service to update and monitor.
  • Largest code change. send checks recipient, budget and reply_to against local state, and that has to split between host and gateway. Some refusals become later status updates. CODE internal/router/send.go:75 send
  • Same-host messages gain a dependency on something that works locally today.
  • One view of messages, not one terminal. Prompts stay in each host's window. Streaming terminals through the gateway would give it your keystrokes, and the architect would keep that out.
  • Single owner only. Per-user permissions and who can read what are a separate design.

  4. Mac: outbound · Gateway: no row · Ubuntu B: no row

    Claude calls ratatoskr_send with to: codex@ubuntu-b. It's authenticated by Claude's local token, and that token never leaves the Mac. The runtime saves the message before sending it on.

  5. Mac: gateway_stored · Gateway: full message stored · Ubuntu B: no row

    The Mac sends over its runtime connection, and the gateway stores the full body with its routing details, then confirms. A retry with the same ID is confirmed again and isn't stored twice.

  6. Mac: gateway_stored · Gateway: host_stored · Ubuntu B: queued

    It uses the connection Ubuntu B already opened. The gateway can only offer the message. It has no way to write to Codex's terminal. Ubuntu B saves it, ignoring any ID it already has, then confirms.

  7. Ubuntu B: held, pasted, accepted · Gateway and Mac: accepted (reported)

    Codex's own hooks decide when it's safe. The gateway and the Mac record each state as Ubuntu B's report. Hook payloads stay on Ubuntu B. accepted still doesn't mean the model acted.

  8. Ubuntu B agent: needs_you

    You answer in Ubuntu B's window. The gateway could show a status, but nothing it sends can answer the prompt. Whether it shows that status is still open, and so is one window versus one per host.

  9. Ubuntu B: gateway_stored · Gateway: stored · Mac: held, pasted, accepted

    Codex sends to claude@mac with a reply_to. Ubuntu B and the Mac never connect directly. They don't even need to reach each other.

  10. Gateway: stored, waiting · Mac session: disconnected

    The gateway keeps the reply. When the Mac wakes, its runtime dials again, resumes the same session, and gets anything it hasn't confirmed. Duplicates are ignored.

    The hard case: a disconnected session looks the same as a dead one until the runtime returns. If it comes back as a new run, the old session has ended, and what happens to the held reply is still undecided. UNVERIFIED Sleep behaviour hasn't been tested.

Deployment and packaging options

These are proposals, and they're separate choices: where components run doesn't dictate how they're packaged.

Gateway on its own machine

The scenario above. The ledger stays up if either agent's machine goes down, and no harness runs beside the stored messages. Drawback: one more machine to keep running, and its outage is unrelated to the agents' machines.

Gateway beside a runtime

For example, gateway and Codex both on one Ubuntu server, and Claude on the Mac. Still two components, and the runtime connects to its gateway the same way. Benefit: no extra machine. Drawback: agents on that machine run beside the ledger, so a compromised agent there is close to all stored messages. Separate OS users would reduce that.

Everything on one machine

Two choices. Local mode: no gateway, working as rtk does today. Connected mode with a gateway on the same machine: gives the central view, with the same contract as the other deployments. Connected versus local mode remains an open choice.

SSH and Tailscale are transports, not delivery designs. A could run through an SSH tunnel, and B could run over a tailnet. The real difference is who routes messages.

Good for: one person's two or three machines. No third party, and no service to keep running.

Drawbacks:

  • We own reconnect, retries, duplicate handling and ordering, permanently.
  • Nothing moves while either rtk is down.
  • Peer configuration grows with each host. Past a few hosts it's the wrong shape.
  • Each host gets a new listening port, which needs careful authentication.

Good for: many hosts, several owners, or holding messages while a host is away. Hosts only dial out, so NAT needs no special handling.

Drawbacks:

  • A service to deploy, update, back up and monitor. It's the biggest build here.
  • Router down means all cross-host messaging is down.

On two hosts, B mostly becomes A with the server acting as hub, and the server's outage takes the link with it.

A broker such as NATS is a form of B. DOCS JetStream describes at-least-once delivery and a two-minute default duplicate window, with a retry after that window stored as a second copy. It could replace our transport retries. It can't replace the recipient's gate or its report of what happened, and it's one more service. I wouldn't add it for two hosts.

The message link doesn't depend on your SSH session, which is a real advantage of A over C. Drawback: while you're detached, Codex can sit at a prompt nobody is watching. The README's warning about SSH drops still applies, and it's UNVERIFIED.

8. Trust boundaries and threats

An incoming message becomes typed input to an agent that can run tools. So the link is a sensitive interface, even though it never carries approvals.

What Tailscale can establishWhat Ratatoskr must still establish
DOCS Which node, and which user or tags own it, through WhoIs. Which sources may reach which destinations and ports, through grants. Traffic is end-to-end encrypted, and relays handle only encrypted packets. That the caller is a paired rtk, not another process on that node. Which agent it speaks for. What it's allowed to send. Tagged devices lose their user identity, so "same user" isn't always available.

Another device on the tailnet connects

What stops it: the connection is refused without a paired key. Tailnet policy should also limit that port to your hosts. UNVERIFIED Your tailnet's current policy hasn't been read, so it could allow any of your devices.

Another process on a paired host connects

What stops it: the key. Tailscale sees only the node, so this is why tailnet identity isn't enough. What doesn't: a process running as you can read your key file. That's outside this design, and such a process could already reach much of what's in your home directory.

A pairing key is stolen

What it allows: sending messages that get pasted into the other host's agents, which is prompt injection. It doesn't allow answering prompts, forging hooks or reading panes, because the link has no route for those. Needed: an unpair command that removes the peer on the receiving side. Earlier research found that agent-net has no node revocation, so this mustn't be left out.

A valid peer sends a hostile message

For example, the sending agent has itself read a malicious web page. The frame sanitises the body and names the sender, and the receiving model decides what to do. This isn't solved. The harness's own permissions are what stop a harmful action, and only when it asks. Cross-host messaging makes this more serious, because the server may hold different credentials from the Mac.

A peer lies about readiness or status

It can't affect the recipient's gate, because the gate reads only local hooks and local input. It can lie about what happened to messages you sent, so status from a peer is always labelled as reported. The receiver takes the host name from the paired key, so a peer can't pose as another host. It can still name any agent on its own host, so the agent part of the sender's name is only that peer's claim.

Secrets and privacy

  • PROPOSAL Keys stay in the per-machine state directory, never in the repo. MCP tokens never cross the link.
  • Message bodies are stored in both hosts' databases, so anything an agent sends is now on two machines, under each one's retention.
  • Agents can paste secrets into messages. Nothing scans for that today.
  • Trusting the tailnet includes trusting its coordination service. Pinned keys inside it reduce how much depends on that. PROPOSAL

10. Possible build order

This is not authorization to build. It applies if the user selects A, and each phase would need its own go-ahead. Testing and pushing remain under GR-3.

  1. The user answers section 5 and reads the tailnet's policy. This record then gets updated, or replaced if the choice changes its shape. Done when: an option is selected.

  2. Choosing which agents start, and qualified addresses, with no networking yet. Done when: a single-host run behaves as it does today, with the new names.

  3. Listener, pairing, outbox and duplicate handling. Done when: a message reaches the other host's gate, and a repeated ID doesn't paste twice.

  4. Status reports, replies across hosts, and the TUI's view of link health. Done when: the flow in section 6 runs by hand.

  5. Reconnect, the retry window, restarts and sleep. Done when: each scenario in section 7 has been forced and observed, not just reasoned about. This phase depends on the user lifting GR-3 for it.

  6. A daemon split, PTY streaming or a router. Each is a separate decision and doesn't follow automatically from the earlier phases.
