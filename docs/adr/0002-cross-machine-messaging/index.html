1. Where this stands

The selected direction: agents message through a central gateway on your tailnet, and a send fails straight away if the other host can't be reached. Each machine's runtime still decides when a message is safe to paste. This is still a proposal: its details aren't accepted, and nothing is authorized to build.

What this gives you

  • One place to read every message that reached the gateway, including ones that failed.
  • A clear answer at send time in the common cases, so a model isn't left assuming a message will arrive.
  • No queued message landing later in a session that has moved on.
  • Less retry and reconnect code than the earlier design.

What it costs you

  • If the gateway is unreachable, no connected agent can message another, even on the same machine, and those attempts stay out of the central view.
  • Closing your laptop makes replies to it fail. Their text stays readable at the gateway, but they aren't delivered when you return.
  • A brief network drop shows up as a failed or uncertain message, and someone has to send again.
  • The gateway is a new, sensitive service to run. A compromised one can read stored messages and inject prompts into connected agents.

Still open: see section 5.

It's not exactly-once. Nothing is retried automatically, and message IDs only stop the same network attempt being applied twice. They can't catch a model that decides to send again, because that's a new message with a new ID. Section 7 walks through each failure.

The gateway is unreachable

Agents keep workingSends fail at once: gateway_unreachableRecorded on the sending host only

This includes two agents on the same machine in a connected deployment. Using a local shortcut instead would make the central view incomplete, so there isn't one.

Nothing is resent when the gateway returns. If the gateway's disk is lost, its ledger is gone, but each host still has its own history.

If the gateway shares a machine with an agent, an outage there takes both down together. On its own machine, its outages are independent of either agent, so it adds a failure the agents wouldn't otherwise have. Section 1b compares these.

What it costs compared with option A

  • Bigger target. A compromised gateway can read all stored messages and inject prompts into every connected agent. It still can't answer prompts or bypass a host's gate.
  • Plaintext on the gateway. Reading messages there is the purpose, so end-to-end encryption would defeat it. Any secret an agent sends is stored centrally, which needs file permissions and backup rules. With full bodies and no deletion policy yet, the ledger keeps growing, and any secret stays in it until a policy or a person removes it.
  • A single point of failure for all connected messaging, and a service to update and monitor.
  • Largest code change. send checks recipient, budget and reply_to against local state, and that has to split between host and gateway. CODE internal/router/send.go:75 send
  • Same-host messages gain a dependency on something that works locally today.
  • One view of messages, not one terminal. Prompts stay in each host's window. Streaming terminals through the gateway would give it your keystrokes, and the architect would keep that out.

With immediate failure, the gateway's main benefit is the central view. A gateway could also have held messages while a host was away, but that was not selected.

  2. The runtime launches the harness in a PTY it owns, with a local MCP token and hooks.

    A Codex you started separately can't simply join. Delivery needs the PTY, and the MCP and hook setup, that the launcher provides. Attaching to one would be its own feature. CODE internal/pane/pane.go:188 exec.Command

  3. Directory: claude@mac · codex@ubuntu-b

    Each runtime opens a long-lived connection outward across the tailnet. The gateway never dials a runtime, and runtimes need no listening port. The gateway takes the host name from the pairing, so ubuntu-b can't register as mac. It gives each session its own ID, so a later restart counts as a new session under the same name.

  4. Mac: sending · Gateway: no row · Ubuntu B: no row

    Claude calls ratatoskr_send with to: codex@ubuntu-b. It's authenticated by Claude's local token, and that token never leaves the Mac. The runtime records the attempt, then forwards it. The tool call waits for a short, bounded time for the result. That's a change from today, when it returns as soon as the message is accepted locally.

  5. Mac: sending · Gateway: gateway_stored · Ubuntu B: no row

    The gateway stores the full body with its routing details, then looks up the session. If the host isn't connected, or the session has ended, the send fails here, and the failure stays in the ledger. Section 7 shows those cases.

  6. Mac: host_stored · Gateway: host_stored · Ubuntu B: queued

    The gateway offers it once, over the connection Ubuntu B already opened. It has no way to write to Codex's terminal. Ubuntu B saves the message, ignoring any ID it already has, and confirms. Only now does the tool call return success, meaning "the recipient's host has it", not "delivered".

  7. Ubuntu B: held, pasted, accepted · Gateway and Mac: accepted (reported)

    Codex's own hooks decide when it's safe. Holding here isn't an offline queue. The host is reachable, and the agent is busy, waiting on approval or has your draft in progress. The gateway and the Mac record each state as Ubuntu B's report. Hook payloads stay on Ubuntu B. accepted still doesn't mean the model acted.

  8. Ubuntu B agent: needs_you

    You answer in Ubuntu B's window. The gateway could show a status, but nothing it sends can answer the prompt. Whether it shows that status is still open, and so is one window versus one per host.

  9. Ubuntu B: host_stored · Gateway: host_stored · Mac: held, pasted, accepted

    Codex sends to claude@mac with a reply_to. Ubuntu B and the Mac never connect directly. They don't even need to reach each other.

  10. Ubuntu B: destination_unreachable · Gateway: destination_unreachable, body kept · Mac: no row

    The gateway records the reply and tells Codex straight away that it failed. It isn't delivered when the Mac wakes. The Mac's runtime reconnects for future messages. You can read the reply at the gateway, or Codex can send it again.

    Unavoidable ambiguity: just after the Mac sleeps, its connection can still look alive. The offer then gets no confirmation, and the result is delivery_uncertain, not a clean failure. UNVERIFIED Sleep behaviour hasn't been tested.

Deployment options and packaging

These are separate choices. Where components run is still proposed. How they're packaged is decided: one binary.

Gateway on its own machine

The scenario above. The ledger stays up if either agent's machine goes down, and no harness runs beside the stored messages. Drawback: one more machine to keep running, and its outage is unrelated to the agents' machines.

Gateway beside a runtime

For example, gateway and Codex both on one Ubuntu server, and Claude on the Mac. Still two components, and the runtime connects to its gateway the same way. Benefit: no extra machine. Drawback: agents on that machine run beside the ledger, so a compromised agent there is close to all stored messages. Separate OS users would reduce that.

Everything on one machine

Two choices. Local mode: no gateway, working as rtk does today. Connected mode with a gateway on the same machine: gives the central view, with the same contract as the other deployments. Connected versus local mode remains an open choice.

One binary, with separate startup commands SELECTED

  1. You run rtk on each host. They've paired once, so each trusts the other's key. Each announces its current run and agents, so the Mac knows codex@server exists.

  2. Mac: outbound · Server: no row

    Claude calls ratatoskr_send with to: codex@server. That's still a local MCP call with a local token. The Mac saves the message before anything crosses the network, then returns its ID to Claude. That return means "accepted for sending", not "delivered".

  3. Mac: outbound · Server: no row

    The Mac sends the oldest unconfirmed message for that peer, one at a time, which keeps the order simple. The server checks that the caller holds a paired key and that the message is meant for its current run. A new listener handles this. It has no route to /mcp or /hook.

  4. Mac: peer_stored · Server: queued

    The server inserts the row, then confirms. If the same ID arrives again, it confirms again and does nothing else. messages.id is already unique, which suits this. CODE internal/store/migrations/0001_init.sql:22 UNIQUE

  5. Mac: peer_stored · Server: held, then pasted

    The server's existing gate looks at Codex's own hooks. If Codex is busy, or you're typing in its pane, the message waits. The Mac can't tell the server that Codex is ready. When it's safe, the server pastes the message, with claude@mac named as the sender.

  6. Mac: accepted (reported) · Server: accepted

    The server reports each state change to the Mac, and resends the latest state after a reconnect. On the Mac this is only a display of what the server reported. accepted still doesn't mean the model acted on it.

  7. Server agent: needs_you

    The prompt appears in the server's window, and you answer it there. The link never carries the answer. Whether the Mac should show "Codex needs you on server" is an open question. Nothing on the link could answer it.

  8. Server: outbound · Mac: no row for the reply

    The same steps run in reverse, and the Mac's gate uses Claude's hooks. If you're typing in Claude's pane, the reply waits. Round trip complete, with a copy of each message on both hosts and no shared database.

7. Scenarios: what happens when something can't be reached

The rule: nothing is retried automatically, and nothing is held for a host that's away. Certain failures say so, and uncertain ones say that instead, because after a timeout nobody can honestly say a message didn't arrive. All of this is proposed and untested. The status names are proposals.

StatusWhat it meansCould it still be delivered?In the central view?
gateway_unreachableThe runtime had no connection to the gateway, so it sent nothingNoNo, sending host only
gateway_uncertainThe runtime sent it, and the gateway didn't answer in timeYesPossibly
destination_unreachableThe gateway has it, and the destination host had no live connection. It was never offeredNoYes, as a failure with its full body
session_goneThe destination host is connected, but that session has ended. It isn't given to a new sessionNoYes, as a failure with its full body

After that, today's states still apply: pasted, accepted, unconfirmed, failed and interrupted.

The gateway is unreachable when Claude sends

Where two decisions meet: a message that never reached the gateway can't be in its view. So the central view covers every message that reached the gateway, not every attempt. These attempts are local records, and they're never delivered. Uploading them later as records only is an open choice.

The gateway doesn't answer in time

Sent to the gatewayNo answerTool returns gateway_uncertain

The gateway may have stored it and may still deliver it, so the result can't say "failed". The runtime doesn't resend it. When it reconnects it can ask about that ID and correct its record.

The destination host is away

The stored copy is a failure record, not a queued delivery. When the host returns, nothing is delivered. This covers a closed laptop, a stopped rtk, and a dropped SSH connection if rtk wasn't in tmux. With tmux, rtk keeps running and messages still flow, though a prompt can sit unwatched.

The session has ended

This isn't "unreachable", so immediate failure doesn't apply. It can take a long time if a prompt is waiting for you. The message belongs to that session, and it ends interrupted if the session ends first.

8. Trust boundaries and threats

An incoming message becomes typed input to an agent that can run tools. So the link is a sensitive interface, even though it never carries approvals.

Trust: this host only

MCP tokens, hooks, gate, panes, promptsnever exposed to a peer
untrusted peer input

checked at the receiver

Crosses the link

Message, confirmation, statusnothing else
What Tailscale can establishWhat Ratatoskr must still establish
DOCS Which node, and which user or tags own it, through WhoIs. Which sources may reach which destinations and ports, through grants. Traffic is end-to-end encrypted, and relays handle only encrypted packets. That the caller is a paired rtk, not another process on that node. Which agent it speaks for. What it's allowed to send. Tagged devices lose their user identity, so "same user" isn't always available.

Another device on the tailnet connects to the gateway

What stops it: the gateway refuses anything without a paired credential. Tailnet policy could also limit that port to your machines, but this design doesn't change your policy. UNVERIFIED Your tailnet's current policy hasn't been read, so it could allow any of your devices.

Another process on a paired host connects

What stops it: the pairing credential. Tailscale sees only the node, which is why tailnet access isn't enough. What doesn't: a process running as you can read the credential file. This design doesn't promise isolation between processes on a machine.

A pairing credential is stolen

What it allows: sending messages that get pasted into the other host's agents, which is prompt injection. It doesn't allow answering prompts, forging hooks or reading panes, because the link has no route for those. The thief also needs tailnet access. Needed: a way to remove a runtime at the gateway, and pairing again to replace its credential. Earlier research found that agent-net has no node revocation, so this mustn't be left out.

A valid peer sends a hostile message

For example, the sending agent has itself read a malicious web page. The frame sanitises the body and names the sender, and the receiving model decides what to do. This isn't solved. The harness's own permissions are what stop a harmful action, and only when it asks. Cross-host messaging makes this more serious, because the server may hold different credentials from the Mac.

A peer lies about readiness or status

It can't affect the recipient's gate, because the gate reads only local hooks and local input. It can lie about what happened to messages you sent, so status from a peer is always labelled as reported. The receiver takes the host name from the paired key, so a peer can't pose as another host. It can still name any agent on its own host, so the agent part of the sender's name is only that peer's claim.

Secrets and privacy

  • PROPOSAL Keys stay in the per-machine state directory, never in the repo. MCP tokens never cross the link.
  • Message bodies are stored at the gateway and on the hosts involved, so anything an agent sends can be on three machines. The hosts have a 30-day limit today, and the gateway's retention is undecided.
  • Agents can paste secrets into messages. Nothing scans for that today.
  • Choosing the tailnet includes trusting its coordination service for this phase. Pairing is a second check, but it isn't a full defence if that trust fails.

10. Possible build order

This is not authorization to build. It applies if the user accepts this record, and each phase would need its own go-ahead. Testing and pushing remain under GR-3.
