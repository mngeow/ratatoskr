ARCHITECTURE DECISION RECORD 0003

Moving from rtk runtime to a daemon on each host

Why agents should stop living inside a terminal window, what that gives you, what it costs, and which choices are still yours.

1. Where this stands

The proposal: one long-lived rtk daemon on each machine owns the agents. The terminal window becomes something you attach to and close at will. The central gateway keeps its job from ADR-0002.

Why now: the goal, relayed from the user, is that each independent session should eventually spawn workers on its own to finish tasks. Today every agent lives and dies with one terminal window, which is a poor home for work that's meant to outlast your attention.

Who decides whatIn the proposal
Parent agentsPlan the work, delegate it, review the results and integrate them.
The daemonEnforces the permissions and capacity limits you chose. It makes no product decisions: it doesn't decide what work to do, or whether a result is good.
YouSet the limits and the permissions agents start with, and answer permission prompts, within the ceiling on workers. Nothing in this design answers a prompt for you.

Decided: your answers are in section 11, in your words. Still open: how to establish worker permissions, the loop budget and time limits, worktrees, how the daemon holds its processes, and a few smaller items, all listed in the same section. Remote dispatch is deferred. Building is authorized for the daemon transition only, and workers aren't part of it. Section 12 says what has been written so far.

2. The benefits

These five are the reason for the change. Each one is a design intent, and none has been built. Your decisions narrow the last three, and each panel says how. Select one to see today's behaviour beside the proposal.

Close the TUI without stopping your agents

Today

The TUI process owns the agents. Quitting it, or losing the terminal to a hangup, stops them all. That's why the README suggests tmux on a server. CODE internal/tui/model.go:19 App owns the processes internal/app/runtime.go:86 syscall.SIGHUP internal/app/runtime.go:284 closeAll(closeGrace, panes)

With a daemon

PROPOSAL Closing a window, or an SSH connection dropping, ends only that window. Agents keep running, and messages keep arriving through the same gate. You attach later and see the current screen.

Several windows share one host service

Today

One run per state directory. A second rtk is refused, and a run's panes appear only in its own window. CODE internal/store/store.go:77 acquireLock(filepath.Join

With a daemon

PROPOSAL Any number of windows can attach to one daemon, and each can show different sessions. Several can view one session, but only one may type into it at a time (section 7).

Workers stay tracked when their parent's window goes away

Today

There are no workers. A harness can start its own sub-processes, but rtk can't see them, and nothing records who started what.

With a daemon

PROPOSAL The daemon starts each worker and keeps its record: owner, task, working directory and outcome. If the parent's window closes, the parent and its workers carry on. USER If the parent's session ends, its workers are stopped, and the records stay readable. Section 5 has the details.

One place to limit how many workers run

Today

Nothing coordinates agents on a machine. If several sessions each spawned workers from separate foreground processes, none would see the others' load, or know that a worktree was already in use.

With a daemon

PROPOSAL All sessions on a host ask one daemon, so one limit applies to all of them. USER The first limit is a maximum worker count. This is an admission check rather than a scheduler: at the limit, the request is refused and the parent decides what to do. A single daemon is also where CPU, memory and worktree coordination could live later, but none of those is decided.

Dispatch work to another machine through the gateway

Today

An agent can message codex@ubuntu-b, but only if you've already started a runtime there, and it can't start anything new on that machine.

With a daemon

PROPOSAL A parent asks the gateway to pass a request to the target machine's daemon, which is always there to receive it. That daemon applies its own limits, and starts a worker or refuses. USER "Remote dispatch, will come back to it later". So this isn't part of the current design. It's kept here because a daemon is what would make it possible, and it carries a real risk.

4. What stays from ADR-0002, and what changes

ADR-0002 remains the record of its decisions, and this page doesn't rewrite them. It did leave this open: it lists a daemon split under "later, only if wanted", as a separate decision, and the contract lists it as out of scope.

Retained

  • A central gateway sees every Ratatoskr message, including between two agents on one machine. USER
  • If the other host is unreachable, the send fails immediately. No retry window, store-and-forward or replay. USER
  • Full message bodies in the ledger. USER
  • One rtk binary with different startup commands. USER
  • Tailnet or opt-in LAN, with pairing. No public gateway. USER
  • The result names, including the uncertain ones.
  • A new session never gets an older session's message.
  • The MCP and hook server stays on loopback.
  • Hosts dial out, and no PTY bytes cross the network.
  • The receiving host's gate decides when to paste.

Proposed to change

  • rtk runtime stops owning agents. It becomes an alias for rtk attach for a while. USER
  • "One host has one live run." A host would register and end sessions one at a time, rather than replacing them all. CODE internal/gateway/sessions.go:87 one host has one live run
  • The cap of 8 agents per host would become a daemon limit. CODE internal/gateway/sessions.go:29 maxAgentsPerHost = 8
  • "One terminal per host" becomes any number of windows per host.
  • The protocol changes for per-session registration, as a new version. Dispatch across machines is deferred, so it isn't part of this.
  • A new local socket between windows and the daemon, the first new local control surface since ADR-0001.

Who owns a worker

  • The owner session asked for it, receives its result by ordinary message, and may cancel it.
  • You can see and cancel any worker, and you answer its prompts. An answer doesn't lift its permissions above its parent's.
  • If the owner ends, its workers are stopped. USER "If owner ends, stop workers too". Ownership is never passed on. Any result already on its way ends session_gone, and isn't given to a new session, as ADR-0002 requires. The records stay readable.
  • What counts as the owner ending: its harness process ending, for any reason, or the daemon stopping it. What doesn't: closing a window, an SSH drop, or anything else that leaves the process running. PROPOSAL Nor does /clear or /compact, because the harness process continues.
  • Workers can't start workers. USER So the tree is one level deep.

7. Input: one writer, no double delivery, no automatic approval

Once several windows can see one session, "who is typing?" needs a real answer. Today the question can't come up, because only one TUI exists. This part is built. The user's report doesn't say whether they tried several windows. BUILT

One input owner per session

  • Any window may view a session. A window that attaches takes input for any session nobody holds, and views the rest. This changed during building: the first version of this record said new windows start as viewers, which would have made one window on its own press a key per session on every attach.
  • One window at a time holds input, and the daemon refuses viewers' keys, paste and mouse input.
  • Taking over is an explicit action, F6, and the previous holder sees that it happened.
  • The input holder's size sets the PTY's size, since a PTY has only one. Others show it as it is, cropped if needed.
  • A window closing releases its input, and nothing else gets it automatically.
  • The daemon, and only the daemon, applies today's draft rule to the holder's keys. CODE internal/router/deliver.go:19 func (r *Router) UserDraft

Only the daemon pastes

  • Delivery stays in the daemon: one gate, one record before each write. Windows never receive a message to paste, so ten windows can't paste it ten times. CODE internal/router/gate.go:61 func gate(in gateInput)
  • Windows get screen frames and status, as the TUI reads cached frames today. CODE internal/pane/pane.go:377 func (p *Pane) Snapshot()
  • A window reconnecting asks for the current frame. It isn't sent any messages again.

Permission prompts

  • The daemon never answers a prompt, and neither does the gateway or a parent agent. A worker can't get approval from its parent. No message or request type means "approve".
  • A waiting prompt appears as needs_approval in every window and in the worker list, so that a detached worker doesn't wait unseen. You attach, take input and answer, within the permission ceiling.
  • The cost: a worker that hits a prompt stops until you come. See section 7a.

7a. Worker permissions, and who may spawn

USER "A workers permissions will always be a subset of the parents permissions. Can be less, equal, but never more than the parent."

USER "Yes a parent should be able to spawn without asking". USER "Workers cannot start workers".

USER "A parent can decide what type of harness to launch. E.g. A claude code parent can launch a codex worker or a pi worker".

What these mean

  • Spawning needs no per-spawn approval. The spawn tool would be pre-approved for top-level sessions, as sending is today.
  • That approves the act of starting a worker, and nothing else. It raises no permission, answers no prompt, and doesn't allow nested spawning.
  • Workers don't get the tool, and the daemon refuses a spawn request from a worker's token, whatever its text says. PROPOSAL
  • The parent chooses the worker's harness, and it isn't limited to its own. The daemon starts the harness named, or refuses. It never substitutes another one.
  • Permissions can only narrow. A parent may start a worker with the same permissions or fewer.
  • The ceiling has no exceptions. That includes approvals at a worker's native permission prompt, even when you give them by hand. USER "never more than the parent".

What rtk can't honestly promise yet

  • It doesn't know a parent's effective permissions. They come mostly from your own harness settings, project settings and any "always allow" answers during the session. rtk adds only its hooks and its one tool. CODE internal/agent/claude.go:98 "--settings", settingsPath, internal/agent/codex.go:22 codexApprovalModeKey =
  • Each harness has its own permission model, so a parent's permissions don't carry over to a different harness by themselves. Each parent and worker pairing needs a reviewed mapping before "equal or less" means anything for it. A pairing without one is refused. OPEN
  • Pi isn't supported by rtk yet. Only Claude Code and Codex can be launched today, and Pi's permission model, MCP and hooks haven't been checked. UNVERIFIED CODE internal/agent/agent.go:39 exactly "claude" or "codex"
  • A different directory can mean different permissions, because project settings differ. Worktrees are undecided, so this is too.
  • Native prompts could exceed the ceiling. A harness's own prompt can offer more than the parent has, and rtk can't read what it asks or stop the answer. The ceiling already forbids this. The problem is only how to prevent or detect it. OPEN
  • Prompt text isn't enforcement. Telling a worker to stay within limits in its task limits nothing.

So the rule needs a mechanism, and it should fail closed: PROPOSAL if the daemon can't establish that a worker's permissions are within its parent's, it refuses the spawn with reason permissions. It doesn't start the worker and hope. That includes a configuration where a native prompt could approve more than the parent has and nothing can prevent or detect it. If no harness configuration can meet this, workers stay unavailable rather than the rule being relaxed. Until a mechanism exists, the rule is a requirement, not a property of the system. Section 11 has the open questions.

Choosing a harness is only that. This decision doesn't cover which model or provider a worker uses, which remains undecided. It also doesn't make a harness available: one that isn't installed or logged in on that host fails with a clear reason. PROPOSAL The daemon can check that a harness is installed before starting it. A login problem may only show after it starts, and that's recorded as the worker's outcome. UNVERIFIED

A limit that remains: agents run as you. A worker allowed to use a shell could also run a harness or reach the daemon's socket directly, which no tool list can prevent. The same goes for a harness's own built-in subagents, which rtk doesn't see. "Workers cannot start workers" is enforced for Ratatoskr's own route. Beyond that, it relies on the worker's permissions.

10. Costs and truth boundaries

A daemon crash doesn't preserve your agents. The daemon makes agents independent of the window, not of the daemon. Moving the processes into a service moves the single point of failure. It doesn't remove it.

New power means new ways to misuse it

  • The local socket is the main new risk. Whatever a window can do, anything running as you could do if it reaches that socket. That includes an agent with shell access, which could take input on another session and answer its permission prompt. That isn't possible through rtk today, because no such socket exists. File permissions keep out other users, but not your own agents. OPEN Hardening could include refusing connections from the daemon's own harness process trees and keeping risky actions out of the socket. Neither would be a real security boundary against an agent running as you.
  • If remote dispatch is built later, it raises the stakes of a compromised gateway. ADR-0002 accepts that one could inject prompts. With dispatch it could also start processes on a host. A list of allowed source hosts doesn't help here, because the gateway is what vouches for the source. So the real protection is the host's own opt-in, off by default. PROPOSAL
  • The same would apply to plain LAN HTTP. Anyone who can redirect that traffic could pose as the gateway. PROPOSAL Refuse remote dispatch on a plain HTTP pairing, with no override.
  • A hostile message could now lead to workers, not only persuade one agent, and because spawning needs no approval, no person sees it happen. The worker count limits how many start, and the parent's permissions limit what they can do. Those permissions are the real check, as they are today.
  • Not a boundary, as before: agents run as you, and can read each other's files. Separate directories would prevent accidents, not intent.

A service has to be installed, started and upgraded

  • Installation: something must start it. Running it by hand is simplest, but doesn't survive a reboot. launchd and systemd --user differ, and on a server a user service may need lingering enabled. UNVERIFIED
  • Environment: agents inherit the runtime's environment today. A service has a different PATH and environment, which could break finding or logging in to a harness. UNVERIFIED CODE internal/app/runtime.go:177 env: os.Environ()
  • Working directory: today it's wherever you ran the command, so each new session must now say where it runs. CODE internal/app/runtime.go:60 dir, err := os.Getwd()
  • Upgrading: restarting the daemon ends every agent on that machine, unless a handover is built. It should warn you, and it should refuse a window from a different build rather than guess.
  • Logs and a way to see what's wrong, because errors no longer appear in your terminal.

Agents that nobody is watching

  • Stopping with the owner has a price: when a parent crashes, its workers' unfinished work stops too, and is left partial. That's what you chose over leaving workers running with nobody responsible for them.
  • Cancelling is imperfect: stopping a worker sends the same signals as today, to its process group. Tools it moved to another group may survive, and its partial work stays.
  • The loop budget doesn't fit: today it resets only when a person presses Enter. Unattended workers would hit 20 and be held. It stays until you decide otherwise, because "no spending limits" doesn't remove it. CODE internal/router/deliver.go:45 r.used = 0 OPEN
  • Draft holds can last: if you detach with text half-typed, that session waits until you return.
  • Spending: USER "No spending limits at first". A worker limit bounds how many run, not what they cost, and a parent can start replacements as workers finish.

More states to recover from

  • Windows reconnecting: a new client protocol, version checks, slow clients that must not hold up the daemon, and frames that are dropped rather than queued.
  • Storage: worker and dispatch records need a schema change, and a backup, as ADR-0002's did.
  • Retention: the 30-day clean-up runs only at startup, and a daemon rarely starts. It would need a timer. CODE internal/app/runtime.go:102 st.Retain(ctx, now.Add(-retention))
  • Recovery: today's recovery assumes the whole run has ended, which stays true only while agents can't outlive the daemon. Crash survival would change that assumption.

What a daemon must not quietly change

  • No replay. Because a daemon is always running, it's tempting to hold messages for a session or a host. That would reverse a decision you made. USER "If other host is unreachable, fail immediately."
  • No dispatch queue, for the same reason. A task doesn't start later without a fresh request.
  • No inferred success. accepted still means only that the harness took the input, and completed is only the worker's claim.
  • No automatic retries of messages or tasks.
  • Plain rtk stays local only. USER It doesn't use the daemon or the gateway.

Built USER reported working, with one open bug
