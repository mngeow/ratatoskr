ARCHITECTURE DECISION RECORD 0008

OpenRig operator integration: the bridge is a participant-API adapter

How Ratatoskr sessions on other machines talk to one OpenRig seat, the main operator, and how that seat talks back, without Ratatoskr launching, owning or editing anything inside OpenRig. This revision is grounded in OpenRig's installed documentation and compiled daemon (version 0.7.7), read statically, and in the participant API that ADR-0007 now specifies and the repository implements. This is a design record. Nothing was built or run for it, and no OpenRig state was changed. The user's two decisions are marked USER; everything else is a PROPOSAL or an OPEN question.

1. Short answer

Is the bridge just a participant-API adapter? Yes. The gateway side of the bridge is already specified: pairing, one registered session, the long-poll inbox, acknowledgements and the six send results are in the spec. The only new design is the OpenRig side: how a message enters one OpenRig seat, and how that seat sends one out. PROPOSAL

OpenRig keeps everything it owns. OpenRig launches the operator, builds its tmux session, writes its MCP and hook configuration, types into its terminal and keeps its queues. The bridge never launches a harness, never edits a seat's configuration files, never types into tmux directly and never reads OpenRig's database. SOURCE S1 S5 S7 PROPOSAL

Decided shape. USER (2026-11-09) One Go program in a separate folder, integrations/openrig/, with a long-running sidecar supervised by the operating system's service manager (not by OpenRig) and a thin local client. Inbound text reaches the operator with rig send. The bridge refuses when the seat is not ready, reports only pasted, failed or unconfirmed, never retypes after an unknown outcome and never types after the 5-second acknowledgement window.

Still open: how the operator sends. OPEN The recommendation is a skill plus a local command, with no MCP server and no hook. Section 7 explains it from scratch, what it installs in OpenRig and what it does not, and how it compares with an MCP server.

A gateway message is not an OpenRig queue item. With rig send the bridge creates no row at all. A queue row (R2) is a documented alternative that the user did not choose (section 8).

One security fact shapes the design. The operator runs with full-access, no-approval launch flags. With no sender allow-list in v1 USER, text from any paired participant reaches it (section 10). SOURCE S7

2. Who owns what

OpenRig is a daemon that launches each agent as a tmux session (the kernel's operator is operator-agent@kernel, a Codex seat) and drives its terminal by pasting through tmux buffers. Herdr is the terminal workspace OpenRig opens views in when it is installed; OpenRig works with plain tmux without it. SOURCE S6 S7 S2 It follows that Ratatoskr never needs to touch Herdr: every byte that reaches the operator's terminal goes through an OpenRig verb. PROPOSAL UNVERIFIED that Herdr plays no part in launching a harness; the sources read show tmux as the session owner and Herdr as a viewer only.

Two products, the same words

OpenRig and Ratatoskr both have a "gateway" and a "participant", and they are unrelated. In this record "gateway" and "participant" mean Ratatoskr's unless prefixed "OpenRig". SOURCE S14 S9

What this means for the design

  • Transport needs neither MCP nor hooks. Inbound text is delivered by an OpenRig verb (a queue row, or rig send); outbound text is sent by a command the operator runs. The participant API itself requires neither (ADR-0007 section 3a). PROPOSAL
  • Hooks are out of the recommended v1 unless the user chooses otherwise. The bridge does not need hooks, because OpenRig already installs activity hooks in its seats and reports the result as agentActivity and sessionStatus in rig ps --nodes --json. The bridge reads that state instead of adding a second hook channel. SOURCE S3 S7 PROPOSAL
  • The recommended outbound tool is a skill plus a command, not an MCP server. A skill works for Claude and Codex alike, needs no approval gate and no global Codex edit. (OpenRig marks skill installation through a spec reliable; the v1 activation path is a walk, see section 7.) A shell command is something the operator already runs. PROPOSAL OPEN the user has not accepted it; section 7 explains it in full.
  • An MCP server remains possible later, as a spec fragment the owner selects, with the costs above (Claude's approval gate, Codex's global block, a relaunch, no way to confirm the tool loaded). It would wrap the same local client, so the sidecar and the contract do not change. PROPOSAL OPEN whether the user wants it.
  • Agreement with ADR-0007 section 3a. That section says an external harness's integration is the adapter's, and the gateway installs nothing in it. This record agrees and adds one precision: for an OpenRig-owned seat the adapter describes what it needs (a skill file, optionally a fragment) and OpenRig applies it; the bridge never writes .mcp.json, config.toml or settings.local.json itself. ADR-0007 is not revised. PROPOSAL

Packaging and language: accepted

USER (2026-11-09) accepted: a separate executable under integrations/openrig/; P3, a long-running sidecar plus a thin local client; Go. The reasons given earlier still describe it:

  • Separate executable. It is an external participant, so it does not live inside the rtk daemon, which owns managed sessions and their terminals. It speaks only the HTTP contract and imports nothing from internal/, so a bridge for another harness would look the same.
  • Long-running sidecar. The gateway treats a participant as online only while its poll is parked or was seen within 15 seconds, so an on-demand program could never receive. SOURCE S9 Sending needs only the credential, which is why the client stays thin and holds none.
  • One program, subcommands: setup (a guided wizard), serve, send, status, pair, and directory. Folder files: the program, a README, the skill source, and example service units that nothing applies.

Supervision: the operating system's service manager

USER (2026-11-09) The sidecar is started and restarted by the operating system's service manager (a launchd agent on macOS, a systemd user unit on Linux). It is not an OpenRig member, so no OpenRig topology, roster or rig spec changes. A runtime: terminal member was the alternative and is not chosen. SOURCE S5 S13

What that means for identity. The sidecar runs outside every seat, so OpenRig records nothing authenticated about who sent a message to the operator, and OpenRig's envelope shows an unknown sender (exactly what the operator sees is in section 5). SOURCE S7 USER accepted with the service-manager choice.

6. Inbound: Ratatoskr to the operator

Steps (the user's choice: rig send)

  1. The sender. A Ratatoskr session calls its send tool or the participant API to operator@openrig-main. The gateway authenticates the sender, writes the origin, checks the recipient is a current participant session and has a parked poll, and offers it. If the participant is not polling, the sender gets destination_unreachable at once; nothing is queued. SOURCE S9
  2. The offer. The sidecar's long poll returns the offer (id, gateway-written origin, body up to 64 KiB, optional reply_to). The sidecar has 5 seconds to acknowledge. SOURCE S9
  3. Ready check, and the not-ready refusal. The sidecar reads the seat's state (section 5). If it is not ready, it acknowledges saved:false with a reason, which the sender sees as session_gone plus that reason. Nothing is typed or held. Rate and size limits are applied here too (below).
  4. Journal, then acknowledge. If ready, it writes the offer to its journal (flushed to disk) and acknowledges saved:true inside the 5 seconds. The sender sees host_stored: the adapter has it. Not delivered, not read. SOURCE S9
  5. Type. Only if the acknowledgement was made inside the window, the sidecar runs rig send to the one configured seat with the rendered text. OpenRig pastes it through a tmux buffer and refuses to type into an interactive prompt or, where the seat's typing guard says so, over a draft. A busy Codex seat takes it into its running turn, where it "may redirect it". SOURCE S5 S6
  6. Report. A successful rig send is reported to the gateway as pasted, a failure as failed, an unknown outcome (timeout, killed command) as unconfirmed. accepted is never reported, because OpenRig gives no proof that the harness took typed text; its own sources say a wake "isn't proof that the seat claimed or finished the work". SOURCE S5 S9
  7. The operator acts. What it does is its own judgment under its own rules. If it needs another seat, it creates an ordinary OpenRig queue row, which Ratatoskr never sees. A reply is an explicit send (section 7).

The four rules that come with this choice. USER (1) Refuse when the seat is not ready. (2) Report pasted, failed or unconfirmed, never accepted. (3) Never retype after an unknown outcome: there is no retry identity that would make a second paste safe. (4) Never type after the 5-second acknowledgement window: an entry whose window passed without an acknowledgement is not typed, including after a sidecar restart.

The alternative that was not chosen: a queue row (R2)

Creating an OpenRig queue row instead would have typed only a 120-character sanitised pointer, made a claim the proof of pickup, and made a repeat safe by a retry id (section 8). USER The user chose rig send. R2 stays documented for a later change of mind.

7. Outbound and replies: the operator to Ratatoskr

  1. The operator runs the client. For example ratatoskr-openrig send --to codex@ubuntu --reply-to m-8c21 with the body on standard input. The skill the owner installs tells it the form and says to use it only for messages it intends to send. PROPOSAL
  2. The client hands the message to the sidecar over a Unix socket in the bridge's state directory (mode 0600, owned by the same user). It carries the destination, the body, the optional reply_to and a client-chosen message id; the client holds no gateway credential. PROPOSAL
  3. The sidecar sends with POST /participant/v1/messages as the registered operator session. The gateway answers 200 with one of six results, including host_stored (success), destination_unreachable, unknown_recipient (with the directory), session_gone, delivery_uncertain and gateway_uncertain. SOURCE S9
  4. The client prints the result word and the message id and exits non-zero unless the result is host_stored. The operator therefore knows what happened and says so honestly; it does not claim delivery from a stored result. PROPOSAL
  5. Retries are safe by id. The same id from the same sender "stores and offers once", so a client retrying after an unknown result reuses the id and cannot create a second message; gateway_uncertain is what a repeat of a send still in progress returns. SOURCE S9
  6. Replies. A reply is an ordinary send with reply_to set to the offer's id. The contract has no conversation object, so a "conversation" is only that field. A reply is delivered to the original sender's inbox like any message. SOURCE S9

The skill-plus-command option, explained (choice 2: OPEN)

The user asked for a clear explanation and has not accepted this yet. The rest of this record does not depend on the answer.

In plain words

The operator is an AI agent that already runs shell commands. To send a message to a Ratatoskr session it needs two things: to know that a command exists and how to use it, and the command itself. The skill is a short instruction file that tells it. The client is the command: a small program that hands the message to the sidecar. The sidecar, not the operator and not the client, holds the gateway credential and makes the network call. Nothing is added to the operator's tool list, nothing hooks into its turns, and none of OpenRig's configuration files change.

How a skill reaches an OpenRig seat (corrected 2026-11-09)

Correction. An earlier revision of this section said the owner could copy the skill into OpenRig's managed catalog and select it. That is not a dependable route: the catalog is a Git checkout, a skill folder with uncommitted or untracked content is skipped, and an uncommitted change in the catalog root makes the whole catalog unavailable. SOURCE S18 The section below replaces it.

  • What a skill is here. A directory with a SKILL.md. OpenRig keeps its own skill source in one managed catalog (skills.root, default $OPENRIG_HOME/skills) and refers to a skill by a stable id; a spec's uses.skills or a project's install.skills name catalog ids. SOURCE S16 S18 Where OpenRig puts a projected skill for the Codex operator is its own seat storage, ~/.openrig/state/seats/<rig id>/operator.agent/codex/skills/<id>. SOURCE S2 S17
  • The activation that works in v1: a walk, run by the user. rig walk operator-agent@kernel --through <absolute path>/SKILL.md delivers the file's text into the running conversation. It is a supported verb, it changes no OpenRig configuration and no file, and it is not persistent: it is lost when the conversation is replaced (a handover, a fresh launch, a compaction that drops it). The skill file itself stays in this repository, under integrations/openrig/skill/. The bridge never runs rig walk. SOURCE S1 S7 UNVERIFIED how Codex treats the walked text.
  • A persistent install is a documented gap. Options, none chosen: commit the skill into OpenRig's catalog checkout (an OpenRig-owned repository that upgrades may touch, and where an uncommitted change disables the whole catalog); put the instructions into the operator's startup guidance in its spec (changes an OpenRig spec); or walk the skill again after every fresh launch. OPEN the user's decision.
  • Does the walk change OpenRig's configuration? No. It adds text to one conversation. It does not touch the catalog, project.yaml, .mcp.json, Codex's config.toml, settings.local.json, hooks, plugins or topology. PROPOSAL

The client and the sidecar

  • The client is the same program as the sidecar run as ratatoskr-openrig send .... It reads the body from standard input, adds a message id of its own choosing, and writes the request to a Unix socket in the bridge's state directory (mode 0600, owned by the same user). It holds no gateway credential and makes no network call. PROPOSAL
  • The sidecar reads the request, checks the destination is a registered, well-formed address, and sends POST /participant/v1/messages with its participant credential, from set to its one registered session, the client's id, and reply_to if given. The same id from the same sender stores once, so a retry after an unknown result cannot create a second message. SOURCE S9
  • The client prints the gateway's result word and the message id and exits non-zero unless the result is host_stored, so the operator can report honestly. PROPOSAL

Both directions, end to end

  • Inbound. Gateway offers on the long poll; the sidecar checks the seat is ready, journals, acknowledges inside 5 seconds, then runs rig send; OpenRig types it into the operator's pane. SOURCE S9 S5
  • Outbound. Skill (read by the operator) leads it to run the command; the command passes the message over the socket to the sidecar; the sidecar posts it to the gateway; the gateway routes it to the managed session or participant and returns a result word, which travels back to the operator. SOURCE S9
  • Replies. A peer's reply is an ordinary send to operator@openrig-main with reply_to set: it arrives as inbound (above). The operator's reply to an inbound message is an outbound send with reply_to set to the offer's id. There is no conversation object in the contract. SOURCE S9

What OpenRig's own outside-agent recipes show

OpenRig documents, and says it trialled in both directions, how an outside agent reaches a seat: a composition of the official A2A SDK and the existing rig queue commands, "not a rig a2a command or a daemon endpoint". SOURCE S13 Ratatoskr's A2A work is deferred (ADR-0006); this is a precedent for the shape, not a dependency, and the bridge speaks no A2A.

  • An outside party never types into a pane. The inbound example front creates a queue row for a worker seat, the worker claims and closes it with a resolution, and the front returns that resolution to the outside client. SOURCE S13
  • Retry rules. "A timed-out write is uncertain: read its row and transitions before trying again. Do not silently send the task a second time", and a create can carry a retry id. This is the rule the bridge adopts. SOURCE S13 S7
  • No invented state mapping. "There is no one-to-one A2A/queue state mapping." The bridge likewise reports only what it observed: stored, and claimed. SOURCE S13
  • Identity. The recipes run rig in a seat's environment. SOURCE S13
  • Limits stated by OpenRig. The example keeps its task-to-row map in memory, binds loopback and supplies no public authentication, so it is "not an unauthenticated public gateway"; the trials used an OpenRig 0.7.0 candidate on Linux and did not exercise durable restart. The bridge journals durably, and none of this has been run on 0.7.7 here. SOURCE S13

10. Security

Recorded user decision (2026-11-09): no sender allow-list in v1. USER Any authenticated Ratatoskr participant may contact any registered session, consistent with ADR-0007 decision 7.

Consequence. Text from any paired participant reaches an operator seat that is launched with -s danger-full-access -a never (its next launch plan and its last observed launch arguments). SOURCE S7

What is left to enforce: (1) pairing and revocation: the owner decides who holds a credential, and a revoked one is refused within about 2 seconds; (2) the bridge's own size and rate limits and its not-ready refusal; (3) the owner's own launch permissions for the operator seat. The labelled provenance block is guidance to a model, not enforcement.

  • OpenRig's shared-channel precedent. OpenRig treats what unregistered people write in a Slack shared channel as correspondence: it can never answer, approve, deny or close anyone's ask (a request that tries is refused with answer_not_recorded), and the row ends with a labelled provenance block after the sender's words. Its policy text is "context, not enforcement". SOURCE S14 The bridge follows the pattern: text from Ratatoskr is correspondence, is never recorded as a person, and the bridge calls no answer, approve, resolve or close verb. PROPOSAL
  • The sender is the bridge's statement. OpenRig shows From: <unknown sender> for every message the sidecar types (section 5). SOURCE S7
  • Nothing bypasses OpenRig's gates. rig send still refuses to answer an approval or question prompt for another seat and obeys the typing guard; --dangerously-interact is never used. SOURCE S5 PROPOSAL
  • Credential hygiene. The gateway credential is a bearer secret in a mode 0600 file in the bridge's state directory, never in OpenRig's env: (which OpenRig says is not secret), never in the skill, never printed. SOURCE S2 PROPOSAL The operator can read files its user can read, so the client/sidecar split keeps the secret out of the places the operator is told to look; it is not a wall.
  • Transport. The participant API is HTTPS by default on a tailnet or LAN with the gateway's pinned certificate and plain HTTP only with an explicit flag; the bridge pins the certificate's SHA-256 on every connection. SOURCE S9 S10
  • Scope. One participant, one session, one destination seat. The bridge refuses to register or address anything else. PROPOSAL

12a. The setup TUI and the certificate pin

The user found two problems in the first scenario 8 guide: it did not say where the certificate pin comes from, and setup had too many manual steps. USER The lead's proposal, recorded here and specified in the bridge contract (sections 4.1 and 4.2), is a command ratatoskr-openrig setup. PROPOSAL Nothing has been run. UNVERIFIED

  • A guided Bubble Tea TUI. USER ground rule GR-2: any terminal UI is built with Bubble Tea (charm.land/bubbletea/v2 v2.1.1 and lipgloss v2.0.6; bubbles is not adopted because it needs module downloads the user has not approved). Command: ratatoskr-openrig setup [--config PATH] [--insecure-http]; exit 0 finished (items left for the owner are allowed), 1 failed or stopped, 2 not a terminal or bad configuration, 3 pairing uncertain. The user judged the first version hard to use, so it was redone around ordinary terminal conventions. SOURCE internal/setup/tui/model.go and components.go, via the lead; UNVERIFIED nothing was run or rendered.
  • What the screen shows. A header with the step number and a progress bar; a sidebar of the nine steps (done, current, to do, skipped, your turn: each with a word, never colour alone) that becomes a one-line strip on narrow terminals; a scrolling main pane; and a footer legend for the focused control. A terminal that is too small gets a message and keeps its state.
  • Controls. Tab, Shift+Tab and the arrow keys move focus; Left and Right move the cursor or flip a Yes/No; Space, y and n set a toggle; Enter goes to the next control or presses a button; Esc goes back one level, and at the top of a step opens the quit dialog; PgUp and PgDn scroll; ? opens the full help except inside a text field. There are no Ctrl-only paths. Forms have visible Back and Continue buttons, a blocked button shows its reason, and each field is validated as it is typed. Back never reopens an applied step.
  • Quitting. Ctrl+C or Esc at the top opens a dialog, Quit setup? Nothing more will be changed, with Stay focused. A running step finishes first. Ctrl+C quits at once only if nothing has been changed.
  • Pairing step. The owner chooses to paste the whole output block (recommended) or to enter the address, pin and code separately. The paste goes into a masked box that shows only a byte count, is read automatically when the closing line arrives, and keeps its buffer on a parse error. Only the address and the pin are shown back; the code appears as received. The engine (internal/setup) has no terminal I/O, and internal/setup/tui is the only package that imports Charm. pair --pair-code-file is the only non-TUI route.
  • Nine steps and their consents. Preflight; local OpenRig (check, default Yes); pairing material (keep and use, default Yes); config (write, default Yes, with a diff and a timestamped backup); pair (in memory); service on macOS (prepare and install default Yes; checkout, replace, start and restart default No); readiness (up to about 20 seconds); skill (replace and run default No; rig walk is not persistent); and a checklist ending scenario 8 round trip: pending user execution. It skips the service step, printing the foreground serve command, when not on macOS, inside a seat, over plain HTTP, or for a go run binary.
  • Honest limits. A pasted secret reaches the program as a Go string, so wiping every copy from memory is best effort (the TUI itself keeps secrets in wipeable byte buffers and shows byte counts only). Whether a bracketed paste survives Herdr and tmux is unverified, and no interactive behaviour has been run or rendered. golang.org/x/sys is an indirect dependency through Charm, so adding a dependency is no longer the cost of the open macOS socket-check decision.
  • One paste instead of three values. The owner runs rtk gateway participant pair openrig-main on the gateway host and pastes the whole output block once, with echo off. The wizard takes the code, the participant API address and the certificate pin from it, shows back only the address and the pin, and prints pairing code: received. The code never reaches a file, the command line, the environment or a log.
  • Nine steps: preflight, local OpenRig, pairing material, config, pair, service (macOS launch agent, with a yes before launchctl bootstrap), readiness, skill (rig walk, not persistent), and a finish checklist. The scenario 8 round trip stays pending user execution.
  • The pin rule. The value to use is the certificate SHA-256 line, written sha256: followed by 64 lowercase hex digits. It is never the key pin line (sha256// followed by base64): that is a rule for clients that pin only a public key, and this bridge pins the certificate and refuses it. Over plain HTTP no pin is printed. SOURCE internal/gateway/participant_admin.go, internal/gateway/fingerprint.go
  • What it does not change. No OpenRig file, seat, MCP or hook configuration is written, and no OpenRig session is started or stopped. The manual steps remain the fallback.
