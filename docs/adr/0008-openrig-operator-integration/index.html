ARCHITECTURE DECISION RECORD 0008

OpenRig operator integration: one network identity, nothing else moves

A proposal for letting Ratatoskr sessions on other machines talk to one OpenRig seat, the main operator, through the gateway. The contract between the gateway and the bridge is not decided. The user has chosen a direction for it, a separate HTTP+JSON participant API on the gateway (option W2 in ADR-0007), but that record is still a proposal and reachability, TLS, authentication, identifiers and inbound delivery are open. The A2A protocol that an earlier draft assumed is deferred (deferral record), and this page does not replace it with another one. OpenRig keeps its teams, its seat lifecycle, its terminals and its durable queues. This is a proposal only. No code was written, nothing was run, no OpenRig command was tried, and the page has not been opened in a browser.

1. Short answer

Only the operator is exposed. One OpenRig seat, the main operator, gets a network identity that Ratatoskr sessions on any paired host can reach. No other seat, pod or rig is registered. OpenRig still launches, restarts, supervises and tears down its seats, and still owns its terminals, teams and queues. USER

A small bridge, not an import. A bridge on the operator's machine speaks the gateway's participant interface (direction chosen by the user: a separate HTTP+JSON API, ADR-0007; the contract itself is OPEN). Inbound, it hands a message to the exact current operator through a supported OpenRig delivery. Outbound, it lets the operator send and report through a tool or command. It never starts a harness, never copies OpenRig topology, and never treats the sender field of a message as proof of identity. PROPOSAL

A message is not a queue item. A message that crosses the gateway lives in the gateway. An OpenRig queue row lives in OpenRig. The operator may create a queue row because of a message; the bridge does not, and the two are never the same record. PROPOSAL

Today. The operator is an ordinary OpenRig seat, reached by rig send and queue rows from other OpenRig seats. Ratatoskr's gateway knows nothing about it: the custom send tool addresses Ratatoskr sessions on paired hosts only (internal/server/mcp.go). A Ratatoskr session on another machine therefore cannot reach the operator, and the operator cannot reach it, except by a human relaying.

3. The bridge

Where it lives and who it is

Recommendation. The bridge is an externally managed participant (an idea first written in the deferred ADR-0006 section 5a, kept as a record, not as a requirement): a separate process or package maintained near OpenRig (an optional integrations/openrig folder is acceptable), with a stable participant id, its own scoped, independently revocable credential, and no Ratatoskr daemon, terminal, hooks or MCP on the OpenRig side. It is not a session of a Ratatoskr host: host delegation is a trust boundary for managed hosts only, and the host pairing key is not reused for it. The gateway never depends on OpenRig's internals; the bridge is the only piece that knows them. In the terms of ADR-0007 the bridge would be an OpenRig adapter; if that record is not accepted, this boundary stands and only the wire sections change. PROPOSAL An earlier draft of this page made the operator a session of its host through the daemon; that is withdrawn. The owner enrols exactly one participant for the operator; the bridge refuses to register any other seat. OPEN how the enrolment is done, and by which interface.

Inbound: Ratatoskr to the operator

  • The gateway routes a message to the operator's endpoint and sends it to the bridge over a mechanism that is OPEN (polling, long-polling, a stream or a push to a URL; ADR-0007): not chosen, not designed, and not authorised to be built. (Candidates such as a registered URL or an outbound connector were discussed under the deferred ADR-0006; none is adopted here.)
  • The bridge delivers it with a supported OpenRig verb, to the exact current operator session, never to a name that could mean a replacement: a short message through rig send, shown with a header the gateway wrote ("from codex@ubuntu, verified by the gateway, task T1"). The body's own from is ignored. UNVERIFIED that rig send reaches the intended occupant reliably, handles long or multi-line bodies, or reports success truthfully.
  • Delivery is reported truthfully: the gateway may say a message was handed to the bridge, and the bridge may say it was delivered, only when each has confirmed it. A result exists only if the operator explicitly sends one. If the delivery command's outcome is unknown, that is said and the delivery is not retried.

Outbound: the operator to Ratatoskr

  • A tool or command the operator can call to send a message or an answer. Name, form and wire are OPEN. Who owns any local MCP tool server or hook the operator's harness would use is the adapter's, not the gateway's (a recommendation, ADR-0007 section 3a); which local form suits OpenRig is open.
  • The operator's own credential never leaves the bridge's side of the machine, and the gateway, not the operator's text, sets the origin of everything it forwards.

No double ownership

The operator's harness is owned by OpenRig. No Ratatoskr daemon launches, pairs, supervises or pastes into it as a managed session, and the bridge must not start a second copy. If both an OpenRig occupant and a daemon-managed session claimed the name, the gateway would see two participants for one seat; the one-participant rule above prevents that.

5. Limits to state plainly

  • Correlation lives in the bridge. It keeps a table of gateway message id to the delivery it made and to any queue row the operator says it created. Neither OpenRig nor the gateway knows the other's ids. Lose the table and a late reply cannot be matched; it is then reported as unmatched, not guessed.
  • Cancellation cannot stop OpenRig work. A cancel request, if the chosen interface has one, can only tell the operator; it cannot undo what the operator already started.
  • A queue result is not a reply. A queue row closing in OpenRig does not answer the sender. Only the operator's explicit message does.
  • Restart and replacement. The operator participant keeps its stable id across an OpenRig restart. Open conversations follow a policy the owner declares (suggested default: they end, with a reason), and nothing is moved to the new occupant silently.
  • Stale. If the gateway cannot reach the bridge, it marks the operator unreachable; new messages fail immediately and are not queued for later.
  • Trust. The gateway proves which host and session sent a message; it cannot prove the operator will act wisely on it. OpenRig's own gates and permission prompts are unchanged and not bypassed. Text from another machine is treated as untrusted input by the operator, like any message.
