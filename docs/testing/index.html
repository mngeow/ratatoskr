Overview

Testing the daemon by hand

Three setups, simplest first, then the Network tab. Start with the first: if something fails there, the network isn't the cause.

Changed on this branch (ADR-0009 D14 to D20: implemented, untested). rtk gateway now listens on 0.0.0.0 by default, and port 7777 (the host protocol and the new dashboard at /ui/) is plain HTTP unless --https. The participant API on 7790 stays HTTPS unless --participant-insecure-http. The retired flags (rtk gateway --allow-lan and --insecure-http, --participant-allow-lan, and rtk runtime pair --insecure-http) are still accepted for one release with a warning, and change nothing. So the commands on this page still work, but a command that relied on --allow-lan alone for HTTPS is now plain HTTP: add --https. Anything that can reach these ports can read them, and the dashboard has no login: firewalling is the exposure boundary.
The owner reports that the daemon works, with one open bug: text appears in the prompt box after an answer, and the cause is unknown. That report doesn't say which scenarios it covered, and the team may not run anything (GR-3). Every expected result here comes from reading the code, not from seeing it work, so tell the team when something differs.

Rules that apply to every scenario

  • State is per XDG_STATE_HOME. One directory has one daemon, one pairing and at most one claude and one codex. Commands only find a daemon when that variable matches, so a surprising no daemon is running usually means a terminal is missing its export lines.
  • Starting is always explicit. rtk attach and rtk runtime never start a daemon, and --agents is what starts agents. Without it, rtk attach only joins what's running.
  • Two separate version checks. Between machines: the gateway checks only protocol 2, and refuses older runtimes, so a gateway and daemons from different builds can work together if they speak it. On one machine: a window must exactly match its own daemon's build. If it doesn't, stop the daemon with rtk daemon stop, which works across builds, and start it again.
  • Use one explicit build identifier. Build with -X main.version= and a name you choose, and use a new name for each rebuild. Without one, every build is called dev, and the window check can't tell them apart.
  • In a window: F10 detaches, Ctrl+C goes to the agent if you hold input (a second press within a second detaches, and for a viewer the first press does), F6 takes input, F1 and F2 change focus, F3 opens the log, and F4 delivers held messages.
  • The promise is limited. Agents should survive a closed window or a dropped SSH connection. A reboot ends them, macOS logout is unknown, and after a crash nothing resumes. If a daemon crashes, check for leftover harness processes yourself.
  • The gateway also serves the participant API (scenario 7) on port 7790 of its --listen IP, unless you add --participant-listen off. Pick a host port other than 7790.
  • Not included: workers, a Pi agent, service setup, and attaching across the network. A window always runs on the machine with the daemon.
  • Please send the team: what differed, the relevant lines of daemon.log (rtk daemon status names it), and whether Codex asked about hooks. Don't paste credentials or pairing.json.

Scenario 1: everything on one Mac

A gateway and two daemons on one Mac, with two copies of each harness. Each daemon pretends to be a machine, so this exercises real cross-machine messaging over loopback, with no network to go wrong.

One message, step by step

  1. Claude calls ratatoskr_send. The call goes to its own daemon over loopback, using MCP. The agent sees only the result.
  2. The daemon sends to the gateway. If there's no connection, it fails straight away with gateway_unreachable. Nothing is queued.
  3. The gateway records it. The full text goes in the ledger, then it offers the message once on the recipient's stream. If that machine isn't connected, the result is destination_unreachable.
  4. The recipient's daemon stores it and acknowledges. The sender gets host_stored. If the session has ended, it gets session_gone.
  5. The delivery gate pastes it when safe. It waits while the agent is busy, at a prompt or has a draft, and it pastes with no window open. Only the daemon pastes, so more windows can't mean more pastes.
  6. The result flows back to the ledger. accepted means the harness took the input, not that the model read it. Nothing is ever resent.

2. LAN, plain HTTP

Scenario 2: across machines on a LAN, plain HTTP

A gateway on one Ubuntu VM, a daemon on a second, and a daemon on your Mac, all talking in the clear over your LAN.

Plain HTTP is readable on this network. Anyone who can see the traffic can read messages, the pairing code and the credential, and anyone who can redirect it can inject messages into your agents. Use it only on a LAN you trust. If you take the Mac elsewhere, stop its daemon first, because it keeps trying to reach this address and would send its credential to whatever answers.

3. Tailnet

Scenario 3: across machines on a tailnet

The same three machines, connected by Tailscale instead of your LAN.

This page can't test HTTPS on a tailnet, because rtk doesn't support it

You asked for tailnet and HTTPS. The code refuses that combination, so this page doesn't pretend otherwise.

AddressGateway flagsTraffic between rtk and the gatewayStatus
TailscalenonePlain HTTP, inside Tailscale's WireGuard tunnelSupported. The steps below
Tailscale--allow-lan, or --fingerprint when pairingPinned HTTPSRefused. PlanListen and planTransport allow these on LAN addresses only
Private LAN--allow-lanPinned HTTPSSupported. HTTPS on a LAN

What Tailscale gives you instead. WireGuard encrypts traffic between tailnet devices, so this isn't readable on the network. But it isn't HTTPS: nothing checks the gateway's certificate, and encryption depends on that address really being Tailscale. Any device your tailnet policy allows can reach the port, though it can't do anything without pairing.

What it would take to add. A small product change: an explicit gateway opt-in for HTTPS on a Tailscale address, and letting --fingerprint through for that class in both flag tables. The pinning, certificate and pairing code already exist and don't depend on the address class. It also changes a recorded decision in ADR-0002, so it's your decision, and nothing has been changed.

Tailscale's own tailscale serve HTTPS doesn't help today: rtk accepts IP addresses only, not hostnames, and trusts only a pinned certificate. Reaching a LAN gateway through a subnet router should work with the LAN HTTPS mode, but it hasn't been checked, it needs tailnet settings this guide doesn't change, and on one LAN the traffic may bypass Tailscale altogether.

3Pair VM-B and the participant

A second owner terminal on VM-A.

Expect the vmb pairing line, exactly as in scenario 2 or 3. For the participant, the command prints one block; over HTTPS it looks like this (everything in angle brackets is a placeholder — the only real values are the ones your terminal prints):

The first line is the one-time code, alone on its line. Copy the certificate value whole, including the sha256: prefix. The value on the line labelled certificate SHA-256 (the pin to use when your TLS library can pin a certificate) takes the form sha256: followed by 64 lowercase hex characters: it is the certificate's DER SHA-256 fingerprint. That whole value — prefix included — is what S8_CERT_PIN above and the config's certificate_sha256 take, and it is the pin the bridge compares against the peer certificate. The parser also accepts 64 bare hex digits, but the value to copy and use is the prefixed one from this line.

The next line is a different rule and is not that value. The line labelled key pin (a different rule, for clients that can pin only a public key) carries sha256// and base64: it is a key pin, it is not the config value, and the bridge refuses it if you put it in certificate_sha256. Use the certificate SHA-256 for the config; the key pin is for clients that can pin only a public key, and this bridge is not one of those.

Expect

  • A vmb pairing line, exactly as in scenario 2 or 3.
  • For the participant: the block above, with a single-use code valid 10 minutes, the participant API URL (https:// and port 7790) and the two pins.
  • The certificate value must come from this terminal, not from a remote tool or a preflight request.
  • The code is shown once. Write it to the code file on the Mac in step 7; it never goes in argv or the environment.
  • On a re-pair (the participant already exists and is not revoked) the command adds one line, between the expiry line and the API line: this is a rotation: redeeming the code replaces the credential and ends this participant's open sessions. The old credential stops working when the new code is redeemed.
  • Over plain HTTP there is no certificate pin at all. The two pin lines are not printed; where the listener needed the explicit opt-in, the gateway's own warning takes their place, so there is nothing to copy: WARNING: the participant API is served over plain HTTP. The bearer credential, the pairing code and message bodies are readable by anything on the network path, and messages can be injected. A loopback listener, where plain HTTP needs no opt-in, prints nothing in their place. Either way certificate_sha256 must be unset: no certificate pin may be set for a plain-HTTP URL.
  • The participant API may be http:// as well as https://. Paste whichever address the gateway prints on its participant API: line; nothing asks you to type a flag into a field. This scenario's primary path stays HTTPS, and an http:// gateway needs one explicit consent in setup: on the review screen, directly above Use these values?, Accept plain HTTP for this gateway? (not encrypted) starts at No and lists the reason - nothing is encrypted, so anything on the network path can read the pairing code, the credential and every message. Continuing with it at No does not fail the step: the wizard stays on the review with the gateway's explanation and applies nothing. Choosing Yes lets setup use the address, the bridge must then run with --insecure-http, and the launchd step is skipped. setup --insecure-http remains an optional way to accept plain HTTP for the whole run in advance. Leave the certificate pin empty for http://: there is nothing to pin, and a pin typed by mistake is refused.

Optional: a plain-HTTP participant listener

Not the primary path, not recommended, and not exercised by anyone. Two different flags are involved and they are not interchangeable: --insecure-http on rtk gateway makes the host protocol plain and does not touch the participant API; --participant-insecure-http is the one that changes the pairing block, and the gateway then warns that the credential and every message are readable on the network path.

Expect

  • The participant listener line says the transport is plain, followed by the gateway's plain-HTTP warning.
  • Pair with the flag that asks for a plain block: rtk gateway participant pair openrig-main --insecure-http. The block then carries an http:// address and no certificate pin lines, because there is no certificate to pin.

11When it refuses, stops or is uncertain

Expect

  • Exit 0: stored by the other side. Say "it was stored", not "it arrived".
  • Exit 1: definitely not done. The gateway refused it or decided it was not delivered, or it was provably not sent. Say so.
  • Exit 2: your own arguments, config or files. Nothing was sent.
  • Exit 3: uncertain: it may have been stored. Do not resend under a new id; check first, and only ever retry with the same --id.
  • Exit 4: another poll replaced this one. This is the sidecar's result, not a send's; the sidecar records stopped.json and stops.
  • Exit 5: the credential is revoked or unknown. The sidecar records stopped.json and stops; sends cannot arrive.
  • Exit 6: the sidecar is not reachable on its socket. Nothing was sent. Tell the owner; do not start or repair it from a seat.
  • An offer refused (the operator side reports a refusal) means the seat was not ready, the bridge was busy, the journal was unavailable, or a size or rate limit was hit. Nothing was pasted. The sender sees it as a refusal, never as delivery.

The sidecar survives transient failures by backing off (1, 2, 4, 8, 16, then 30 seconds, capping at 30); a pin mismatch backs off much longer and is logged loudly. A sidecar that exits 4 or 5 stays stopped by design: the marker makes the next start exit 0.
