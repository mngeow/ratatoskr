Overview

Testing the daemon by hand

Three setups, simplest first, then the Network tab. Start with the first: if something fails there, the network isn't the cause.

The owner reports that the daemon works, with one open bug: text appears in the prompt box after an answer, and the cause is unknown. That report doesn't say which scenarios it covered, and the team may not run anything (GR-3). Every expected result here comes from reading the code, not from seeing it work, so tell the team when something differs.

Rules that apply to every scenario

  • State is per XDG_STATE_HOME. One directory has one daemon, one pairing and at most one claude and one codex. Commands only find a daemon when that variable matches, so a surprising no daemon is running usually means a terminal is missing its export lines.
  • Starting is always explicit. rtk attach and rtk runtime never start a daemon, and --agents is what starts agents. Without it, rtk attach only joins what's running.
  • Two separate version checks. Between machines: the gateway checks only protocol 2, and refuses older runtimes, so a gateway and daemons from different builds can work together if they speak it. On one machine: a window must exactly match its own daemon's build. If it doesn't, stop the daemon with rtk daemon stop, which works across builds, and start it again.
  • Use one explicit build identifier. Build with -X main.version= and a name you choose, and use a new name for each rebuild. Without one, every build is called dev, and the window check can't tell them apart.
  • In a window: F10 detaches, Ctrl+C goes to the agent if you hold input (a second press within a second detaches, and for a viewer the first press does), F6 takes input, F1 and F2 change focus, F3 opens the log, and F4 delivers held messages.
  • The promise is limited. Agents should survive a closed window or a dropped SSH connection. A reboot ends them, macOS logout is unknown, and after a crash nothing resumes. If a daemon crashes, check for leftover harness processes yourself.
  • Not included: workers, a Pi agent, service setup, and attaching across the network. A window always runs on the machine with the daemon.
  • Please send the team: what differed, the relevant lines of daemon.log (rtk daemon status names it), and whether Codex asked about hooks. Don't paste credentials or pairing.json.

1. One Mac

Scenario 1: everything on one Mac

A gateway and two daemons on one Mac, with two copies of each harness. Each daemon pretends to be a machine, so this exercises real cross-machine messaging over loopback, with no network to go wrong.

One message, step by step

  1. Claude calls ratatoskr_send. The call goes to its own daemon over loopback, using MCP. The agent sees only the result.
  2. The daemon sends to the gateway. If there's no connection, it fails straight away with gateway_unreachable. Nothing is queued.
  3. The gateway records it. The full text goes in the ledger, then it offers the message once on the recipient's stream. If that machine isn't connected, the result is destination_unreachable.
  4. The recipient's daemon stores it and acknowledges. The sender gets host_stored. If the session has ended, it gets session_gone.
  5. The delivery gate pastes it when safe. It waits while the agent is busy, at a prompt or has a draft, and it pastes with no window open. Only the daemon pastes, so more windows can't mean more pastes.
  6. The result flows back to the ledger. accepted means the harness took the input, not that the model read it. Nothing is ever resent.

1Open five terminals

Use ordinary terminal windows or tabs, not a pane that belongs to OpenRig or another tool. Name them so you can follow along. Each one needs its own lines below, because the state directory is what makes it a separate machine. A command run without them talks to your normal state directory.

Your usual ~/.local/state/ratatoskr and ~/.local/bin/rtk stay untouched, because everything lives under ~/rtk-test.

2Build, and make the working directories

Each agent gets its own directory, so that no two can overwrite each other's files. Replace <BUILD_ID> with one identifier you choose.

Expect

  • rtk --version prints rtk and your build identifier, not dev.

Choose a new identifier every time you rebuild, such as daemon-test-2. It's how a window tells that a daemon came from a different build, and two builds with one identifier look identical.

Port 7791 is only for this guide. If something else is using it, pick another and use it throughout.

5Start both daemons

Expect

  • daemon started (pid N), the log path, and harnesses will inherit the environment of this terminal.
  • rtk daemon status shows link: connected, windows: 0 and sessions: none. If the link isn't connected yet, run it again.
  • rtk gateway hosts shows alpha and beta as live.

6Start four agents

Start each one from its own directory. F10 detaches and leaves the agent running, so the last rtk attach shows both. Answer any trust or hook-review questions in the pane. Each Codex launch costs one model turn, and these are real agents using your logins.

Expect

  • Press F10 after each of the first two commands in each terminal. It prints detached; the agents keep running (rtk attach returns to them, rtk daemon stop ends them).
  • Both panes appear, with headers starting INPUT HOLDER. The title says Gateway connected.
  • A window only shows sessions that existed when it attached, which is why the last rtk attach comes after both have started.

You can't run two of one harness in a single daemon. Names are fixed as claude and codex, and --agents claude,claude is refused as a duplicate. A second identity is the only way to get a second copy.

7Send messages between them

Type these into the panes. They're prompts for the agents, not shell commands.

Expect

  • The message appears in the recipient's pane, and the reply comes back. accepted means the harness took it, not that the model read it.
  • F3 in a window shows received messages, and Tab shows what this identity sent.
  • Each message appears in rtk gateway log. To see one in full, run rtk gateway show ID.
  • A bare codex only means the agent on the sender's own identity. Other identities need the full name@host.

8Try several windows

Expect

  • Both headers in T5 say VIEWER. Typing doesn't reach the agent.
  • F6 in T5 takes input for the focused pane. It becomes INPUT HOLDER, and the same pane in T3 becomes VIEWER.
  • Ctrl+C in a VIEWER pane detaches that window at once, and the agents keep running.
  • Press F10 in T5, then run rtk daemon status there. The session T5 held shows no holder, and T3 stays a viewer of it until you press F6 in T3.

9Close the window: the point of this work

Close the T3 terminal window while attached. Open a new one, and give it the T3 lines again.

Expect

  • rtk daemon status still lists claude and codex.
  • rtk attach shows the same agents on their current screens.
  • Detach, ask an agent in T4 to message claude@alpha while no alpha window is open, then attach again. The message arrived or is held, and F3 shows it.

10Check the failure cases

Keep T3 attached, so that you can type into its Claude pane. Detach T4 with F10. T5 should be at a shell prompt from the last step. Run these one at a time.

Expect

  • Stopping codex on beta prints session ended: codex, and claude@beta keeps running.
  • The send to codex@beta gets session_gone.
  • The new codex@beta is a new session and never gets the earlier message. Note whether Codex asks to review its hooks again. It may ask once for each state directory, and shouldn't ask on later starts.
  • The send to nobody@beta gets unknown_recipient, with a list of known agents.
  • --agents claude,claude is refused with duplicate agent.
  • Plain rtk under alpha's state is refused: another ratatoskr is already running.

11Stop and restart the gateway

Press Ctrl+C in T1, watch a window, then start it again.

Expect

  • With the gateway down, the title says Gateway reconnecting — sends unavailable, the agents keep running, and a send returns gateway_unreachable.
  • After the restart the title returns to Gateway connected. The failed message doesn't arrive, because nothing is resent.

12Stop, restart, clean up

Detach T3 and T4 first. Stop T1 with Ctrl+C before the last command. The rm removes only this scenario's folder, including its messages and test credentials, so leave it out if you want to look through them. The test binary stays in ~/rtk-test/bin.

Expect

  • rtk daemon stop lists the agents and refuses without --yes.
  • --yes prints daemon stopped once the process has gone, with no agent left running. If it says still finishing its shutdown, tell the team.
  • The restarted Claude is a new session, with no memory of the last one and no old messages. If rtk attach says the gateway has not been reached yet, the daemon has only just started: run it again.
  • Your Claude and Codex logins stay as they were. Codex may keep its records of trusted hooks for these paths.

2. LAN, plain HTTP

Scenario 2: across machines on a LAN, plain HTTP

A gateway on one Ubuntu VM, a daemon on a second, and a daemon on your Mac, all talking in the clear over your LAN.

Plain HTTP is readable on this network. Anyone who can see the traffic can read messages, the pairing code and the credential, and anyone who can redirect it can inject messages into your agents. Use it only on a LAN you trust. If you take the Mac elsewhere, stop its daemon first, because it keeps trying to reach this address and would send its credential to whatever answers.

3. Tailnet

Scenario 3: across machines on a tailnet

The same three machines, connected by Tailscale instead of your LAN.

This page can't test HTTPS on a tailnet, because rtk doesn't support it

You asked for tailnet and HTTPS. The code refuses that combination, so this page doesn't pretend otherwise.

AddressGateway flagsTraffic between rtk and the gatewayStatus
TailscalenonePlain HTTP, inside Tailscale's WireGuard tunnelSupported. The steps below
Tailscale--allow-lan, or --fingerprint when pairingPinned HTTPSRefused. PlanListen and planTransport allow these on LAN addresses only
Private LAN--allow-lanPinned HTTPSSupported. HTTPS on a LAN

What Tailscale gives you instead. WireGuard encrypts traffic between tailnet devices, so this isn't readable on the network. But it isn't HTTPS: nothing checks the gateway's certificate, and encryption depends on that address really being Tailscale. Any device your tailnet policy allows can reach the port, though it can't do anything without pairing.

What it would take to add. A small product change: an explicit gateway opt-in for HTTPS on a Tailscale address, and letting --fingerprint through for that class in both flag tables. The pinning, certificate and pairing code already exist and don't depend on the address class. It also changes a recorded decision in ADR-0002, so it's your decision, and nothing has been changed.

Tailscale's own tailscale serve HTTPS doesn't help today: rtk accepts IP addresses only, not hostnames, and trusts only a pinned certificate. Reaching a LAN gateway through a subnet router should work with the LAN HTTPS mode, but it hasn't been checked, it needs tailnet settings this guide doesn't change, and on one LAN the traffic may bypass Tailscale altogether.

  • This is the adapter's card. The gateway serves a different card for each participant it hosts.

7Enrol and register the adapter

Enrolment is an owner action on the gateway host. Both secrets are printed once: the enrolment credential (what refbot would use to call the gateway) and, at registration, the outbound secret (what the gateway sends to the adapter).

Expect

  • enrol prints the participant name and a credential, and says it cannot be recovered. Copy it into the CRED field above.
  • register fetches the adapter's card, checks that it declares an HTTP Bearer scheme, mints the outbound secret, prints it once and prints registered refbot at .... Paste that secret into the token file (the adapter re-reads it on every request, so no restart is needed). Registering again mints a new secret and the old one stops working.
  • list shows refbot as active, its URL, and an AUTH column of bearer. A card that declares no security is refused unless you pass --no-auth, which warns loudly and shows NONE. A card that needs OAuth2, OpenID Connect, mutual TLS or an API key is refused. A plain-HTTP LAN address is refused unless you add --insecure-http, and then a warning says the secret and every task cross that network in the clear; https needs --fingerprint; loopback and tailnet addresses need neither.
  • The secret never appears in list, in --json output, in any log, or in any error text. Check that.

register also refuses a public address, a hostname, a redirect and an oversize card. Try a wrong port once and read the refusal.

8Find a session id and its endpoint

The endpoint of a managed session is its session id.

Expect

  • Each session shows its id. Put the Codex on VM-B id in SESSION_ID above.
  • The public card for that session names a JSONRPC interface at /a2a/agents/<id> and a bearer security scheme. Reading it needs no credential and gives no permission.
  • A name that matches more than one live session is refused with the candidates, rather than guessed. (Optional: scenario 1's layout makes two sessions of one harness.)

9The first round trip: ask, clarify, answer, result

You drive it from the two panes. The first prompt goes to Claude on the Mac.

Expect

  • Claude calls ratatoskr_task_send and prints a task id at once; the call does not wait for Codex. Put it in TASK_ID above.
  • Codex's pane receives a labelled prompt: from claude@mac, verified by the gateway, with the sender's text quoted between marker lines.
  • Codex calls ratatoskr_task_report with input_required. Claude's pane is woken (through the normal readiness gates) with a short "needs input" note, not only a database row. ratatoskr_task_get shows INPUT_REQUIRED and the question.
  • Claude answers with ratatoskr_task_send using the task id; Codex receives the answer, reports completed with a result, and Claude is woken again. ratatoskr_task_get shows COMPLETED and the result.
  • The task became WORKING only after Codex's harness accepted the prompt. A turn ending without a report does not complete it. Write down anything that differs.

The three task tools are ratatoskr_task_send, ratatoskr_task_get and ratatoskr_task_report. ratatoskr_send is unchanged.

10Authentication, forgery and scoping, with curl

These talk to the endpoint directly, as a standard client would. The JSON shapes follow the A2A v1.0 spec but have not been checked against the running server.

Expect

  • No credential: HTTP 401 with WWW-Authenticate: Bearer realm="a2a". A wrong credential is also refused.
  • With refbot's credential the message is accepted and Codex's pane shows it from ext:refbot, verified by the gateway. The from you put in the body is ignored: the origin is the authenticated principal.
  • refbot has no permission to read the task from the first round trip: GetTask returns a not-found error (-32001), exactly as for a task that does not exist. Its ListTasks omits it too.
  • Enrolment is not a grant: refbot can message any session, but it can read only tasks it is party to.
  • ListTasks returns totalSize as the number of tasks refbot may see before pagination, newest first (by last update), with nextPageToken always present and empty on the last page.

11Refusals the standard requires

Each should answer with the spec's own error, not silence.

Expect

  • A wrong or empty A2A-Version gives VersionNotSupportedError (-32009).
  • SendStreamingMessage, SubscribeToTask and the extended card give UnsupportedOperationError (-32004); the push-config methods give PushNotificationNotSupportedError (-32003).
  • CancelTask on a task that is still working gives TaskNotCancelableError (-32002). No canceled state, no interrupt. An unknown task gives -32001.
  • Try also a parse error, an unknown method and bad params, which give -32700, -32601 and -32602.

12End the target mid-task

Start a new task to Codex from Claude, then end Codex before it reports.

Expect

  • The open task becomes FAILED with the reason "session ended". ratatoskr_task_get on it shows that.
  • A new send to the old session id is refused. It is not redirected to a replacement. Start Codex again with rtk attach --agents codex: it is a new session with a new id, and the old task stays failed.
  • Sending to a target the gateway knows is offline fails at once and creates no task.

13An external service takes part

Claude asks the reference adapter. It asks which format, then answers.

Expect

  • The gateway sends a standard A2A SendMessage to the registered URL. The task reaches INPUT_REQUIRED and Claude is woken. After the answer it reaches COMPLETED with a result counting lines, words and characters.
  • The gateway mirrors the adapter's task by polling it (every 5 seconds at first). The task id you see is the gateway's, not the adapter's.
  • Stop the adapter (Ctrl+C) in the middle of another task. The task stays non-final, with an observation that the participant was lost; it is not marked failed on a disconnect. A later send to refbot fails at once.
  • Replace the token file contents with a wrong value and send again: the task fails at once as FAILED with a reason that the service refused the gateway's credential (HTTP 401), and an auth=refused observation. Put the right secret back and the next send works. With no credential the adapter cannot be reached from anything but the gateway holding that secret.

14Retention, deletion and clean up

Tasks are kept until the owner deletes them. Nothing expires.

Expect

  • Restart the gateway first and check the tasks are still there. delete-tasks reports how many tasks it removed, and removes their dispatch and wake messages from the ledger. A running task is not deleted by --all-final.
  • revoke makes the next call from refbot fail and ends its open tasks with a reason.
  • Stop the gateway with Ctrl+C. To roll back the migration: stop, restore the .bak (or your copy), and run the older binary.
